# Advanced 질문 해석과 조회 분기 실험 구현 계획

2026-11-09. 이 문서는 개인 Advanced 검색 실험의 구현 계획이다. 현재 **Bigram-ID BM25 + Snowflake-ko 5:5 RRF, KURE nano 상위 3쪽, 기존 HG·원본 조회, 후보 20쪽과 최종 최대 8쪽·8,000토큰**을 비교 기준으로 삼는다. 먼저 표현 규칙을 DB에서 읽어 동일 결과를 재현하고, 다음으로 앞단 LLM의 해석 효과를 분리한다. 사건과 원본 쪽을 담는 SQLite 스키마와 빌드 절차는 [정제와 관계 조회 계획](advanced-curation-implementation.md)에 둔다.

## 1. 지원 범위와 실행 흐름

첫 실험은 개인 Advanced 평가 경로에서 실행한다. 운영 API에는 별도 입력을 추가하지 않는다. 초기 지원은 검증된 HG 사건 최대 두 개의 식별, 사건별 기록 요청, 일반 문서 질문이다. 정확히 지원되는 조회 유형은 코드가 처리한다. 표현이 다양한 질문은 LLM이 조회 단서를 제안하고 서버가 실제 자료에 대조한다. 복수 후보, 확인된 기록 없음, 해석 실패, 저장소 오류는 각각 구분한다.

```text
질문
  → 코드가 등록된 키와 지원하는 단순 요청 전체를 확인
      ├─ 확인됨 → 앞단 LLM 생략
      └─ 그 외 → LLM이 대상별 단서와 요청 기록을 한 번 구조화
  → 서버가 단서의 출처와 자료의 일치 여부를 검증
      ├─ 사건 확인 → 해당 사건의 원본 기록 확보
      ├─ 일반 규정 또는 추가 규정 필요 → 기존 5:5 검색
      └─ 대상이 모호함 → 구분에 필요한 정보를 반환할 상태로 표시
  → 원본 출처와 필수 근거를 보존한 문맥 조립
```

LLM 비교 단계에서는 두 설정의 최초 5:5 후보와 KURE 순위를 공유한다. SQLite 먼저 조회하는 단계에서만, **검증된 키와 데이터가 요청을 모두 충족하는 경로**에서 검색·리랭킹을 생략한다. 예약번호가 있어도 적용 사유나 예외까지 묻는 질문은 일반 문서 근거를 추가한다. 첫 벤치는 사건 식별과 근거 확보를 평가한다. 실제 생성 답변, 집계, 세 사건 이상, 세션에서의 대상 추론은 후속 실험 범위다. 기존 검색은 일반 문서와 지원 범위를 벗어난 요청의 처리 경로로 사용한다. [현재 검색 기본값](README.md#현재-advanced-구성)

## 2. 표현 규칙 SQLite

표현 규칙은 로컬 `artifacts/u_10o0o/advanced-routing/routing_rules.sqlite3`에 둔다. 사건·원본 출처 DB는 문서 스냅샷으로 만들고, 규칙 DB는 질문 해석 규칙의 버전으로 관리한다. 실행 결과에는 두 자료를 각각 식별할 수 있는 버전 또는 지문을 남긴다.

| 테이블 | 키와 주요 필드 | 제약 |
| --- | --- | --- |
| `rule_versions` | `version_id` PK, `base_version_id` FK, `base_activation_id` FK, `status`, `author_kind`, `created_by`, `created_at`, `content_sha256`, `validation_report_sha256` | 검증된 버전의 내용은 고정한다. 수정은 새 초안 버전에서 한다. |
| `routing_rules` | `(version_id, rule_id)` PK, `scope`, `target_code`, `match_mode`, `pattern`, `flags`, `position`, `enabled` | 대상 코드는 해당 범위에 허용된 날짜 필드 또는 기록 역할이다. 같은 버전·범위·대상·매칭 방식·표현·플래그의 중복을 막는다. |
| `rule_activations` | `activation_id` PK, `version_id` FK, `previous_version_id`, `activated_by`, `activated_at`, `reason` | 마지막 활성화 행이 활성 버전을 가리킨다. 되돌리기도 새 활성화 이력으로 남긴다. |

### 최초 적재와 로드

1. `advanced_target_lookup.py`의 `DATE_CUES`와 `ROLE_CUES`, `advanced_clause_binding.py`의 절별 `ROLE_TERMS`를 각각 `target_date`, `target_role`, `clause_role` 범위로 옮긴다. 기존 패턴 문자열·플래그·순서와 호출 범위를 유지한다. `advanced_pair_context.py`에서 공유하는 역할 규칙도 같은 로더의 해당 범위를 쓴다. BM25의 제목 보너스나 검색용 역할 단서는 현재 경로에 둔다. [대상 규칙](advanced_target_lookup.py#L52) · [절별 규칙](advanced_clause_binding.py#L28) · [공유 호출자](advanced_pair_context.py#L60)
2. 서버 또는 실험 러너는 시작할 때 활성 버전이나 실행에 지정한 검증 버전 하나를 읽어 메모리에 올린다. 실행 중 해당 버전을 고정하고 다음 실행에서 새 버전을 읽는다. SQLite 실험에서 지정한 DB나 버전이 잘못되면 시작 단계에서 오류로 표시한다. 기준선 실행은 기존 코드 규칙을 사용한다.
3. 기존 패턴은 이관할 때 `legacy_regex`로 가져온다. 새 표현은 첫 버전에서 `literal_phrase`로 받는다. 같은 NFKC·대소문자·공백 정규화를 한 뒤 해당 호출 범위에서 문자 그대로 찾는다. 날짜의 주변 범위, 문장이나 절의 경계, 충돌 처리, 명시 ID 검증은 호출 코드의 책임이다. 서로 다른 날짜 유형이 같은 날짜에 걸리면 모호함을 유지한다.

### 관리자 및 LLM 제안에서 활성화까지

- 관리자 수정과 LLM 제안은 둘 다 **현재 활성 버전에서 파생한 초안**으로 저장한다. LLM은 범위·대상 코드·새 문구·제안 이유와 확인용 예시를 구조화해 반환한다. 제안은 별도 관리 작업에서 받으며, 사용자 답변을 처리하는 경로에서는 규칙 DB를 읽기 전용으로 연다.
- 활성화 전에 허용 값·중복·패턴 형식과 기존 질문의 회귀 결과를 검사한다. 보고서 지문을 검증한 규칙 내용 지문과 연결한다. 승인 시 초안이 기준으로 삼은 활성화 ID가 현재와 같은지 확인하고, 승인 기록과 활성화 이력을 한 트랜잭션으로 저장한다. 그 사이 다른 버전이 반영됐다면 최신 버전을 기준으로 초안과 회귀 결과를 다시 확인한다.
- **첫 버전은 관리자 승인으로 활성화한다.** 문제가 있으면 이전 검증 버전을 다시 활성화하고 다음 실행에서 해당 버전을 사용한다. 관리 기능은 로컬 CLI의 초기 적재, 초안 등록, 검증, 활성화, 복귀에 한정한다. 사례 예시는 합성문 또는 접근이 통제된 문항 ID로 기록한다. [설정 검증 패턴](https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-creating-configuration-and-profile-validators.html) · [SQLite 트랜잭션](https://www.sqlite.org/lang_transaction.html)

## 3. 앞단 LLM의 계약과 서버 검증

호출에는 질문과 허용 필드·역할의 설명을 전달한다. 첫 실험은 현재 질문만 대상으로 한다. 기존 프로젝트의 스키마 기반 출력을 참고해 검증된 객체를 받으며, 해석이 필요한 요청당 호출 한 번과 시간 한도를 둔다. 아래는 합성 예시다. [기존 구조화 출력](../../app/generation/chain.py#L71) · [LangChain 구조화 출력](https://docs.langchain.com/oss/python/langchain/structured-output)

```json
{
  "route": "mixed",
  "targets": [
    {
      "anchor": "2026-05-11에 지정 장치장에 넘긴 냉동 건",
      "constraints": [
        {
          "field": "actual_designated_return_date",
          "raw": "2026-05-11",
          "polarity": "include"
        }
      ],
      "roles": ["비용 조건 약정", "계약 조건 대조 회신", "비용 청구 명세"]
    }
  ]
}
```

| 항목 | 서버가 검증할 내용 |
| --- | --- |
| `route` | `lookup`, `documents`, `mixed`, `unresolved`만 허용한다. 해석 결과를 조회 권한이나 정답 근거로 사용하지 않는다. |
| `targets`와 `anchor` | 사건 조회는 대상이 하나 또는 둘이다. 원문에 있는 대상 표현을 확인하고 각 대상의 단서와 요청 역할을 함께 보존한다. 서로 다른 절의 단서를 한 사건의 조건으로 합치지 않는다. |
| `constraints` | 지원하는 예약·장비·계약 키, 화주·화물·규격, 검증된 날짜 유형을 사용한다. `raw`가 질문의 해당 범위에 있는지 확인한 뒤 서버가 기존 규칙으로 키와 날짜를 정규화한다. 불명확한 연도·날짜 종류를 임의로 채우지 않는다. |
| `polarity` | 포함과 제외를 별도로 받는다. 제외 의미와 범위를 확인한 조건만 적용한다. 제외 표현을 이해하지 못한 경우 해당 조건을 버리고 유일 후보로 확정하는 대신 모호 상태로 둔다. |
| `roles` | 기존 HG 역할 목록으로 제한한다. 여러 대상은 각 대상별 요청을 유지한다. 역할이 불명확하면 해당 사실을 확인했다고 표시하지 않고 원본 검색과 필요한 경우 추가 확인으로 넘긴다. |

확인된 양의 단서를 기존 `TargetLookup`의 원본 기반 필드 맵에 대조한다. 지원 조건의 교집합으로 후보를 구하고, 상충하는 단서를 없애 후보를 억지로 만들지 않는다. 문서 검색에서 발견한 페이지는 추가 후보를 찾는 단서로 쓸 수 있다. 자동 확정에는 **검증된 단일 예약 키** 또는 **기존 조회에서 지원하는 복합 단서가 원본 기록에 일치하는 경우**를 사용한다. 예를 들어 화주·규격·실제 반출일을 함께 확인한다. 일반 단서 하나로 우연히 한 건이 남은 경우는 보류한다. 두 사건을 비교할 때는 양쪽을 각각 검증하고, 한쪽이 미해결이면 해결된 쪽과 구분한다. 유효한 증빙은 `(book_id, page)`와 기록 역할을 유지한다. [기존 사건 필터](advanced_target_lookup.py#L416) · [기존 복합 조회](advanced_source_lookup.py#L26) · [출처와 기록 조립](advanced_source_lookup.py#L89)

유효한 해석이 나오면 기존 문맥 조립기로 확인된 쪽을 전달한다. 두 사건의 역할을 조립 단계에서 다시 키워드로 해석하지 않도록 확인된 대상·역할 매핑을 넘긴다. 확실히 검증된 명시 ID와 모델 제안이 충돌하면 그 제안을 적용하지 않는다. 형식 오류, 빈 해석, 시간 초과는 실패 종류를 기록하고 기존 5:5 경로로 처리한다. 대상 복수와 원문 부족은 각각 되묻기와 근거 부족 상태로 보존한다.

## 4. 구현 순서와 통과 기준

| 단계 | 바꾸는 부분 | 실행과 통과 조건 |
| --- | --- | --- |
| **A → B** | 현재 5:5 기준선 → 동일 규칙을 SQLite에서 읽기 | LLM 호출 없이 동일 입력에서 사건, 역할, 원본 조회 경로, 후보 순서와 최종 문맥 지문이 문항별로 같아야 한다. |
| **B → C** | 규칙 DB 고정 → 앞단 구조화 LLM 추가 | 원래 질문의 5:5 최초 후보와 KURE 결과를 공유한다. 기존 원본 보강 직전 순위에 각각의 해석을 연결해, 후보와 최종 문맥에서 대상·역할별 근거가 얼마나 늘었는지 비교한다. |
| **C → D** | 기존 검색 후 보강 → 충분한 정확 조회만 SQLite 우선 | 별도 단계에서 진행한다. 동일 근거를 반환한 단순 조회에서 5:5 검색과 KURE를 생략했는지 확인하고, 빠진 인용과 경로별 응답 시간을 비교한다. DB 행만으로 답할 경우에는 검증된 요청 필드·상태·원본 쪽이 있어야 한다. |
| **규칙 버전 갱신** | 활성 버전 → 관리자 또는 LLM 제안이 담긴 버전 | 새 표현의 개선·하락, 예정일·실제일 혼동, 대상 오확정을 검토한다. 실패한 초안이 활성 버전을 바꾸지 않고, 이전 버전 복귀 시 결과가 재현돼야 한다. |

처음에는 가짜 모델 응답으로 **명시 ID, 번호 없는 한 사건, 두 사건의 역할 교차, 같은 날짜의 예정·실제 구분, 제외 조건, 복수 후보, 해석 시간 초과, 규칙 활성화 충돌과 복귀**를 검증한다. 다음에 상황별 140문항, 업무 규정 20문항, 일상 표현 40문항, 범위 밖 20문항을 유형별로 비교한다. 번호 없는 사건과 두 사건 질문은 해석 규칙이나 프롬프트를 고치는 데 쓰지 않은 별도 표본에서도 확인한다. 평가 입력은 질문으로 한정하고, 정답 사건·쪽·역할은 결과 저장 뒤 채점에 읽는다. 보고에는 **정확히 확정한 사건 수 / 자동 확정한 사건 수**, 오확정 건수와 분모, 역할 연결 정확도, 후보·최종의 전체 필수 근거 충족, 문항별 개선·하락, 되묻기 필요 여부, 실패 및 호출 수를 포함한다. 모호·범위 밖 질문은 자동 확정과 생성 품질을 구분해 집계한다. 경로별 p50·p95는 워밍업 후 단건 요청에서 측정하고 해석·검색·DB 시간을 나눠 기록한다. 일반 규정 질문이 해석 호출을 거쳤다면 그 비용도 따로 집계한다. 채택 조건은 별도 표본에서 대상·근거 회복이 재현되고 새 오확정이 발생하지 않으며, 사전에 정한 시간·비용 기준을 만족하는 것이다.
