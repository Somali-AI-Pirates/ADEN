# Advanced 실사용 문맥 평가 후보

Advanced 원본에서 업무 질문의 대상, 적용 조건, 답변 근거를 함께 찾을 수 있는지 확인하는 후보 세트다. [전 페이지 6,500문항](../advanced_full_coverage/README.md)은 전체 검색 범위의 기준으로, [기존 후보 410문항](../advanced_coverage_v2/README.md)은 별도 평가 세트로 보존한다.

| 기대 행동 | 파일럿 | 블라인드 후보 | 문항 구성 |
|---|---:|---:|---|
| 답변 | 20 | 250 | 필수 사실 1~5개에 각각 파일럿 4문항, 블라인드 50문항 |
| 추가 확인 | 5 | 25 | 화주·장비 규격·실제 반출일이 같고 청구액이 다른 두 HG 사건 중 하나를 특정 |
| 확정 보류 | 5 | 25 | 지정 반납 증빙과 반납지연료의 확정 상태를 함께 확인 |
| 합계 | 30 | 300 | |

블라인드 후보는 원본 PDF **120개 전체의 653쪽**을 참조한다. HG 199문항은 계약·현장·승인·청구·수납, HA 39문항은 계약·사건 증빙·터미널 정산, 업무 자료집 62문항은 예약·서류·운항·승인·청구·입금 등 실제 기록을 다룬다. 174문항에 원문이 두 쪽 이상 필요하며 20문항은 다섯 쪽을 요구한다.

한 문항은 인계, 일정 대조, 정산 확인처럼 업무 목적 하나를 다룬다. 요청하는 필수 사실 수와 근거 페이지 수를 구분한다. 자료집에서는 원문 표의 한 셀을 하나의 채점 항목으로 센다. 한 셀이 상태와 날짜를 함께 담는 경우 그 내용 전체를 채점한다.

질문은 업무 상황을 바탕으로 작성한 문장 패턴을 사용한다. 장비 규격 풀어쓰기, 화주·화물만 주는 경우, 장비 번호만 주는 경우, 계약과 청구의 조건 대조, 예정일을 실제일로 오해하는 경우를 포함한다. 실제 문의 분포는 별도 수집 대상으로 남겨둔다. 배분과 입력·산출물 지문은 [manifest.json](manifest.json)에 기록한다.

## 데이터와 검수

- 질문 파일은 `id`와 `question`만 담는다. 참고 파일은 필수 사실·근거 인용·기대 행동을 분리해 담으며, 검색과 답변을 만든 뒤 읽는다.
- 기존 공식 평가 60문항, 추가 검증 280문항, 이전 파일럿 40문항과 블라인드 후보 410문항에 연결된 사건과 근거 페이지를 제외했다. 새 파일럿과 블라인드 후보도 사건·근거 페이지를 분리했다. 후보 근거 653쪽은 모두 과거 전 페이지 평가에 등장한 원문이고, 기존과 같은 질문 문구는 제외했다.
- 채택한 인용문은 PDF 파일 지문을 확인하고 원본 레이아웃에서 다시 뽑아, 검색용 복원 페이지와 대조했다. 정답 근거만 문맥에 넣으면 후보 850항목과 파일럿 80항목을 모두 확인할 수 있었고, 가장 긴 문맥은 2,451토큰이었다. 개별 질문의 자연스러움과 기대 행동은 사람 검수 대상으로 남겨둔다.
- `local/`에 질문·참고 파일을 로컬 보관한다. 공유 기록은 집계·설정·지문으로 구성한다. 실사용 문의와 원문의 식별정보는 집계에 포함하지 않는다.

하이브리드에서 전체 근거를 새로 충족한 문항은 9개였고 기존 충족을 잃은 문항은 8개였다. 번호 없는 답변형의 순증 5개는 장비 규격을 풀어 쓴 29문항에서 나왔다. 이 유형은 8/29에서 13/29로 바뀌었다. 원문 단서를 유지한 31문항은 양쪽 모두 31개를 충족했고, 규격을 생략한 30문항은 양쪽 모두 12개를 충족했다. 번호 있는 답변형은 두 설정 모두 정답 페이지가 후보 20쪽 안에 있었으나, 하이브리드에서 6문항이 최종 문맥의 근거를 잃었다.

추가 확인형에서 하이브리드는 재정렬 전 28/100쪽, 최종 문맥에서 25/100쪽을 찾았다. 두 사건의 현장·청구 근거를 함께 충족한 문항은 두 설정 모두 0개였다. 이번 결과는 검색과 최종 문맥에 있는 근거를 채점한 값이다. 생성 호출은 0회였으며 실제 답변·추가 확인·보류 행동은 별도 평가 대상이다.

이 비교에서는 기존 BM25 기반 설정을 유지한다. 하이브리드는 규격을 풀어 쓴 질문에서 개선을 보였고, 번호가 있는 질문에서는 최종 근거를 잃었다. 전체 근거 충족의 차이는 1문항이었다. 이 세트는 같은 Advanced 원문을 바탕으로 만든 업무형 질문이며, 문항별 자연스러움과 기대 행동의 사람 검수는 남아 있다.

## 추가 확인형 25문항 답변 비교

2026-11-09에 저장한 두 검색 설정의 최종 문맥을 그대로 복원해 GPT-6 Luna로 25개씩 답변을 생성했다. 두 설정에 같은 서비스 프롬프트와 생성 조건을 적용했다. GPT-6 Luna 채점기는 검색 방식과 응답 상태를 가린 상태에서 질문과 답변 본문을 평가했다. 적절한 되묻기는 화물명·예약번호·장비번호처럼 아직 주어지지 않은 구분 정보를 요청하면서 사건과 금액을 확정하지 않은 경우다. 후보 금액을 조건부로 언급한 경우는 금액 언급으로 따로 셌다. [실행 설정과 집계](clarify-answers.json)

| 답변 본문 기준 | 본문·제목 BM25 | BM25 + Snowflake-ko 5:5 |
|---|---:|---:|
| 금액 단정 없이 구분 정보를 되물음 | 0/25 | 3/25 |
| 질문의 대상에 금액을 단정함 | 0/25 | 4/25 |
| 조건부 후보를 포함해 금액을 언급함 | 0/25 | 15/25 |
| 사건·금액 단정 없이 되묻지 않음 | 25/25 | 16/25 |

응답 상태는 BM25에서 보류 25개, 하이브리드에서 보류 19개·답변 완료 5개·추가 확인 1개였다. 하이브리드에서 본문 기준으로 적절히 되물은 3개는 서로 다른 응답 상태를 반환했다. 최종 문맥에 정답 쪽이 하나라도 있었던 문항은 BM25 0개와 하이브리드 20개였으며, 어느 설정에서도 한 사건의 반출과 청구 근거가 모두 들어오지 않았다. 하이브리드에서는 되묻기가 늘었지만 금액 단정도 발생했다. 50개 응답의 자동 채점을 마쳤고, 생성 요청 51회와 채점 요청 50회를 기록했다.

## 추가 확인형의 실패 지점과 개선 실험

### 검색 결과가 사건을 특정하지 못한 이유

질문마다 같은 화주·규격·실제 반출일에 해당하는 사건이 두 건이다. 사건별 실제 반출일은 현장 기록, 보관료는 청구 명세에서 확인한다. 앞선 결과를 같은 입력으로 재현하고 25문항의 필수 100쪽이 각 단계에 얼마나 남았는지 세었다.

| 검색 단계 | 필수 쪽 확보 | 두 사건에서 각각 한 쪽 이상 확보 | 한 사건의 현장·청구 두 쪽을 확보 |
|---|---:|---:|---:|
| BM25 후보 20쪽 | 0/100 | 0/25 | 0/25 |
| Snowflake-ko 후보 20쪽 | 38/100 | 15/25 | 0/25 |
| RRF 결합 후보 20쪽 | 28/100 | 7/25 | 0/25 |
| 하이브리드 최종 문맥 | 25/100 | 5/25 | 0/25 |

최종 문맥에서 찾은 정답 25쪽은 모두 청구 명세였다. 날짜는 BM25에서 숫자 단위로 나뉘고, 질문의 풀어 쓴 규격과 원문의 규격 코드는 표현이 다르다. RRF는 두 검색 순위를 합쳐 페이지를 고른다. 같은 사건의 현장·청구 기록을 묶어 남기는 조건은 없다. 기존 HG 간접 조회도 날짜가 든 25문항을 전부 `unsupported_constraint`로 처리했고, 화물명까지 있는 고유 조합을 요구했다. [BM25 토큰화](../../bm25.py#L38) · [기존 HG 조회](../../advanced_hg_lookup.py#L167) · [Azure AI Search의 RRF](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)

### 바꾼 조건과 답변 결과

검증된 원문에서 화주·장비 규격·실제 적입 반출일을 가져와 정확히 일치하는 사건을 조회했다. Azure AI Search의 구조화 필터처럼 사건의 속성으로 후보를 제한하는 방식을 로컬 조회로 구현했다. 후보가 여러 건이면 구분할 정보를 한 가지 묻는 방식은 Qulac과 모호성 감지·확인 질문·다음 답변을 나눠 평가한 연구를 참고했다. [실험용 조회 코드](../../advanced_clarify_lookup.py) · [Azure AI Search 필터](https://learn.microsoft.com/en-us/azure/search/search-filters) · [Qulac](https://arxiv.org/abs/1907.06554) · [Clarify When Necessary](https://arxiv.org/abs/2311.09469)

| 변경 조건 | 두 사건의 필수 4쪽 확보 | 적절히 되물음 | 금액 단정 |
|---|---:|---:|---:|
| 기존 하이브리드와 기존 프롬프트 | 0/25 | 3/25 | 4/25 |
| 기존 하이브리드 문맥에 확인 지시만 추가 | 0/25 | 25/25 | 0/25 |
| 원문 필드로 두 사건의 4쪽을 확보하고 기존 프롬프트 사용 | 25/25 | 3/25 | 22/25 |
| 원문 필드 조회로 복수 사건 확인 후 규칙으로 되묻기 | 25/25 | 25/25 | 0/25 |

프롬프트 보완은 사건 확인 전 금액을 제시하지 말고 화물명·예약번호·장비번호 중 아직 받지 않은 정보를 묻도록 했다. GPT-6 Luna로 두 변경군을 각 25문항씩 생성하고 기존과 같은 본문 기준으로 채점했다. 생성 51회, 채점 50회를 기록했다. 원문 조회 조건에서 두 사건의 근거를 모두 제공해도 기존 프롬프트로 금액을 단정한 응답이 22개였다. 자료가 충분히 검색됐는지와 질문이 어느 사건을 가리키는지는 별도로 확인할 필요가 있다. [집계와 실행 설정](clarification-debug.json)

규칙은 실제 반출 날짜가 명시된 보관료 문의에서 여러 사건이 정확히 일치하면 화물명 또는 예약번호를 묻는다. 나머지 275문항과 파일럿의 나머지 25문항에서 잘못 발동한 건은 없었다. 새 규칙과 같은 원문 코퍼스에서 골라 문장을 바꾼 별도 복수 사건 25개, 단일 사건 25개, 식별자·예정일·부정·집계 등 250개 대조 입력도 확인했다. 두 후보 중 하나의 예약번호를 준 50개 후속 입력은 기존 명시 HG 조회로 해당 원본 기록을 찾았다. 이번 검증은 고정된 문항과 표현에 대한 개인 실험이다. 사람의 답변 판정과 후속 턴의 금액 생성 검증은 별도 범위다.

[검색 비교 스크립트](../../advanced_usage_retrieval.py)는 기본으로 파일럿만 읽는다. 본문·제목 BM25와 같은 BM25에 Snowflake-ko를 5:5 RRF로 더한 방식을 비교한다. 양쪽 모두 후보 20쪽, 같은 KURE nano, HG 조회, 최대 8쪽·4,000토큰을 적용한다. PDF 근거가 후보에 들어왔는지, 조립한 문맥에 필수 사실의 인용이 모두 남았는지를 각각 센다.

~~~bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 TOKENIZERS_PARALLELISM=false \
  uv run --no-sync python -m experimental.u_10o0o.advanced_usage_retrieval \
  --data experimental/u_10o0o/evaluation/advanced_usage_blind/local \
  --output artifacts/u_10o0o/advanced-usage-pilot-replay
~~~

300문항 검색을 재실행하려면 같은 명령에 `--split blind`와 새 출력 경로를 지정한다.
