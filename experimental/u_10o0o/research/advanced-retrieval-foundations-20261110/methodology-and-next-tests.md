# 문제 정의와 다음 검증의 경계

2026-11-10. 이번 문서는 조사 후의 제안이다. 새 검색 설정을 구현하거나 채택한 기록이 아니다.

## 1. 사용자가 해결하려는 업무

Advanced 자료에서 **질문이 가리키는 대상과 요청을 확인하고, 그 요청을 충족하는 원본 기록·규정을 빠짐없이 찾아 출처와 함께 반환**한다. 질문이 특정 사건을 구별할 정보를 주지 않으면 확인이 필요한 상태로 남긴다. 특정 검색 모델의 사용 여부나 전체 평균 점수 자체를 목표로 삼지 않는다.

다음 세 업무는 성공 조건이 다르다.

| 업무 | 성공 조건 | 잘못된 성공 판정 |
| --- | --- | --- |
| 특정 사건의 값·상태 조회 | 같은 사건, 같은 기록 역할, 같은 날짜 종류·효력·단위의 원본을 찾음 | 같은 장비 유형의 다른 사건이 상위에 나옴 |
| 일반 업무 규정·예외 탐색 | 질문의 업무와 적용 조건을 설명하는 규정을 찾음 | 질문에 등장한 계약 코드만 맞는 사건 기록을 찾음 |
| 사건과 규정 또는 여러 대상의 결합 | 각 요청의 근거를 모두 확보하고 연결의 유효성을 확인함 | 한 요청의 유사한 페이지가 여러 개 검색됨 |

`20GP`처럼 공유되는 표현에는 **특정 건을 찾는 요청, 그 종류 전체를 나열하는 요청, 그 종류의 일반 규칙을 묻는 요청**이 모두 가능하다. 표현의 후보 수와 사용자의 요청 종류를 함께 봐야 한다. 특정 사건 요청에서 후보가 여러 개라는 이유와 일반 규정 질문이라는 이유를 혼동하지 않는다.

현재 평가 세트는 운영 질문의 분포를 추정할 수 있는 실제 서비스 로그가 아니다. '코드 질문이 주류일 것'은 데이터 특성으로 세운 가설이며, 이를 반영한 테스트 비율을 실제 이용 비율이라고 부르지 않는다.

## 2. 지금 확인한 것과 아직 설명이 필요한 것

- **확인한 것** — 알려진 HG 사건과 기록 역할의 연결은 이미 매우 규칙적이며 기존 조회가 이용한다. 기존 메모리→SQLite 비교에서는 220문항의 경로·순서·최종 문맥이 모두 같았다. 그 결과로 DB 제품 변경의 품질 이득을 주장할 수 없다.
- **확인한 것** — 최근 새 질문 검증에서 두 HG 사건 질문은 6/6, HG와 IS 규정의 혼합 질문은 1/6이었다. 혼합 실패 5건 중 4건은 규정 근거가 보강 후 후보에도 없었고, 1건은 후보에 있었지만 최종 선택에서 빠졌다. 이 표본에서는 원인이 적어도 두 단계로 나뉜다. [원 기록](../../records/advanced-plan-followup-20261110/stage-3.md)
- **설계 가설** — 현재의 결정론적 조회를 포함한 전체 흐름 중 페이지 유사도 기반 후보를 합치고 선택하는 구간이 '대상 식별', '기록 관계 조회', '업무 규정 탐색'을 같은 점수·예산으로 처리하는 구간에서 손실이 생길 수 있다. 필드·관계·적용 범위를 명시하면 이 손실을 줄일 수 있다.
- **미검증** — IS 규정 누락 각각이 잘못된 검색 표현, 입력 구조, 모델의 한국어 의미 대응, 후보 경쟁 중 어느 원인인지 아직 충분히 분리하지 못했다. 현재 결과만으로 GraphRAG나 새 임베딩 모델이 해결한다고 결론내릴 수 없다.

다음에는 실패 문항마다 **질문에서 알 수 있는 정보 → 올바른 대상 후보 → 필요한 기록/규정 → 검색 가능 여부 → 후보 포함 → 최종 포함**을 한 줄로 연결한다. 이 연결 없이 새 점수표를 추가하면 원인 설명이 다시 끊긴다.

## 3. 조사 다음에 먼저 할 진단

네 업무의 성공 조건을 고정한 뒤, 최초 진단 대상으로 최근 혼합 질문의 IS 규정 후보 누락 네 사례를 사용한다. 해당 문항에 특수 규칙을 맞추지 않고 재현되는 실패 유형을 찾는 데 쓴다. 이미 결과를 본 문항은 이후 개발용으로 취급한다. 아래는 결과에 따라 사용할 진단 도구 목록이며 모두 재실행할 계획이 아니다. 기존 전 HG 관계 검증과 저장층 동등성은 재사용하고 새 실패 조건이 없는 전체 재시험은 하지 않는다. 아래 진단은 제품 성능 비교와 별도로 기록한다. 진단에 정답을 사용한 결과에는 `oracle diagnostic`을 명시하고 일반 검색 성적으로 집계하지 않는다. 이번 조사에서는 실행하지 않았다.

| 진단 | 고정·개입할 부분 | 답할 수 있는 질문 |
| --- | --- | --- |
| 대상 해석 진단 | 검색기는 그대로, 사람이 확인한 대상·요청만 입력 | 실패가 질문 해석 때문인가? |
| 조회 연결 진단 | 올바른 대상과 역할을 주고 DB 출처를 대조 | 식별 이후 관계나 원본 연결이 빠졌는가? |
| 규정 검색 진단 | 동일한 원 요청으로 전체 색인과 확인된 업무 범위 검색을 대조 | 다른 종류의 페이지와 경쟁해서 놓치는가? 범위 정보의 실용적 추출 가능성은 별도다. |
| 입력 단위 진단 | 같은 모델에서 원본 페이지와 제목·조건·표 관계를 보존한 검색 단위를 대조 | 필요한 의미가 한 페이지 표현에 묻혀 있는가? |
| 최종 선택 진단 | 후보를 고정하고 필수 요청별 근거 존재 여부를 직접 대조 | 후보에 충분한데 순위·중복·페이지 상한 때문에 빠지는가? |

예를 들어 규정의 올바른 업무 범위를 알려줘도 검색을 못 한다면, HG 라우팅을 더 정교하게 만드는 것은 해당 실패를 해결하는 개입이 아니다. 반대로 원문 표에 값과 열의 대응이 잘못되어 있으면 모델 교체보다 추출 검증이 선행해야 한다. 특정 표본의 개선만으로 전체 원인을 하나로 단정하지 않는다.

## 4. 데이터에 맞춘 검증 묶음

기존 공식·동료·일상 표현 세트는 회귀 비교로 유지한다. 아래 목록 전체를 새로 생성하겠다는 뜻은 아니다. 기존 문항이 덮는 범위를 재사용하고, 특히 부분표현의 식별 가능성을 통제한 검증이 빠졌는지 먼저 확인한다. 새로운 묶음은 **같은 업무를 통제해 표현과 식별 가능성만 바꾸는 쌍**으로 만든다. 질문 생성 후 그 문장이 실제로 원본의 해당 대상을 유일하게 가리키는지 독립 검수한다.

| 묶음 | 통제된 변경 | 기대 행동 |
| --- | --- | --- |
| 완전 코드 | 대소문자·허용된 대시·공백 표기 | 원문·업무 규칙에서 동등성이 검증된 표기라면 같은 대상 |
| 코드 오타 | 실제 존재하는 다른 코드로 한 자리 변경 / 존재하지 않는 코드 | 전자는 다른 대상, 후자는 무조건 원래 대상으로 보정하지 않음 |
| 부분 코드·유형 | 유형만 / 유형+계약 / 유형+날짜+화주 | 후보 집합 변화가 실제 DB와 일치. 유일한 경우와 여럿인 경우를 구별 |
| 간접 대상 | 코드 대신 실제로 식별 가능한 업무 단서 | 대상 및 요청 기록 유지 |
| 날짜·부정 | 예정↔실제, 포함↔제외, 정정 전↔후 | 관련 조건이 바뀌며 원래 정답을 그대로 반환하지 않음 |
| 무코드 규정 | 공식 용어↔현장식 표현, 전문용어 축약 | 같은 업무 조건과 예외 근거 |
| 혼합 요청 | 사건 조회만 / 같은 조회+규정 요청 | 기존 조회는 유지하고 추가 규정까지 확보 |
| 관계 경로 | 원문에서 확인된 코드→사건→기록 또는 사건→계약→규정 | 각 연결의 출처와 적용 범위가 유효 |
| 실제 모호함 | 식별 단서를 제거하거나 서로 모순되게 설정 | 단정 대신 후보·부족한 조건을 반환 |
| 집합·집계 | '이 건'↔'이 조건인 모든 건' | 한 사건 확정과 전체 집합 조회를 구별 |

이는 CheckList의 최소 기능·불변성·방향성 검사를 이 업무에 적용한 제안이다. 단순히 문장을 복잡하게 만든 테스트와 업무 요구를 구별할 수 있다. [CheckList 원 논문](https://aclanthology.org/2020.acl-main.442/)

임의의 서로 무관한 네 문서를 이어 붙인 합성 문제도 다중 검색의 스트레스 검사에는 쓸 수 있다. 다만 '현장 복합 질문'이라고 집계하려면 한 업무에서 함께 요청할 이유와 각 문서의 필수성을 확인해야 한다. 기존 합성을 삭제하거나 낮은 결과를 임의로 제외하지 않고 용도를 표시한다.

## 5. 채점에서 보존할 것

1. **대상 후보 정확도** — 가능한 대상을 빠뜨렸는지와 다른 사건을 유일하게 확정했는지를 별도 집계한다. 오확정은 값이 비슷해도 성공이 아니다.
2. **대상·요청 쌍 정확도** — A의 청구와 B의 수납을 바꾸지 않았는지 확인한다. 대상과 역할을 각각 맞힌 비율만으로 대체하지 않는다.
3. **관계 조회 완전성** — 검증된 사건의 요청 기록과 원본 출처가 모두 일치하는지 본다.
4. **후보 전체 근거 충족** — 검색·DB를 합친 후보에서 각 요청의 필수 근거를 충족하는지 본다. DB 단독 경로의 빈 텍스트 후보를 검색 실패로 세지 않는다.
5. **최종 전체 근거 충족** — 최대 8쪽·8,000토큰 안에서 모든 요청을 충족하는지 본다. 페이지 `(book_id, page)` Recall, 요청별 충족률과 함께 기록한다.
6. **실행 비용** — 전체 p50·p95와 실제 LLM 호출, 검색 횟수, 리랭커 쌍 수, 인덱스 크기·빌드 시간을 나눈다. API 과거 시간의 합과 실측 wall-clock을 구별한다.

대상·역할 정답이 독립 작성되지 않고 인용에서 유추된 proxy인 기존 동료 세트는 인식의 참고 지표로 쓴다. 정답 목록 밖의 역할을 전부 잘못된 과잉 검색으로 간주하지 않는다. 반복 문구가 다른 페이지에 있어도 같은 사건·효력·조건을 보장해야 대체 근거로 인정한다. 특정 정답 페이지와 달라도 업무상 충분한 근거일 수 있으므로, 기존 정답 목록에 없는 페이지를 곧바로 오답이라고 단정하지 않는다. 반대로 공통 규칙 문장이 같다는 이유로 다른 사건의 금액 출처를 대체하지 않는다. 불완전한 relevance judgment가 평가를 흔들 수 있다는 문제는 검색 평가 연구에서도 다룬다. [NIST, Retrieval Evaluation with Incomplete Information](https://www.nist.gov/publications/retrieval-evaluation-incomplete-information)

## 6. 한 번에 검증할 주장

우선순위는 모델 수를 늘리는 순서가 아니다. 위 진단에서 실제로 남은 실패 유형을 확인한 뒤 아래 개입 중 하나만 선택한다.

- **코드/간접 대상 문제가 남았다면** 기존 관계 DB를 재사용해 타입별 키·부분표현·복합 조건의 후보 집합을 정확하게 만든다. 새 그래프 서버를 비교 변수로 넣지 않는다.
- **규정 입력 문제가 남았다면** 이미 실행한 IS 머리말 제거·표 재렌더링 결과를 먼저 재사용한다. 그 결과가 설명하지 못하는 실패 조건에서만 업무명·제목·표 열·조건·예외를 보존한 다른 검색 단위를 비교한다. BM25·임베딩·최종 원문은 각각 어느 부분을 바꿨는지 기록한다. 기존 머리말 제거와 표 렌더링에서 무엇을 바꾸는지 명시한다. [실행 상태 감사](prior-evidence.md)
- **규정 표현 대응 문제가 남았다면** 같은 검색 단위와 최종 선택에서 기존 BM25+dense, 다국어 learned sparse 또는 late interaction 중 한 대안을 비교한다. 모델의 일반 벤치 점수로 채택하지 않는다.
- **근거 선택 문제가 남았다면** 같은 후보에서 대상×요청별 충족 제약을 둔 선택을 검증한다. 기존 역할 기반 선택·두 사건 배치와 달라진 입력과 보장 범위를 먼저 설명한다.
- **문서에 명시된 다중 관계 문제가 남았다면** 동일 seed와 동일 원본 자료로 제한된 경로 조회를 비교한다. seed 정확도, 경로 유효성, 최종 근거를 따로 재며 공통 업체·장비 유형만으로 무제한 확장하지 않는다.

새 질문만 만든 경우와 새 사건·문서까지 분리한 경우를 구별한다. 현재 원문 전체를 이미 여러 차례 본 상태이므로 모든 역사적 노출에서 독립인 검증이라고 부르지 않는다. 진단 없이 모든 조합을 교차 실행하지 않는다. 실패 원인별 상한, 예상 개선 대상, 허용하지 않을 오확정, 비용 한계를 적고 조건을 고정한 뒤 별도 검증에서 판단한다. 채택에는 유형별 순증과 반복·별도 표본에서의 재현이 필요하다. 운영 지연 목표는 아직 정해지지 않았으므로 임의의 p95를 '실사용 가능' 기준으로 만들지 않는다.

## 7. 추가로 확인한 1차 자료

확인일은 2026-11-10이다. 다음은 설계 판단을 돕는 연구·서비스의 근거이며 ADEN에서 같은 효과가 난다는 증거는 아니다.

| 자료 | 확인한 내용 | ADEN에 적용할 해석 |
| --- | --- | --- |
| [BEIR, NeurIPS 2021](https://arxiv.org/abs/2104.08663) | 서로 다른 retrieval 과제에서 lexical·dense·sparse·late interaction·reranking을 비교했다. BM25가 견고한 기준선이었다. | 정형 식별자가 많은 자료에서 BM25가 높게 나오는 현상을 그 자체로 이상으로 보지 않는다. 최근 한국어 모델의 순위는 이 논문으로 판단하지 않는다. |
| [Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval) | 정확한 코드의 어휘 검색과, 분할된 단위에 설명 문맥을 붙이는 방식을 다룬다. | 코드와 업무 의미를 구별하고 IS 검색 단위에 이미 존재하는 문서 구조를 보존하는 가설에 참고한다. 업체의 개선율을 ADEN의 예상 개선율로 옮기지 않는다. |
| [Google Document AI layout parser](https://docs.cloud.google.com/document-ai/docs/layout-parse-chunk) | 제목 계층·표와 문단의 관계를 유지하고 검색 단위에 상위 제목 문맥을 포함한다. | 기존 복원 파서로 같은 구조 정보를 얻을 수 있는지 먼저 확인한다. 서비스 도입 필요성을 뜻하지 않는다. |
| [Dense X Retrieval, EMNLP 2024](https://aclanthology.org/2024.emnlp-main.845/) | 검색 단위가 성능에 영향을 주며 자기완결적인 사실 단위를 연구한다. | 코드·기간·조건을 잃지 않는 단위가 필요하다. 사실을 작게 나누면 항상 좋아진다는 뜻은 아니다. |
| [Azure agentic retrieval](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview) | 하위 질문 생성·병렬 검색·출처가 있는 결과 병합을 설명하고 추가 지연을 명시한다. | 지난 요청별 검색의 설계 레퍼런스는 존재한다. ADEN 별도 표본의 개선 부재까지 덮는 채택 근거는 아니다. 일부 기능은 preview다. |
