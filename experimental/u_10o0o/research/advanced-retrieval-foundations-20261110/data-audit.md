# Advanced 검색 기초 재분석: 원본·캐시·SQLite 데이터 감사

2026-11-10. 이 문서는 기존 설계 가설을 전제로 삼지 않고 Advanced PDF, 복원 페이지 캐시, 출처 연결 SQLite와 고정 질문 세트를 다시 집계한 결과다. 코퍼스나 검색 동작을 바꾸지 않았고 검색 실험도 수행하지 않았다. 집계 입력, 해시, 정의는 [data-audit.json](data-audit.json)에 남겼다.

## 먼저 확인한 범위

- 데이터 manifest의 PDF 120개 전체 SHA-256이 원본 파일과 일치했다. 복원 캐시 18,000쪽은 `(book_id, page)`가 모두 유일하고, SQLite `source_pages`와 쪽 키 집합이 정확히 일치했다. 각 PDF의 캐시 쪽수도 SQLite 문서 메타데이터와 일치했다.
- 원본 PDF에서 AS001·006·007·016·056·057·088·120의 1·75·150쪽을 PyPDF 레이아웃 추출로 다시 읽었다. 24쪽 모두 NFKC 정규화 후 공백을 제거하면 복원 캐시와 같았다. 원문 문자열 자체는 정규화로 달라졌으며, 전 18,000쪽을 PDF에서 다시 추출한 검사는 아니다.
- `structured-v1`, `hg-code-relations-v1`, `hg-relations-v1` 세 SQLite 파일은 각 manifest의 DB 해시와 일치하고 `integrity_check=ok`, 외래 키 오류 0건이었다. 상세 입력 지문과 검사값은 JSON에 있다.

페이지 구성은 HG 13,650쪽, HA 594쪽, IS 3,750쪽, 기타 6쪽이다. HG는 2,730건마다 다섯 역할 쪽이 있고, 각 쪽은 서로 다른 PDF에 있다. 역할 쪽 13,650개가 전부 고유하다. AS007–056과 AS057–120에 역할 쪽이 걸치는 사건은 108건이다. HA 198건은 3역할·594쪽으로 연결되고 파싱된 표 행은 4,356개다. IS 표는 27,715행이며 `기록번호` 5,321개와 `처리 기록` 5,752개, 합계 11,073개의 `(키 종류, 키 값)`이 이 스냅샷에서 모두 유일하다.

전체 구조화 레코드 141,174개 중 `needs_review` 26,635개가 남아 있다. 따라서 SQLite의 구조화 레코드를 18,000쪽 전체의 완전한 의미 전사로 보지 않는다. 근거 페이지 원문과 미검토 구간은 기존 복원 페이지가 기준이다. [원본 manifest](../../../../data/advanced/dataset-manifest.json) · [구조화 스냅샷](../../../../artifacts/u_10o0o/advanced-snapshots/structured-v1/manifest.json)

## 완전 ID와 넓은 장비 분류는 서로 다르게 작동한다

HG 코드 관계 스냅샷은 전체 2,730건에서 검증된 원문 코드의 관계를 저장한다. 아래에서 사건 식별자인 예약/HG·CT·AP·INV·RCPT·HL·EV 값은 다른 사건으로 연결되지 않았다. 이는 사건 ID 유형에 한정된다. HS도 문법상 완전 코드지만 출처 묶음 유형이므로 여러 사건에 연결되며 사건 식별자 통계에서 제외한다. 사건 하나가 같은 유형의 사건 코드 값을 여러 개 가질 수도 있다.

| 값 종류 | 완전 값 수 | 여러 사건에 연결된 값 | 사건별 값 수 |
| --- | ---: | ---: | --- |
| 예약/HG | 2,730 | 0 | 전부 1 |
| 계약/CT | 2,730 | 0 | 전부 1 |
| 승인/AP | 2,730 | 0 | 전부 1 |
| 청구/INV | 2,730 | 0 | 전부 1 |
| 수납/RCPT | 2,730 | 0 | 전부 1 |
| 장비/HL | 2,821 | 0 | 2,639건은 1개, 91건은 2개 |
| 증빙/EV | 7,917 | 0 | 273건은 2개, 2,457건은 3개 |
| 원본 묶음/HS | 120 값 | 120개 모두 | 묶음당 50–150건; `HS-057`은 150건 |

예약과 계약 코드는 이 자료에서 사건당 하나이고 다섯 역할 쪽에 반복된다. 증빙은 사건당 2–3개, 장비 코드는 91건에서 두 값이 함께 나온다. 둘 이상인 사례를 곧바로 정정 오류나 장비 변경으로 해석할 근거는 없다. 원문 역할·시점 조건을 봐야 한다. 청구/수납 코드는 사건당 하나다. HS는 PDF 묶음 단위라 사건을 좁히는 고유 키가 아니다. 검증 예시 `HS-057` 하나가 HG 사건 150건에 연결된다.

프로필에서 검증된 장비 분류는 두 종류다. `20GP`는 1,350건·완전 HL ID 1,350개, `40GP`는 1,380건·완전 HL ID 1,380개와 연결된다. 즉 사건 식별자 유형의 완전 ID는 이 스냅샷에서 사건 단위로 유일하지만 장비 종류는 각각 1,350건과 1,380건을 묶는다. HS 출처 묶음 코드는 이 규칙에 포함되지 않는다. 합성 예로 `HG20XX-<예약번호>`는 사건 조회 키이고 `20GP`는 후보를 줄이는 장비 분류다. 약칭만으로 사건을 하나 고르면 안 된다.

계약/CT가 2,730건에서 유일한 것도 이 스냅샷의 관측값이다. 일반 운영에서도 계약 하나가 예약 하나에만 대응한다고 결론 내릴 수 없다. 질문에 나온 계약 ID의 완전 일치와 여러 예약에 걸친 계약 허용 여부는 데이터에서 따로 검증해야 한다. [코드 관계 스키마와 추출 경계](../../advanced_hg_relations.py)

## 프로필·복합키·날짜의 충돌

| 프로필 필드 | 값 수 | 값당 사건 수 |
| --- | ---: | ---: |
| 화주 | 30 | 각 91건 |
| 화물 설명(정규화 문자열) | 2,730 | 각 1건 |
| 장비 분류 | 2 | 1,350건 또는 1,380건 |
| 계약 ID | 2,730 | 각 1건 |

화물 문자열은 NFKC·대소문자·공백만 정규화해도 2,730개가 고유했다. 그러나 2,730개 전부 숫자 묶음 1개를 포함했고, 숫자만 `#`로 가리거나 제거하자 15개 값으로 줄어 각 그룹이 182건이 됐다. 화주+화물 문자열의 2,730개 고유 조합은 숫자를 가린 뒤 90개로 줄고 최대 31건이 겹친다. 화주+화물+장비 분류는 정확 문자열 기준 2,730개였지만 숫자를 가리면 180개, 조합당 최대 16건이다. 숫자의 실제 의미는 확인하지 않았으므로 이 결과는 의미상 화물 고유성을 뒷받침하지 않는다.

날짜도 단독 키가 아니다. 같은 날짜 값이 여러 사건에 걸쳐 재사용된다. 실제 양하일 2,730건은 700개 날짜 값에 분포하고 한 날짜에 최대 4건, 실제 반출일은 704개 날짜 값·최대 8건, 예정 반납일은 683개·최대 8건이다. 실제 지정 반납일은 2,457건만 날짜로 확인되며 182건은 영수 기록 누락, 91건은 비지정 야드 기록만 있어 값이 미검증 상태다. 정정 효력일은 273건만 기록됐다(175개 날짜 값, 최대 4건).

같은 `case_id × fact_code` 안에서 둘 이상의 정형 날짜 값이 나온 건은 0건이다. 이는 선별된 `role_facts` 기준이다. 양하일·반출일·예정 반납일·시스템 입력일·정정 효력일은 서로 다른 사건 시점을 뜻하므로 하나의 일반 `date`로 합치면 안 된다. 이 데이터 검사만으로 PDF 전체의 날짜 충돌이 없다고 말할 수는 없다.

## 코드가 없는 질문도 기준 세트에 있다

질문 특징은 검색 전 질문 본문에서만 판정했다. “완전 코드”는 `HG20xx-…` 또는 지원된 `AP-/CT-/EV-/HL-/INV-/RCPT-/HS-` 전체 표기를 말한다. HS는 구문상 완전 코드여도 사건 ID가 아니라 출처 묶음 코드다. “별도 장비 분류”는 인식된 완전 ID 구간을 지운 뒤 남은 `20GP` 또는 `40GP`다. 따라서 `HL-20GP-…` 안의 `20GP`를 별도 약칭으로 세지 않았다. 40HC 등 다른 미등록 표기는 이 집계에 포함되지 않는다.

| 질문 세트 | 문항 | 완전 ID 포함 | ID 바깥 별도 분류 | ID/분류 모두 없음 | 코드 없는 질문의 참고 근거 |
| --- | ---: | ---: | ---: | ---: | --- |
| 공식 Development+Additional | 60 | 15 | 9 | 36 | 15는 HG 1건, 19는 비-HG 쪽, 2는 매핑되지 않음 |
| 동료 합성 세트 | 304 | 165 | 22 | 124 | 14는 HG 1건, 69는 여러 HG 사건 인용 합집합, 41은 비-HG 쪽 |
| 일상 표현 semantic 세트 | 40 | 0 | 0 | 40 | 40/40이 IS 쪽만 인용 |

공식 60문항에서 완전 ID 15개는 전부 장비 코드 안에 분류 토큰이 포함됐으며, 별도 분류만 언급한 문항은 9개다. 동료 304문항은 거짓 전제 20개, 2문서 합성 114개, 다문서 합성 170개로 구성됐다. 그중 ID 바깥 분류 토큰은 22문항이고, 7개는 완전 ID도 함께 포함한다. 동료 세트에서 코드/분류가 모두 없는 124문항 중 참고 페이지가 여러 HG 사건에 걸치는 69건은 질문이 여러 사건을 비교할 수 있어 정답 사건 수로 해석하지 않았다.

공식 문항의 “비-HG 쪽”은 정책/양식 참고 근거일 수 있으며, 자동 의미 라벨은 아니다. 일상 표현 40문항은 참고 근거가 IS로만 연결되어 있어 코드 없는 절차·정책 질문의 별도 근거가 된다. 이 세트도 운영 질문 로그는 아니다. 따라서 위 비율을 실제 사용자 질의 비율로 일반화할 수 없다. ## 검색 설계에 주는 데이터 근거

1. 질의에 예약/HG·AP·CT·EV·HL·INV·RCPT 사건 식별자의 완전 값이 있으면 전체 값 기준 관계 조회가 이 코퍼스에서 직접적인 키다. 해당 유형 값은 다른 사건에 연결되지 않았다. HS 전체 코드는 출처 묶음이므로 사건 키로 쓰지 않는다.
2. `20GP`/`40GP`, 화주, 날짜는 사건 식별자와 다르다. 분류는 1,350–1,380건, 화주 하나는 91건, 날짜 하나는 최대 4–8건과 연결됐다. 대상/역할/시점 조건 없이 단독 확정 키로 취급하지 않는다.
3. 화주·화물·날짜 설명이 있는 코드 없는 질문과 일반 정책 질문도 별도 경로가 필요하다. 이 관측은 검색 경로를 분리하는 가설을 뒷받침할 뿐, 실제 성능 개선을 입증하지 않는다.
4. 원본 묶음/HS, 화물 수치 포함 문자열, 날짜 값을 근거 없이 유일 키로 승격하지 않는다. 출처 페이지와 해당 값의 역할·상태를 유지한다.

모든 키 충돌 수와 날짜별 분모, 입력 파일 SHA-256은 [data-audit.json](data-audit.json)에 기록했다. 원문 페이지 인용, 질문 문장, 화주·화물명, 실제 사건 코드 값은 복사하지 않았다. 범위를 설명하는 장비 분류와 검증된 출처 참조 예시 `HS-057`은 포함했다. 원문 대조 표본 외의 전체 페이지 재추출, 실제 질의 로그 분석, 운영 고유성 검증은 범위 밖이다.
