# Advanced 데이터에서 다시 정의한 검색 문제

2026-11-10 · 원문 패턴, 코드 관계, 기존 실험, 공개 레퍼런스 조사

**Advanced는 사건 레코드와 업무 규정이 함께 들어 있는 자료다. 확인된 코드와 관계는 직접 조회하고, 업무 표현·규정은 검색하며, 두 근거가 함께 필요한 요청은 각각의 근거를 보존하는 구조가 잘 맞는다.** 이 구조의 일부는 이미 구현돼 있다. 이번 조사의 결론은 새 GraphRAG 엔진을 추가하는 것이 아니라, 기존 구성의 지원 범위와 남은 실패 위치를 더 정확하게 정의하는 것이다.

이번에는 자료·코드·기존 결과를 읽고 공개 문서와 논문을 조사했다. 검색 기준선을 변경하거나 새 모델을 호출하지 않았다. 데이터 통계·PDF 표본 대조·토크나이저 출력만 로컬에서 재확인했다.

## 1. 사용자의 관찰에서 확인된 부분

복원 캐시와 검증 DB의 18,000쪽을 재집계했다. PDF 파일 순서와 업무 양식은 일치하지 않는다. AS007–056 안에도 IS와 HG가 섞여 있으므로 문서 파일명 범위만으로 검색 책임을 정하면 안 된다.

| 양식 | 페이지 | 구성과 검색상 의미 |
| --- | ---: | --- |
| HG | 13,650 | 2,730사건 × 5역할. 각 사건의 다섯 역할은 서로 다른 PDF에 있다. 사건이 확인되면 관계 조회로 모을 수 있다. |
| IS | 3,750 | 업무 설명·규정과 구조화 기록이 섞여 있다. 표의 키만으로 답할 수 있는 요청과 설명·조건이 필요한 요청을 구분해야 한다. |
| HA | 594 | 198사건 × 3역할. HG와 다른 양식과 키 범위다. |
| 기타 | 6 | 별도 원본 검색 범위로 보존한다. |

HG가 전체 쪽의 약 75.8%라는 사실은 사건 조회가 중요한 데이터라는 근거다. 실제 사용자 질문의 75.8%가 HG일 것이라는 근거는 아니다. [집계 정의와 한계](data-audit.md)

### 완전 코드와 축약 표현은 다르게 다뤄야 한다

| 단서 | 이번 HG 스냅샷의 관측 | 처리 판단 |
| --- | --- | --- |
| 완전 예약/HG·계약/CT·승인/AP·청구/INV·수납/RCPT 코드 | 각 유형 2,730개 값. 각 값은 사건 하나에만 연결 | 정확 타입·표기·출처가 검증되면 사건 조회에 유용 |
| 완전 장비/HL 코드 | 2,821개 값, 각각 사건 하나. 91사건은 장비 코드 2개 | 한 사건에 장비 코드가 하나라는 가정도 피함 |
| 완전 증빙/EV 코드 | 7,917개 값, 각각 사건 하나. 사건당 2~3개 | 증빙→사건→요청 역할의 원본으로 연결 가능 |
| 인계철 코드 `HS-057` | 이 코드에 150사건이 연결. 전체 HS는 120종이며 코드별 50~150사건 | 출처 묶음 필터. 코드 형태라도 사건 고유키는 아님 |
| 장비 종류 `20GP` | 1,350사건이 공유 | 종류 필터. 특정 HL 장비의 동의어로 확정할 수 없음 |
| 장비 종류 `40GP` | 1,380사건이 공유 | 다른 단서와 결합하거나 집합 요청으로 처리 |

이 유일성은 현재 HG 스냅샷과 해당 코드 타입 안에서 확인한 결과다. 새 문서·새 연도·다른 업무 양식에서도 보장되는 전역 불변식으로 선언하지 않는다. 정규화 충돌과 namespace를 함께 검증해야 한다.

**코드의 모양 자체도 유일성을 보장하지 않는다.** 사용자가 예로 든 `HS-057`은 150사건의 출처 묶음이며, `20GP`는 1,350사건의 장비 종류다. 반면 위 표의 전체 HG/CT/HL/EV 값은 이번 스냅샷에서 사건을 하나로 연결했다.

예를 들어 사용자가 앞서 든 `HL-20GP-0066`을 `20GP`라고 줄여 말할 수는 있다. 하지만 검색기 입장에서는 그 축약으로 고유 번호가 빠졌다. 대화에서 이미 해당 장비가 정해졌거나 다른 단서가 사건을 구별해 주는지를 확인해야 한다. `20GP = HL-20GP-0066`을 전역 동의어로 등록하는 것으로 해결하면 다른 20GP 사건을 잘못 연결할 수 있다.

### '간접 표현'에도 강한 식별 단서가 남아 있다

HG 화물 프로필은 정확 문자열로 세면 2,730개가 모두 다르다. 그런데 **2,730개 모두 숫자 구간이 하나 있으며, 숫자를 마스킹하면 15종으로 줄어든다.** 각 종류는 182건씩 있다. 화주도 30종이 각 91건에 반복된다.

이 결과는 과거 간접 조회에서 화물명 같은 단서가 매우 강하게 작동할 수 있었음을 보여준다. 숫자의 업무 의미는 이 통계만으로 판단하지 않는다. 다만 원문 표현을 조금 바꾼 질문에서 점수가 높았다는 사실과, 식별 단서를 생략한 일상 질문을 이해했다는 사실은 구별해야 한다. 숫자를 없앴을 때 여러 사건이 남는다면 특정 사건을 자동으로 고르는 것은 검색 정확도의 향상이 아니다. [프로필 집계](data-audit.md)

## 2. 왜 실험의 결론이 흔들렸나

**업무가 다른 질문들을 한 검색 점수로 묶었고, 같은 '기준선'이라는 이름 아래 실행 경로도 달라졌다.** 이는 실험 결과를 해석하기 어렵게 만든 확인된 요인이다. 개별 검색 실패의 원인이 모두 이것이라고 단정하지 않는다.

- 개인 기본 `advanced_search`는 5:5 검색·KURE·결정론적 원문 조회를 사용한다. 최근 비교의 A에는 별도 Luna·SQLite 라우팅이 들어갔다. 이번 문서에서는 두 경로를 분리했다.
- 기존 일상 표현 40문항은 지정 근거가 모두 IS이며, 완전 ID와 장비 종류 표현이 없는 질문이다. 이 결과만으로 '코드를 현장식으로 줄여 말한 HG 사건 질문'을 검증했다고 볼 수 없다.
- 통제된 6,500문항에서 거의 전부 맞힌 결과는 원문 관계 조회가 잘 된다는 강한 근거다. 실제 질문 분포·축약·동명이칭·식별 불가능 질문에 대한 일반화를 입증하지는 않는다.
- 최근 별도 질문 24개에서는 두 HG 사건 조회가 두 설정 모두 6/6이었다. HG+IS 혼합은 1/6이었고, 실패 5개 중 4개는 규정 근거가 후보에도 없었으며 1개는 최종 선택에서 빠졌다. 계획 호출을 추가해도 이 다섯 실패는 회복되지 않았다.
- 동료 304문항 중 14개는 정답 쪽을 모두 넣어도 기존 인용 문자열 채점기를 통과하지 못했다. 이 한계를 보존한 원래 점수와 라벨 진단을 나눠 해석해야 한다.

확인한 실패는 **대상 식별·규정 검색·최종 근거 선택**의 서로 다른 단계에 있다. 다음 실험은 이 중 어떤 실패를 고치는지 명시해야 한다. [선행근거와 정확한 분모](prior-evidence.md)

## 3. 어떤 현업 패턴을 가져올 것인가

| 레퍼런스 패턴 | ADEN에서 가져올 부분 | 현재 판단 |
| --- | --- | --- |
| 정확 필드 + 분석한 본문 필드 | 코드에는 정확 일치, 업무 설명에는 어휘·의미 점수. 제목·역할·본문을 구분 | 우선 검토. Elasticsearch multi-fields/BM25F 등 공식 기능이 이 구분을 지원한다. 엔진 이전의 필요성을 뜻하지 않는다. |
| 엔터티 후보 식별 + 검증 관계 조회 | 타입별 ID, 후보 집합, 화주·화물·날짜의 교집합, 연결 근거 기록 | 기존 HG 관계·프로필 조회를 재사용하며 표현 지원과 오확정을 점검 |
| 구조화 값 + 텍스트 규정 검색 | 값·상태는 확인된 레코드, 규정·예외는 출처가 있는 텍스트에서 회수 | TableRAG·구조 인식 파싱의 원칙이 맞는다. IS도 양쪽 역할이 있다. |
| 하이브리드 검색 후 제한된 관계 순회 | 검색으로 찾은 검증 대상을 출발점으로 관계 조회 | Neo4j HybridCypher와 유사한 패턴. 현재 SQLite로도 표현 가능 |
| Microsoft GraphRAG Global/DRIFT | 전체 자료의 개방형 경향·주제 분석 | 지금의 사건·금액·근거 조회에서는 낮은 우선순위 |
| learned sparse·late interaction | 일상 업무 표현과 규정의 어휘 차이 또는 단일 벡터 표현 한계 보완 | 같은 단위·후보 예산에서 후속 비교. 정확 키 검증을 대신하지 않음 |

공식 근거는 [Elasticsearch multi-fields](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/multi-fields), [BM25F 기반 combined fields](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-combined-fields-query), [AWS Entity Resolution](https://docs.aws.amazon.com/entityresolution/latest/userguide/creating-matching-workflow-rule-based.html), [Neo4j retrievers](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html), [Microsoft GraphRAG 질의 모드](https://microsoft.github.io/graphrag/query/overview/), [TableRAG 논문](https://aclanthology.org/2025.emnlp-main.710/)에서 확인했다. 이 자료들은 지원되는 설계 사례이며 모든 기업의 채택 빈도나 ADEN의 개선율을 말해 주지는 않는다.

## 4. GraphRAG에 대한 판단

**검증된 관계를 활용하는 방향은 적합하다. Microsoft GraphRAG 전체 도입은 아직 우선할 근거가 부족하다.** HG 사건→다섯 역할 원본은 이미 결정론적 관계 조회로 해결한다. 기존 그래프 확장 비교도 새 후보를 일부 얻었지만 동료 최종 충족은 126/304에서 121/304로 내려갔다. 따라서 같은 역할 연결을 다른 이름으로 다시 만드는 것은 다음 실험의 핵심이 되기 어렵다.

추가 그래프가 필요한지는 원문에서 **기존에 없는 유효한 연결 경로**를 확인해 판단한다. 예를 들어 계약이 명시적으로 참조하는 규정·효력·예외를 거쳐야 하는 질문이 있고 그 관계를 검증할 수 있다면 평가할 가치가 있다. 같은 코드가 나온다는 사실만으로 계약 적용이나 인과관계를 만들지 않는다. 공유 장비 종류·업체를 무제한으로 연결하면 후보가 커질 수 있다. 상세한 방식별 경계는 [관계·그래프 검토](graph-and-structured-references.md)에 정리했다.

## 5. 권하는 다음 작업

다음 작업의 단위는 **고유 대상 조회, 모호한 대상 해소, 일반 규정 탐색, 대상+규정 결합**의 네 업무다. 각 업무의 입력과 성공 조건을 먼저 고정한다. 이 구분을 확인하는 첫 진단으로 최근 혼합 질문에서 **IS 규정이 후보에도 없던 네 사례**를 원문·질문·검색 입력·순위로 다시 연결한다. 올바른 업무 범위를 주었을 때 회복되는지, 올바른 요청 문구를 주어도 못 찾는지, 원문을 검색 단위로 만들 때 조건이 묻히는지를 나눠 본다. 이 네 질문만 맞히는 정규식이나 예외를 추가하지 않는다. 진단으로 확인한 실패 유형이 다른 문서·표현에서도 재현되는지 확인한다. 정답을 넣는 진단은 제품 성능 점수로 집계하지 않는다.

동시에 코드 중심 가설을 검증할 질문은 같은 대상에 대해 **완전 코드 → 허용 표기 변형 → 구별 가능한 간접 표현 → 식별 정보가 부족한 표현**을 통제해서 만든다. 어떤 단계부터 질문 자체가 여러 사건을 가리키게 되는지 명시한다. 이 검증을 통과한 범위에서 기존 조회 입구를 보완하고, 실제 의미 대응 실패가 남았을 때 검색 모델을 비교한다.

이 순서라면 다음 결과가 '몇 점 올랐다'에서 끝나지 않고, **대상을 잘못 골랐는지, 필요한 규정을 못 찾았는지, 찾고도 문맥에서 버렸는지**를 설명할 수 있다. 구체적인 통제 변수와 채점 기준은 [문제 정의와 다음 검증](methodology-and-next-tests.md)에 있다.
