# IS 업무 표 검색과 Luna 조건 조회 비교

2026-11-11. 공식 60문항과 카테고리 220문항, 총 280문항 실행 완료.

## 결론

**현재 평가 세트에서는 검색 성능이 개선되지 않았다. 280문항 모두 최종 문맥의 페이지·본문·지문이 대조군과 같았다.** 공식 전체 근거 충족은 45/58(77.6%), 카테고리의 정답 근거가 있는 문항은 173/200(86.5%)로 동일하다. 기존 기준선을 교체할 근거가 없으므로 기본 실행은 유지한다.

DB에서 찾은 문항은 5개였고 그 원본 쪽은 이미 대조군의 최종 8쪽에 있었다. 공식·일상 표현에서 새 근거를 가져온 문항은 없었다. 추가 API 호출은 280회, API 단계 지연은 p50 3.79초·p95 8.36초였다. 이번 구성은 근거 검색의 개선 없이 호출과 지연을 추가했다.

이는 TableRAG 논문 전체의 재현 결과가 아니다. 이번에는 IS 표 설명 검색과 한 번의 제한된 조회 계획을 적용했다. 논문의 반복적 질문 분해·중간 답변·범용 SQL·집계 답변은 실행하지 않았다.

## 두 조건과 실행 흐름

이번 대조군은 **KURE-v3 5:5 + 직전 개선 HG 날짜 조회**의 저장된 결과다. 프로젝트의 기본 검색 구성을 새로 바꾼 것이 아니다.

- 대조군: 동일 원질문의 BM25·KURE-v3 5:5 후보와 KURE nano 순위, 개선 HG 조회, 기존 문맥 선택기.
- 변경군: 위 결과에 IS 표 설명 검색 → Luna 조회 계획 → 검증된 SQLite 조회 → 원본 쪽 보충을 추가.

문서 후보는 최대 20쪽, 최종 원본은 최대 8쪽·8,000토큰이다. 추가 표 검색은 별도의 스키마 목록 6개를 고르며, 문서 후보 수를 늘리지 않는다. DB 쪽을 보충할 때도 기존 apply_sources와 문맥 선택기를 사용한다. 이번 실행에서는 모든 보충 쪽이 이미 최종 문맥에 있어 실제 교체가 발생하지 않았다.

Luna는 **계획 JSON을 반환**한다. Python이 조건을 검사하고 파라미터화된 SQL을 실행한다. Luna가 자유 SQL을 쓰거나 DB 값을 받아 답변하는 경로가 아니다. API에는 질문·공통 지침·관련 표의 업무 설명과 열 정의만 보냈다. 실제 셀 값·PDF 본문·평가 정답은 보내지 않았다.

### 원본과 표 색인

검증된 읽기 전용 SQLite에서 IS 파싱 완료 행 27,715개를 읽었다. 업무 책과 열 조합을 함께 사용해 190개 스키마로 나누고, 각 스키마와 원본 행·쪽·행 범위의 연결을 보존했다. 50개 업무 설명을 사용한다. 서로 다른 책의 표를 열 이름이 같다는 이유로 합치지 않았다.

표 설명 검색은 완전 코드 보존 BM25와 KURE-v3를 5:5 RRF(상수 60)로 합친다. 각각 상위 50개에서 스키마 6개를 선택한다. 임베딩은 고정 리비전 KURE-v3, CPU BF16·스레드 2, 질문 벡터는 입력·모델 지문이 같은 기존 값을 재사용했다. 표 설명 임베딩은 약 106초, 최대 75토큰으로 절단은 없었다. 다른 GPU 실험을 중단하거나 변경하지 않았다.

조건의 표·열은 허용 목록에서만 고르고, 값은 질문 원문의 구절에 있어야 한다. 예정일/실제일, 통화·단위, 0/미결을 구분한다. 숫자 또는 날짜를 셀 전체에서 확정적으로 읽을 수 있는 열만 비교 연산을 지원한다. 현재 스키마에서 숫자형 열 항목 10개, 날짜형 3개이며 복합 셀은 문자열로 보존한다. 입금/수정통지의 연결청구는 원문 청구번호가 한 행으로 연결될 때만 따라간다.

## 어디서 막혔나

280회 호출 중 278회가 구조화 응답, 2회가 시간 초과였다. 모든 문항은 low를 유지했으며 재호출하지 않았다. 구조화 응답 성공은 해석이 맞았다는 뜻이 아니다.

| 단계의 결과 | 문항 수 | 실제 처리 |
|---|---:|---|
| 일반 문서 질문 | 45 | 기존 검색 유지 |
| 대상/표 조건 미확정 | 146 | 기존 검색 유지 |
| 집계 요청 · 지원 범위 밖 | 11 | 기존 검색 유지 |
| 원문 구절·조건 검증 탈락 | 30 | SQL 실행 전 차단 |
| 검증 후 SQL 실행 | 46 | 행 조회 시도 |
| API 시간 초과 | 2 | 기존 검색 유지 |

30건의 검증 탈락은 대상 구절 불일치 5, 질문에 없는 조건 값 4, 긍정 식별 조건 누락 10, 대상 구절 중복 11건이다. 이 30건을 올바른 해석으로 집계하지 않았다.

SQL을 실행한 46문항에서는 40문항이 일치 행 없음, 1문항이 복수 행으로 보류, 5문항이 원본 행을 찾았다. 행·출처 읽기를 포함한 SQL 문장은 60개다. 성공 문항은 AS-S01-07·08·09·11·12이며 모두 기존 기준선이 이미 정답 쪽을 찾았다. AS-S01-10은 원하는 페이지가 스키마 후보의 출처 범위에 있었지만 제안한 필터로 행이 조회되지 않았다.

일치 행이 없던 40문항의 45개 조회 요청을 사후 분석했다. 모두 적어도 한 조건이 지정한 열에서 일치하지 않았다. 전체 IS 표의 같은 열까지 넓혀도 일치하지 않았다. 그런 조건 66개 중 59개는 원문 리터럴이 다른 IS 셀에도 없었고, 7개는 다른 열에만 있었다. 이는 **질문의 표현을 DB의 필터 값으로 바로 옮기는 것만으로는 조건이 성립하지 않는 경우**가 많았다는 증거다. 이 검사는 문자열 존재 진단이며 표현의 의미가 같다는 판정은 아니다. 사후 분석 결과로 검색 규칙이나 결과를 수정하지 않았다.

또한 스키마 발견에도 한계가 있었다.

| 평가 구분 | 정답 쪽 중 IS 표가 있는 쪽의 출현 수 | 상위 6개 스키마의 출처에 포함 | SQL로 가져온 정답 쪽 |
|---|---:|---:|---:|
| 공식 | 43 | 25 (58.1%) | 0 |
| 상황형 | 6 | 6 (100%) | 5 |
| 업무 규정 | 27 | 21 (77.8%) | 0 |
| 일상 표현 | 61 | 23 (37.7%) | 0 |

여기서 스키마 출처 포함은 **대리 지표**다. 해당 쪽에 표가 있다는 뜻이지 질문의 답이 그 표 행에 있다는 뜻은 아니다. 업무 규정·일상 표현의 답은 같은 쪽의 설명·조건 문단에 있을 수 있다. 독립적으로 검수한 대상·요청 정답 라벨이 없어 해석 정확도, 표 의미 선택 정확도, 오확정률을 새로 산출하지 않았다.

## 비용·지연과 제한

- GPT-6 Luna low: 280회 요청, 278회 완료, 2회 시간 초과. 호출당 10초, 동시 요청 최대 4, 자동 재시도 없음.
- 반환된 사용량: 입력 815,795토큰, 출력 82,049토큰. 출력 중 reasoning 63,958토큰이다. 시간 초과 호출의 사용량은 반환되지 않아 포함하지 않았다.
- API 단계: p50 3.79초, p95 8.36초. 실제 SQL을 실행한 46문항의 검증·조회 단계: p50 0.87ms, p95 1.42ms.
- 기존 문서 검색·리랭킹 결과와 질문 벡터를 재사용했다. 공정한 전체 검색 지연 벤치를 새로 수행한 것은 아니다. 표 설명 임베딩과 다른 GPU 실험이 동시에 진행된 환경이다.
- 독립 사람 검수나 별도 미사용 검증 세트를 추가하지 않았다. 기존 개발·회귀 문항에서의 비교다.
- 합성 검증은 정밀 숫자/통화 비교와 유일 청구 연결을 검사하지만, 이번 평가 세트가 그 기능의 실제 업무 정확도를 충분히 검증했다고 볼 수 없다.

## 판단

현재 기준선에 이 Luna 호출을 기본으로 넣지 않는다. 확인된 장점은 원본 행과 출처를 안전하게 조회할 수 있는 실행 경로를 만든 것이고, 검색 점수의 이득은 관측되지 않았다.

DB 조회의 가치를 더 보려면 표 행의 식별·조건 조회가 정답인 문항과, 규정·절차 문단이 정답인 문항을 먼저 구분해야 한다. 금액 범위·날짜 종류·미결 상태·명시적 청구 연결을 묻는 별도 표본에서는 값과 출처를 함께 채점할 수 있다. 반면 지금 낮은 일상 표현 점수에는 업무 설명·규정 문단을 찾는 문제가 포함돼 있다. 표 조건 SQL만 늘려 같은 문제를 풀 수 있다고 가정하면 안 된다.

추론 강도를 높이는 권한은 받았지만 이번 비교에서는 조건을 일정하게 유지해 모두 low로 실행했다. higher reasoning이 원문 구절/열 선택 오류를 줄이는지는 별도 비교가 필요하다. 이번 결과만으로 그 효과를 주장하지 않는다.

## 재현과 검증

실행 코드는 [advanced_schema_query.py](../../advanced_schema_query.py), [advanced_schema_benchmark.py](../../advanced_schema_benchmark.py)다. 기본 advanced_search와 운영 API는 수정하지 않았다. 아래 NEW_RUN은 기존 결과가 없는 새 경로여야 한다. plan 단계는 유료 API를 호출한다.

```bash
.venv/bin/python -B -m experimental.u_10o0o.advanced_schema_benchmark build --output NEW_RUN
.venv/bin/python -B -m experimental.u_10o0o.advanced_schema_benchmark plan --output NEW_RUN --effort low --limit 1
.venv/bin/python -B -m experimental.u_10o0o.advanced_schema_benchmark plan --output NEW_RUN --effort low
.venv/bin/python -B -m experimental.u_10o0o.advanced_schema_benchmark retrieve --output NEW_RUN
.venv/bin/python -B -m experimental.u_10o0o.advanced_schema_benchmark score --output NEW_RUN
```

동일 경로의 완료·불확실 API 요청은 다시 제출하지 않는다. score는 양쪽 280문항의 검색 결과와 입력 지문 검증이 끝난 뒤에만 참고 근거를 읽는다. API 호출은 재현 시 비결정적일 수 있으며 저장 결과 재채점은 같은 결과를 반환해야 한다.

공통 Ruff 및 개인 파일 명시 검사·서식 확인 통과. 공통 tests와 관련 실험 검사 345개, 하위 검사 15개 통과. 원본/DB/기준선 입력 지문 확인, 280개 기준선 문맥 완전 재현, 후보·문맥 예산 검사 통과. 실험 코드가 패키징에서 제외되므로 배포 패키지 빌드는 수행하지 않았다. 부대 대화의 독립 에이전트 금지에 따라 자체 리뷰를 했으며 독립 리뷰는 미실시다. 커밋·푸시는 하지 않았다.

## 참고 자료와 적용 범위

- [TableRAG 논문, EMNLP 2025](https://aclanthology.org/2025.emnlp-main.710.pdf): 텍스트/표 검색과 DB 연산의 역할을 나누고 원문 표와 저장 테이블을 연결하는 접근을 참고했다. 논문의 반복 추론·답변 생성 전체를 재현하지 않았다.
- [공개 TableRAG 코드](https://github.com/yxh-y/TableRAG): 공개 실행 코드가 제공하는 table_id 힌트를 우리 실험의 질문에 추가하지 않았다. 표 선택은 질문과 원본 유래 메타데이터로 수행했다.
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): Pydantic 기반 Responses 출력 형식을 사용했다. 형식 준수와 질문 의미의 정확성을 구분하여 로컬 검증을 추가했다.
