# 업무 표 검색과 스키마 조건 조회 실험

## 지원 범위와 비교 계약

2026-11-11. 사용자 승인 계획을 개인 Advanced 실험에 적용한다. 대조군은 직전 KURE-v3 5:5 + 개선 HG 날짜 조회의 저장된 280문항 결과다. 변경군은 같은 원질문으로 IS 업무 표 설명을 BM25·KURE-v3 5:5로 찾고 상위 스키마에서 Luna가 조회 계획을 제안한다. Python이 표·필드·조건·관계를 검증해 기존 읽기 전용 SQLite에서 조회한다. 검증된 원본 쪽을 기존 apply_sources와 문맥 선택기로 보충하며 후보 20쪽·최종 8쪽·8,000토큰은 유지한다. 원문 설명·예외는 기존 검색으로 확보한다. 문서형·모호·잘못된 계획·조회 실패는 기존 검색 결과로 돌아간다.

원본·기존 스냅샷·기본 advanced_search·운영 API·다른 작업의 모델 벤치를 수정하지 않는다. 새 스키마 목록은 원본에서 확인한 업무 책과 열 조합으로 구분하며 표기만 같다는 이유로 서로 다른 책의 행을 합치지 않는다. 기존 record_fields·source_records·원본 지문을 재사용한다. 새 그래프 서버·범용 SQL 생성·다중 LLM 반복·답변 생성·집계 답변은 범위 밖이다. 이번은 조건 조회와 원문 근거 확보만 평가한다. 집계 질문은 별도 상태로 검색에 넘기며 일부 검색 결과의 합계를 계산하지 않는다.

질문 원문에서 확인한 리터럴 필터와 검증 가능한 숫자·날짜만 사용하고 예정/실제·단위·미확정 상태를 임의 변환하지 않는다. 잘못된 열, 잘못된 날짜 종류, 제외 누락, 다중 키 충돌, 중복 관계는 보류한다. 검색 전 평가 정답·유형 라벨·정답 표를 제공하지 않는다. 모든 결과 저장 후 별도 score에서 표 선택·출처 충족과 문항별 증감을 기록한다. 대상·요청 해석의 지표는 독립 사람 라벨이 없는 경우 정확도라고 부르지 않고 구조 유효성·근거 정합성 대리 지표로 구분한다.

## 실행 승인과 자원

사용자는 이번 실행에 기존 .env 키 사용, 비용 한도 없음, GPT-6 Luna의 reasoning 필요 시 상향을 승인했다. low로 시작하며 최대 280회, 자동 재시도 없음, 답변 생성 없음으로 진행한다. 입력은 질문과 관련 표의 업무명·열 정의·허용 연산이며 표의 실제 행 값·PDF 전문·평가 근거는 보내지 않는다. 첫 실제 호출은 전체 문항 중 한 개로 포함하고 오류 원문에 인증값을 출력하지 않는다. reasoning 변경은 검증 점수를 보고 조정하지 않고 형식·실행 가능성 실패가 반복될 때만 별도 기록한다.

현재 별도 8B 임베딩 작업이 GPU를 사용하고 있어 새 표 설명 임베딩은 로컬 KURE-v3의 고정 리비전, CPU BF16·스레드 2로 수행한다. 기존 질문 벡터는 입력·모델 지문이 같은 저장본을 재사용한다. 속도는 동시 실행 환경의 추가 단계 지연으로 보고하며 공정한 전체 GPU 지연 벤치로 주장하지 않는다.

부대 대화에서 위임이 금지돼 있으므로 독립 에이전트 대신 자체 검토를 수행한다. 커밋·푸시는 하지 않는다.

## 구현·검증 경과

- 기존 읽기 전용 스냅샷에서 IS 파싱 완료 행 27,715개를 읽어 업무 책 + 열 조합 190개 스키마로 구성했다. 업무 설명은 50개로 구분된다. 표의 실제 행 값과 출처 목록은 API 입력에서 제외한다.
- 표 설명은 고정 KURE-v3, CPU BF16, 스레드 2로 임베딩했다. 같은 원질문의 기존 벡터와 코드 보존 BM25를 5:5 RRF(60)로 합쳐 상위 6개 표 설명만 제공한다.
- 숫자 셀의 통화 앞 표기(KRW/USD/EUR)를 원본에서 확인하여 처리했다. 현재 스키마에서 완전한 값으로 파싱 가능한 숫자 열은 10개, 날짜 열은 3개다. 나머지는 문자열 조건만 지원한다. 복합 셀의 숫자를 임의 분리하지 않는다. 이 수정은 첫 API 호출 전에 마쳤고 표 임베딩 입력과 순서는 동일했다.
- 합성 테스트로 질문 리터럴 검증, 표·열 허용 목록, 예정일/실제일 구분, 0과 미결 구분, 통화 불일치, 모호한 청구 연결, 읽기 전용 DB, 시간 초과 무재시도를 검사했다. 첫 실제 호출은 strict JSON 응답을 반환했지만 대상 구절이 질문의 연속 부분과 다르게 제안돼 SQL 실행 전에 차단됐다.
- 공통 Ruff 통과. 공통 tests와 새 실험·IS 조회·구조화 저장/라우팅 테스트: 345 passed, 15 subtests passed. 개인 파일은 공통 Ruff 제외 대상이므로 --no-force-exclude로 별도 검사했다. 공유 .venv를 변경하지 않고 /tmp/aden-side-test-deps에 검사 도구만 설치했다.
- 전체 280문항 계획 수집은 같은 low 설정, 호출당 10초, 동시 요청 최대 4, 재시도 0으로 실행 중이다. 평가 정답과 최종 점수는 아직 읽지 않았다.

## 실행 완료와 사후 진단

- 280회 호출 완료: 구조화 응답 278, 시간 초과 2. reasoning은 전부 low로 고정했고 재시도·답변 생성은 없었다.
- 양쪽 280문항의 검색 결과를 먼저 저장하고, 그 후 score 명령에서 참고 근거를 읽었다. 기준선 문맥 280개를 정확히 재현했고 변경군의 문맥도 모두 동일했다. 공식 45/58, 카테고리 정답 근거 보유 173/200, 일상 표현 15/40으로 개선/하락 0이다.
- 실제 SQL 실행 46문항: 일치 행 없음 40, 복수 행 1, 조회 성공 5. 성공한 원본 쪽은 모두 기존 최종 문맥에 있었다. API p50 3.79초/p95 8.36초, SQL을 실행한 문항의 검증·조회 p50 0.87ms/p95 1.42ms.
- 점수 확인 후 조건 불일치의 원인만 읽기 전용으로 분석했다. 40문항의 45개 요청 모두 적어도 한 조건이 전체 IS 표의 해당 열에도 없었다. 없는 조건 66개 중 59개는 다른 IS 셀에도 해당 리터럴이 없었고, 7개는 다른 열에만 있었다. 이 진단으로 실행 규칙·프롬프트·평가 결과를 변경하지 않았다.
- 채택 판단: 새 기본 경로로 승격하지 않는다. 표 행 조회의 별도 효용과 현재 규정·절차 검색의 부족을 구분한다. 실제 의도 정확도와 사람 검수 완료를 주장하지 않는다.
- 공유 기록은 문항 ID·집계·출처 위치·지문으로 제한했다. 원문·질문·조건값과 계획 응답은 artifacts에만 두었다.
