# Advanced TableRAG CPU 리랭커 스레드 결과

단일 요청 p95는 8스레드, 동시 4요청 p95는 8스레드가 가장 짧았다.

리랭킹 점수의 최대 절대 차이는 8.5830688e-06이었다.

세부 지연, 문항별 일치 여부, 실행 시간 및 입력 해시는 [결과 JSON](results.json)에 있다. 질문 원문·후보와 실제 페이지·표 순서는 로컬 artifacts에 남겼다.

저장소 루트에서 새 출력 경로를 지정해 재현한다. 고정 모델은 로컬 캐시, 현재 번들은 준비된 상태를 사용한다.

## ARM64 클라우드 2 vCPU 재실행

SSH로 확인한 my-cloud는 ARM64, 온라인 CPU 2개다. 제품의 배포 프로세스 대신 독립된 임시 디렉터리에서 실행했다. 시작 전 SSH 세션의 CPU 시간 제한은 없었고, 기존 작업에 CPU 우선권을 주기 위해 nice 8로 실행했다.

앞 실험의 16문항과 순서가 고정된 후보 20개를 그대로 사용했다. KURE nano 가중치와 토크나이저 파일 SHA-256을 노트북과 대조했다. FP32·SDPA·배치 4·2,048토큰, 작업자 한도 2와 공유 리랭커 잠금, 예열, 단일·동시 4요청의 제출 순서는 앞 실험과 같다. 2스레드, 1스레드 순서로 실행했다. 서버 Python 3.12.3과 ARM64용 PyTorch 2.15.0+cpu를 사용했다. Transformers 5.22.1, Sentence Transformers 6.2.0, NumPy 2.5.4, AnyIO 4.16.0은 기존 버전과 같다.

| 스레드 | 동시 요청 | 리랭킹 요청 p50 / p95 (초) | 잠금 내 리랭킹 p50 / p95 (초) | 최종 8쪽 순서 일치 | 표 순서 일치 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 54.87 / 86.73 | 54.87 / 86.73 | 16/16 | 16/16 |
| 1 | 4 | 153.87 / 248.94 | 54.38 / 79.66 | 16/16 | 16/16 |
| 2 | 1 | 45.70 / 64.28 | 45.70 / 64.28 | 16/16 | 16/16 |
| 2 | 4 | 125.13 / 202.39 | 44.56 / 63.12 | 16/16 | 16/16 |

1스레드에서 2스레드로 바꾸면 리랭킹 요청 p95는 단일 요청에서 25.9% 감소, 동시 4요청에서 18.7% 감소했다. 요청 지연에는 작업자와 리랭커 잠금 대기가 포함된다. 서버에서 잰 값은 리랭킹 구간에 한정한다.

클라우드 2스레드 단일 조건을 기준으로, 최종 페이지·표 순서, 전체 페이지 순서, 문맥 지문 중 하나라도 달라진 비교는 0/48건이었다. 노트북 2스레드 단일 조건을 기준으로는 0/64건이었다. 점수 최대 절대 차이는 클라우드 내 0, 노트북 대비 1.4185905e-05였다.

클라우드는 순위와 점수를 반환했다. 제품의 표 선택 및 8쪽·8,000토큰 조립은 그 순위를 받아 로컬에서 같은 번들로 재생했다. 실제 API, Luna, SQL, 검색, 데이터 전송, 모델 로딩은 시간에서 제외했다. 16문항을 조건당 한 번씩 측정한 부하 시험이다.

조건별·문항별 지연, 불일치 목록과 입력 지문은 [클라우드 결과 JSON](cloud-results.json)에 있다.

## ARM64 2 vCPU에서 ONNX INT8 비교

같은 my-cloud, 2스레드, KURE nano 리비전, 16문항·후보 20개, 배치 4, 입력 상한 2,048토큰을 사용했다. 대조군은 앞 절에서 저장한 PyTorch FP32 실측이다. 새 ONNX 실행과 교차 배치하지 않았다. 예열 후 단일 16회와 동시 4요청 묶음 4개를 동일한 순서로 실행했다.

원본 FP32 체크포인트에서 ONNX를 만들었다. 풀링과 슬라이딩 어텐션 마스크를 유지했고, 배치 1~4와 입력 길이 17~2,048의 다섯 검증에서 PyTorch와 ONNX FP32 출력의 최대 절대 차이는 4.29e-06였다.
그 뒤 가중치가 상수인 선형 연산을 채널별 동적 INT8로 양자화했다. MatMulInteger 90개를 확인했고 ONNX 파일 크기는 570.2 → 253.9 MiB였다. ONNX Runtime 1.31.1의 CPUExecutionProvider, 연산 스레드 2개, 연산 간 스레드 1개를 사용했다. 기존 CrossEncoder의 토큰화·정렬·배치·활성화는 유지하고 모델 forward를 ONNX로 실행했다.

별도 변환 검증으로 WSL2에서 같은 16문항을 ONNX FP32로 재생했다. 저장된 클라우드 PyTorch FP32와 후보 20개 순서가 16/16문항에서 같았고, 적용 점수의 최대 절대 차이는 1.37e-05였다. 이 검증의 시간은 성능 표에 포함하지 않았다.

| 동시 요청 | PyTorch FP32 요청 p50 / p95 (초) | ONNX INT8 요청 p50 / p95 (초) | PyTorch 잠금 내 p50 / p95 (초) | ONNX 잠금 내 p50 / p95 (초) |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 45.70 / 64.28 | 24.20 / 37.06 | 45.70 / 64.28 | 24.20 / 37.06 |
| 4 | 125.13 / 202.39 | 69.39 / 113.39 | 44.56 / 63.12 | 24.45 / 37.06 |

요청 지연에는 작업자 및 리랭커 잠금 대기를 포함한다. 모델 준비, 검색, 근거 조립, HTTP, SQL, Luna 호출은 측정에서 제외했다. 수치는 ONNX Runtime과 INT8을 함께 적용한 구성의 차이다.

| 동시 요청 | 최종 8쪽 순서 일치 | 최종 8쪽 구성 일치 | 표 순서 일치 | 표 구성 일치 | 전체 20쪽 순서 일치 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 1/16 | 8/16 | 5/16 | 11/16 | 0/16 |
| 4 | 1/16 | 8/16 | 5/16 | 11/16 | 0/16 |

ONNX INT8의 단일·동시 실행 후보 순위는 16/16문항에서 서로 같았다. 표와 최종 근거는 클라우드에서 얻은 순위를 같은 번들과 제품 코드로 로컬에서 재조립해 대조했다. 순서 또는 구성의 변화는 참고답을 사용한 정답률 평가와 구분한다.

동일 문항별 입력 지문, 지연과 불일치는 [ONNX INT8 결과 JSON](onnx-int8-results.json)에 기록했다. 실제 순위·출처 및 모델 변환 스크립트는 로컬 artifacts에 있다.

리랭킹 요청 p95는 단일에서 42.3%, 동시 4요청에서 44.0% 줄었다. 최종 8쪽을 이루는 페이지는 8문항에서 각각 1쪽씩 바뀌었다. 기존과 같은 근거 순서나 구성이 필요한 경우 이 INT8 설정을 그대로 교체할 근거는 부족하다.
