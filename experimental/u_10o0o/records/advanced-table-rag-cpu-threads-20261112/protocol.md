# Advanced TableRAG CPU 리랭커 스레드 비교

CPU 서빙에서 리랭킹 지연을 줄이기 위해, 고정된 KURE nano와 후보로 PyTorch의 CPU 연산 스레드 수만 2·4·8개로 바꾼다.

- 기존 280문항의 질문 전용 파일을 순서대로 16구간으로 나누고 구간 중앙의 문항을 사용했다. 공식 3문항, 상황형 8문항, 범위 밖 대조 2문항, 업무 규정 1문항, 일상 표현 2문항이다. 참고답과 정답 페이지는 읽지 않는다.
- 현재 제품 번들에서 CPU 질문 임베딩과 페이지·표 5:5 RRF로 문항당 서로 다른 원본 페이지에 해당하는 20개 단위를 한 번 저장했다. 320개 중 34개가 표 단위다. 비교마다 순서와 입력 본문이 같은 후보를 재사용한다.
- 리랭커는 제품의 KURE nano 고정 리비전, FP32, SDPA, 배치 4, 입력 상한 2,048토큰을 사용한다. 스레드 설정마다 새 프로세스에서 모델을 로드하고 작업자 두 개를 예열한다. 모드별 같은 16문항을 한 번씩 측정한다.
- 동시 4요청은 동시에 제출하고, 다음 네 요청은 이전 묶음이 모두 끝난 후 제출한다. 제품과 동일한 AnyIO 작업자 한도 2개와 리랭커 잠금을 둔다.
- 응답 지연은 제출부터 리랭킹 정렬이 끝날 때까지다. 실제 리랭킹 구간은 잠금 내부의 토큰 길이 계측 및 추론이며, 작업자 진입 대기 및 잠금 대기를 분리한다. 검색, 모델 로딩, 예열, 근거 포장, HTTP, SQL, Luna 호출은 시간에서 제외한다.
- 같은 페이지·표가 같은 순서로 반환되는지, 제품 문맥 조립기를 최종 8쪽·8,000토큰으로 호출했을 때 최종 원본 페이지와 문맥 지문이 같은지 비교한다. 단일 검색 후보만 입력하고, 계획 모델의 출처 승격과 SQL 결과는 넣지 않는다. 평가 지표는 정답률이 아니라 순서와 문맥의 일치 여부다.

## 실행 중 기록

4스레드 첫 시도는 예열 전 설정 비교에서 중단됐다. 비교기가 스레드 수까지 동결 설정과 같아야 한다고 검사하고 있었다. 이 항목만 해당 조건의 값으로 대조하도록 수정하고, 이미 완료된 2스레드 결과와 동결 후보를 사용해 4스레드부터 재개했다. 제품 파일은 실험에서 수정하지 않았다.
