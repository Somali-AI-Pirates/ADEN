B의 질문128토큰 절단은 1/491회, 최대 원래 질문 길이는 150토큰이다. B의 계획 호출 상태는 {'complete': 499}, SQL 상태는 {'ok': 25}다.
새 외부 호출은 총 505회(계획+답변6회)다. 답변 자동 채점은 하지 않았다. GPU 최대 PyTorch 할당은 3.09GiB다.
A는 CPU bfloat16 질문 임베딩+GPU float32 리랭커다. B는 KURE-v2 질문 임베딩·MaxSim도 GPU로 옮겼고 토큰 색인은 float16이다. 원본 토큰 색인 약1.8GB와 추가 표 색인을 상주시켜야 해 프로세스 GPU 비율을0.12에서0.65로 늘렸다. 두 모델과 MaxSim은 같은 GPU 잠금으로 보호한다. B의 속도를 동일 메모리 비용에서의 순수 모델 성능으로 표현하지 않는다.

## 이번 적용 판단

최종 필수 근거는 A 233/258(90.3%), B 232/258(89.9%)로 개선되지 않았다. 원질문1회 검색도223→221개였다. 일상 표현 최종 점수는25→26개지만 공식은50→48개였다. 현재 KURE-v3 기준선을 교체할 근거는 부족하다.
하락7건 중 DEV14·ADD14는 새 최종 후보20쪽에 필수 근거가 있었지만 최종8쪽에서 빠졌다. 나머지5건은 새 최종 후보20쪽부터 필수 근거가 부족했다. 그5건 모두 최초 검색 실패라는 뜻은 아니며 후속 질의·후보 통합도 포함한다.
128토큰 질의 절단은 SEM-37의 마지막 후속 검색150토큰에서 발생했고 이 문항은 최종 점수가 개선됐다. 리랭커1024 절단1쌍은 하락한 SEM-09의 최초 검색에서 발생했다. 절단 하나가 하락 원인인지 분리한 통제 비교는 하지 않았으므로 원인으로 확정하지 않는다.
6문항은5개가 빨라지고1개가 느려졌다. 느려진 SEM-30은 계획/검색이5회에서6회로 늘었다. 단건 속도 변화에는 GPU에서의 질의 인코딩·MaxSim, 새 LLM 계획과 API 지연이 함께 포함된다. 일상 표현 근거를 놓치는 문제는 이번 교체만으로 해결되지 않았다.

## 판단의 범위

전체 품질 대조군 A는 검증된 과거 v5 출력이며 B는 새 LLM 실행이다. 원질문 검색 비교는 LLM 계획 변동 이전의 신호이고, 최종 변화에는 모델의 후속 질의와 출처 선택도 포함된다. 이번 개발 세트를 여러 실험에 사용했으므로 독립 검증 결과가 아니다. 6개 답변의 API 완료와 실제 답변 정확도는 구분하며, 모델 기반 답변 채점이나 사람 검수는 추가하지 않았다.
기본 모델 자동 교체·운영 API 변경·커밋·푸시는 수행하지 않았다. 독립 에이전트가 금지된 부대 대화여서 자체 검토했다.
