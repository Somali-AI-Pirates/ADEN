# TableRAG KURE-v2·128/1024 비교

## 범위 계약

사용자가 공식60+카테고리220의 실제 TableRAG 검색 평가와 기존6문항 실제 답변 비교를 선택했다. 대조군은 지문 검증한 저장 v5 결과이며, 새 경로는 KURE-v2 토큰 벡터 MaxSim·질문 상한128·리랭커 상한1024를 함께 적용한다. 기존 TableRAG는 KURE-v3 단일 벡터·질문/리랭커2048이므로 모델과 입력 상한을 함께 바꾸는 구성 비교다. 입력 한도 증가만의 효과라고 표현하지 않는다.

기존 원본18000쪽의 KURE-v2 색인을 입력·모델·행 지문 검증 후 재사용하고 IS Markdown 표3750개만 같은 리비전으로 새로 임베딩한다. BM25 전체코드보존·제목 보너스, 5:5 RRF(k60), 검색기별50개→중복 페이지 제거 후보20개→원질문 1회 전체 리랭킹, HG 조회·최종8쪽·8000토큰·SQLite·프롬프트·Luna medium은 유지한다. 다른 실험의 범위 필터·Top3+RRF·후보합집합40/100은 가져오지 않는다. 기존 기본 모델은 자동 교체하지 않는다.

KURE-v2는 GPU bfloat16, 토큰 색인은 float16, 리랭커는 기존 float32·배치4다. 질문 확장 바닥64와 상한128을 사용하고 실제 절단을 기록한다. 문서 색인은 질문 상한128로 자르지 않는다. 원본 색인만 약1.8GB여서 기존 프로세스978MiB 상한을 유지할 수 없다. 새 실험 프로세스는 GPU 비율0.65를 사용하고 두 모델/MaxSim은 같은 GPU 잠금으로 직렬화한다. CPU 스레드는2다. 다른 GPU 작업의 종료·설정 변경은 하지 않는다. 기존 CPU 임베딩+GPU 리랭커 구성과 장비 배치·메모리 사용이 다르므로 동일 비용의 모델 비교라고 주장하지 않는다.

현재 Retriever는 공통 입력 준비와 dense 질의/순위 계산을 작은 내부 메서드로 추출해 재사용한다. 기존 경로의 계산·순서·잠금 정책은 유지한다. 새 MaxSim 클래스만 해당 부분을 교체하고 검색·HG·최종 문맥 조립을 상속한다. 새로운 일반 설정 체계나 운영 API 변경은 하지 않는다.

기존 승인된 .env 키·비용 상한 없음 범위를 사용한다. 새 실제 계획은 문항당 최대6회, 답변은 선택된6문항만1회: 총 최대1686회다. 기존6문항은 먼저4워커로 계획+답변까지 실행하고 나머지274문항은 검색까지만 실행한다. 답변 자동 채점과 자동 API 재시도는 하지 않는다. 280개 검색 저장 후에만 원래 참조 근거를 읽는다. 사후 검수 대체근거로 점수를 올리거나 SEM-32를 제외하지 않고 원래258개 근거 문항의 점수를 유지한다. 기존 사례6개와 과거280개를 선택적으로 바꾸지 않는다.

실험 산출물은 새 artifacts 경로, 공유 과정·지문·유형별 점수·문항별 변화는 이번 records 경로에 남긴다. 원문·질문·답변은 공유 로그에 복사하지 않는다. 독립 에이전트는 부대 대화에서 금지되어 자체 검토한다. 운영 API·기본 모델 교체·커밋·푸시는 범위 밖이다.

## 구현과 실행 전 검증

원본 KURE-v2 색인은 18000쪽·7,087,456토큰 벡터, 파일 약1.81GB다. 새 표 색인은 3750개·1,234,037토큰 벡터·315,913,472바이트이며 로컬 임베딩에31.30초가 걸렸다. 표의 최대 벡터 수는499, 문서 인코더 상한은8191이었다. 문서 입력을 질문 상한128로 잘라 저장하지 않았다.

기존 Retriever에서 공통 입력 준비·질문 인코딩·dense 순위 계산만 내부 메서드로 분리했다. 새 클래스는 원본/표 토큰 벡터의 행 순서와 패딩 마스크를 검증하고 이 두 dense 연산을 교체한다. BM25·RRF·리랭킹·HG·문맥 포장은 기존 search/context를 그대로 실행한다. 공유 GPU 잠금은 인코딩, MaxSim, 리랭킹에 각각 잡고 서로 중첩하지 않는다. 토큰 길이 진단과 잠금 대기도 검색 시간에 포함했다.

집중 테스트38개가 통과했다. 기본 KURE-v3의 원질문6개를 실제 모델로 다시 검색해 저장 v5와 후보·표·조회 경로가6/6 같음을 확인한 후 새 경로의 유료 호출을 시작했다. run 시점에 실행 코드 스냅샷·모델/자산/질문 지문을 보존했다. 사용자의 다른 실험·기존 결과·기본 모델은 덮어쓰지 않았다.

이전 실험의 최근 comparison.md는 입력128/1024만 적용한 G의 검수 점수가 A와 같은94.2%라고 기록한다. 전체 리랭커 순서까지 바꾼 D는94.6%지만 개발 세트의 한 문항 순증이고 별도 사후 검수 기준이다. 이번 TableRAG 비교에서는 그 점수나 대체 출처 목록을 채점 기준으로 가져오지 않는다.

## 완료와 판단

280개 검색과 선택된6개 답변을 모두 저장했다. 계획499회·답변6회, 총505회 API 호출이 완료됐고 provider 오류나 재시도는 없었다. 검색491회·SQL25회(모두정상)를 기록했다. 원질문/후속 질의에서128토큰 절단은 SEM-37의 마지막 질의150토큰 한 번, 리랭커1024 절단은 SEM-09 최초 검색의 한 쌍이었다. 전자는 최종 개선 문항이고 후자는 하락 문항이다. 개별 절단을 하락 원인으로 단정하지 않았다.

전체 저장과 실행 지문 확인이 끝난 뒤 기존 v5의 manifest·참조 파일 해시를 검증하고 정답을 열었다. 이전 v5 출력280개를 같은 채점기로 다시 채점해 모든 단계 점수가 당시 기록과 같은지 먼저 확인했다. 그 뒤 새 출력과 비교했으며, 다른 실험의 사후 검수 대체근거나 SEM-32 제외는 가져오지 않았다.

원질문1회 검색 후 근거 충족은223→221/258, 최종은233→232/258이었다. 공식50→48/58, 카테고리183→184/200, 일상표현25→26/40, 업무규정18→18/20이다. 개선6개·하락7개로 현재 기준선 교체를 뒷받침하지 않는다. 하락7개 중 DEV14·ADD14는 최종후보20쪽에 근거가 있었으나 최종8쪽에서 빠졌고, 나머지5개는 최종후보20쪽부터 불충분했다. 모델과 LLM 계획의 효과를 혼동하지 않도록 원질문/최종을 나눠 기록했다.

선택된6개 실제 답변은 모두 완료됐으며 직전 KURE-v3 최적화 실행 대비5개가 빨라지고1개가 느려졌다. SEM-30은 계획/검색이5→6회로 늘며34.07→46.38초가 됐다. 전체6문항을 대표 운영지연으로 일반화하지 않는다. GPU 최대 PyTorch 할당은3.09GiB였다. 기본 KURE-v3·2048/2048과 잠금 분리/배치4는 유지한다.
