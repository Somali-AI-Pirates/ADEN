# 원문 페이지 검색에 명시 코드 관계를 더한 D 실험

D를 추가해 비교했다. 이번 세트에서는 **원문 페이지 하이브리드에 명시 관계를 더하는 것만으로 기록 단위 C와 비슷한 수준에 도달했다.** 검증 70문항의 최종 전체 근거 충족은 A 57개, C 61개, D 62개다. D가 C보다 1개 높은 차이로 일반적인 우위를 단정할 수는 없지만, 검색 단위를 전부 기록으로 나눠야 한다는 근거도 확인되지 않았다.

기존 개인 기준선과 운영 API는 그대로다. 이번 fresh A/B/C만 비교 대상으로 삼았고 그 이전의 다른 실험 점수·색인·정제본은 사용하지 않았다. 관계 병합 방식은 수정하지 않았다.

## 무엇을 비교했나

| 조건 | 검색 색인 | 명시 코드 관계 |
|---|---|---|
| A | 원문 18,000쪽 | 없음 |
| B | 기록·표 행·설명 49,548개 | 없음 |
| C | B와 동일 | 원문에서 확인한 코드 → 사건 → 기록 |
| D | A와 동일 | C와 같은 관계를 원문 페이지로 연결 |

D는 A의 기존 벡터를 그대로 읽는다. 관계를 원문 페이지로 바꾸는 과정에서도 C의 기록 역할·출처 순서를 유지한다. 같은 페이지가 여러 기록에서 나오면 중복을 제거하고, 기존 하이브리드 후보에 없는 새 페이지를 최대 8개 보충한다. 최대 두 사건을 번갈아 순회한다.

하이브리드 목록과 새 관계 목록을 같은 가중치 RRF(k=60)로 합쳐 20개로 제한한다. KURE는 원질문으로 한 번만 실행하고, 최종 원문은 최대 8쪽·8,000토큰이다. BM25·벡터 각각 Top 50, Snowflake/KURE 리비전, float32, 입력 2,048토큰, 배치 4/8은 기존 fresh 실행과 같다. 질문 분해·재작성·LLM 호출·답변 생성은 없다.

## 전체 결과

새로 만들었던 개발 80·검증 80문항을 그대로 사용했다. 각 세트의 모호성·정보 부족 10문항은 근거 전체 충족의 분모에서 제외한다. 표는 독립 에이전트가 검수한 대체 출처를 모든 조건에 동일하게 적용한 결과다.

| 조건 | 개발 후보 전체 근거 | 개발 최종 전체 근거 | 검증 후보 전체 근거 | 검증 최종 전체 근거 |
|---|---:|---:|---:|---:|
| A | 60/70 · 85.7% | 57/70 · 81.4% | 60/70 · 85.7% | 57/70 · 81.4% |
| B | 54/70 · 77.1% | 53/70 · 75.7% | 57/70 · 81.4% | 55/70 · 78.6% |
| C | 63/70 · 90.0% | 60/70 · 85.7% | 64/70 · 91.4% | 61/70 · 87.1% |
| **D** | **65/70 · 92.9%** | **61/70 · 87.1%** | **66/70 · 94.3%** | **62/70 · 88.6%** |

원래 동결 근거로 채점하면 개발 최종은 A 52, B 48, C 55, D 56개다. 대체 출처 보강은 각 조건에 같은 개발 5문항을 더 인정했으며 검증 수치는 바꾸지 않았다. 원래 채점과 보강 채점 파일을 모두 보존했다. 이 5문항 증가는 검색 개선으로 세지 않는다. [두 채점 및 전체 지표](metrics.md)

## A에 관계만 추가한 효과

개발에서 최종 4문항이 개선됐고 하락은 없었다. 검증에서는 6문항이 개선되고 1문항이 하락해 순증 5문항이다. 검증 후보는 7문항 개선·1문항 하락이었다.

| 검증 유형 | A | C | D |
|---|---:|---:|---:|
| 완전 식별자 | 9/10 | 10/10 | 10/10 |
| 간접 단서 | 11/11 | 11/11 | 11/11 |
| 코드 없는 일상 절차 | 7/8 | 7/8 | 7/8 |
| 한 사건의 여러 단계 | 4/10 | 8/10 | 8/10 |
| 두 사건 비교 | 6/10 | 5/10 | 5/10 |
| 사건과 규정·예외 | 10/11 | 11/11 | 11/11 |
| 정정·상태·날짜 | 10/10 | 9/10 | 10/10 |

큰 변화는 한 사건에 속한 여러 기록을 모으는 유형이다. 반면 코드가 없는 일상 절차에서는 A→D 개선이 없었다. D는 명시된 관계를 찾아 보충하는 기능이며, 간접 표현을 새로 해석하는 기능을 추가한 것은 아니다.

## D와 C의 차이

D의 최종 충족은 개발·검증 모두 C보다 1문항 높다. 검증에서 C가 맞히고 D가 놓친 문항은 2개, D가 맞히고 C가 놓친 문항은 3개였다. C가 더 나은 개별 사례도 있으므로 기록 단위 검색이 항상 불필요하다고 말할 수는 없다.

개발의 두 사건 비교에서는 D 9/10, C 7/10이었다. DEV-109·110·113의 필수 페이지는 D의 초기 하이브리드에서 C보다 높은 순위에 있어 관계 병합 후에도 남았다. 반대로 FRESH-DEV-005는 C에서 모두 모았지만 D에서는 이미 있던 필수 페이지가 관계 병합 중 밀렸다. 데이터 구성과 병합의 상호작용이 남아 있다. [문항별 변화](changes.md), [단계별 순위 JSON](stage-diagnosis.json)

D의 검색용 벡터 배열은 18,000행·73.7MB, C는 49,548행·202.9MB다. D는 B 벡터를 만들거나 읽지 않아도 되지만, 코드 관계와 역할 순서를 확인할 기록 정보는 여전히 읽는다. 따라서 **기록 단위 벡터·BM25 색인의 필요성**을 검토한 결과이지, 관계 추출 자체를 제거해도 된다는 결과가 아니다.

같은 160문항의 리랭커 입력은 D 약 161만 토큰, C 약 118만 토큰이었다. D는 벡터 배열이 작고 C는 리랭커 입력이 짧다는 서로 다른 비용 특성이 있다. 전체 지연의 우열은 이번 실행으로 결정하지 않는다.

## 남은 문제: 관계 병합이 이미 찾은 근거를 밀어낸다

검증에서 A→D로 하락한 FRESH-VAL-005의 흐름은 다음과 같다.

1. A와 D가 공유하는 초기 하이브리드에서 필요한 AS104:001은 17위였다.
2. 이 페이지가 이미 검색 목록에 있어 현재 정책은 관계 목록에서 제외했다.
3. 새로운 관계 페이지 4개만 RRF에 넣자 해당 페이지의 병합 순위는 21위가 됐다.
4. 후보 상한이 20개라 리랭커가 보기 전에 빠졌다.

FRESH-DEV-005에서도 초기 16위의 AS108:001이 새 관계 8개와 합쳐진 뒤 24위로 밀렸다. 이 문항은 A부터 전체 근거가 부족했기 때문에 전체 충족의 하락 집계에는 잡히지 않지만, 병합이 기존 근거를 없앤 현상은 같다.

D의 검증 실패 8문항은 후보 부족 4개와 최종 선택 손실 4개다. 최종 문맥의 최대 길이는 7,203토큰이었고, 모델 입력 절단·원문 부분 절단은 모두 0건이었다. 따라서 토큰 상한 확대가 이번 두 병합 손실을 해결하지는 않는다.

다음 한 가지 변경은 **기존 검색에 있는 페이지도 관계 순위에 포함해 두 목록의 RRF 점수를 합산하고, 최종 후보에서 중복 제거**하는 방식과 현재 D를 비교하는 것이다. 이번에는 그 변경을 적용하지 않았다. 그 변경만으로 남은 후보 부족과 최종 선택 손실이 모두 해결된다고 예측하지 않는다.

## 실행과 검증 기록

- D 160행을 모두 저장한 뒤 새 경로에서 기존 ABC 480행과 합쳐 총 640행을 채점했다. 참고 근거는 검색 입력으로 전달하지 않았다.
- A/D의 질문 해시, 벡터 상위 50, 관계 보충 전 하이브리드 20 순서는 160문항 모두 같았다. BM25 상위 50은 DEV-109의 33·34위만 바뀌었고 포함 페이지 집합과 하이브리드 20에는 변화가 없었다. 두 점수는 정밀 합산 시 동점이었다. 이 차이를 숨기지 않고 [비교 입력 감사](comparison-manifest.json)와 [동점 감사](bm25-tie-audit.json)에 남겼다. 검색 코드는 이를 맞추려고 수정하지 않았다.
- C/D가 해석한 사건 목록은 160문항 모두 같았다. 차이는 사건 해석 변경에서 나온 것이 아니다. 기대 ID와의 차이에 대한 기존 같은 예약/기록 ID 주의는 [상세 지표](metrics.md)에 적었다.
- 기존 ABC의 후보·관계 메타데이터는 새 코드로 480행 모두 재현됐다. 기존 검색 결과·평가 입력·벡터 및 개인 기준선 파일의 보존 해시도 검사했다.
- D는 측정 질문 임베딩 160회·리랭킹 3,200쌍, 별도 워밍업 1회·20쌍을 실행했다. 새 문서 임베딩이나 유료 API 호출은 없었다.
- GPU 관측 50회 모두 다른 프로세스가 함께 등록돼 있었다. D-only 측정 p50 1.21초·p95 1.76초는 이번 공유 환경 관측값이며, 과거 ABC보다 느리다는 비교 결론에 쓰지 않는다. CPU 지연은 측정하지 않았다.
- 독립 코드 리뷰에서 검색·채점 결함을 발견하지 못했다. 별도 수치 감사에서 전체·유형별·문항별 집계와 FRESH-VAL-005의 병합 손실을 확인했다.
- Ruff 공통/개인 검사와 포맷, 공통·개인 pytest **316개 및 subtest 15개**, 새 CLI 도움말, sdist/wheel 빌드가 통과했다. [검증 기록](verification.json)

이 세트는 결과를 이미 관찰한 회귀 세트이며, 질문 작성·근거 검수는 독립 AI 에이전트가 수행했다. 사람 검수 완료나 미사용 검증 결과로 표현하지 않는다. D를 다음 병합 실험의 출발점으로 삼을 근거는 있지만, 이번 결과만으로 기존 기준선을 교체하지 않는다.
