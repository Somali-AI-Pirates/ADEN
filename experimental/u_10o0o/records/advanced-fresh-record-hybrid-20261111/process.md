# 실행 과정

## 시작

사용자가 이전 실험을 참조하지 말라고 명시했다. 새 폴더를 만들고 원본 PDF만 다시 읽었다. 기존 실험 결과 파일·정제본·평가 문항·색인은 열지 않았다. 기존 작업 트리에 다수의 변경이 있어 수정하지 않고 새 실험 폴더만 사용한다.

원본 120개/18,000쪽을 Poppler layout으로 새 추출했다. PDF별 SHA-256과 원문 행을 로컬 산출물에 저장했다. 임베딩 캐시는 모델 가중치만 사용한다. 임베딩·검색 결과는 새로 계산한다.

검색 단위/관계 작성, 문항 작성, 검색 구현을 분담했다. 질문 작성자는 검색 결과를 볼 수 없다. 다른 에이전트가 근거를 검수하고 검색 전에 입력 지문을 고정한다.

GPU에서 별도의 모델 실험이 실행 중임을 확인했다. 해당 프로세스는 건드리지 않고 CPU 원본 처리·구현·검수를 먼저 진행한다.

## 계산과 채점 경계

다른 작업이 GPU 메모리 대부분을 사용하고 있으므로 CPU float32 경로도 준비했다. GPU 작업의 산출물이나 결과는 읽지 않는다. 장치와 스레드, 동시 작업으로 인한 시간 측정 한계는 실제 실행 기록에 남긴다.

필수 검증 도구가 현재 가상환경에 없어서 저장소가 지정한 Ruff 0.17.4, pytest, build, httpx만 보충 설치했다. 모델·공통 제품 의존성·잠금 파일은 바꾸지 않았다.

채점기는 모든 질문의 A/B/C 결과가 저장됐는지 먼저 확인한 뒤 별도 참고 파일을 읽는다. 후보 충족은 선택한 단위에서 복원 가능한 원본 쪽, 최종 충족은 실제 8쪽·8000토큰 안에 저장된 인용을 확인한다. 동일 페이지 번호라도 책이 다르면 맞았다고 하지 않는다. 허용 대체 출처의 사실 충족과 기본 원본 쪽 Recall은 별도 지표다. 모호성 문항은 빈 정답을 모두 맞힌 것으로 처리하지 않는다.

## 원본의 분류 확인

새 추출본 전체의 페이지 머리말을 독립적으로 집계했다. HG 13,650쪽, IS 3,750쪽, 그 외 계약·비용 600쪽이었다. 한 PDF 안에서도 계열이 섞여 있었다. AS001~006에는 계약 자료와 HG가, AS007~056에는 IS와 HG가 함께 들어 있어 파일 번호만으로 분류하지 않는다. 질문 세트의 사건 분리도 PDF 파일명 대신 원문 사건 키를 기준으로 확인한다.

## CPU 사전 실행

결과·평가를 보기 전, 새 원본에서 균등 간격으로 고른 32쪽으로 Snowflake CPU float32/4스레드/배치4만 시험했다. 워밍업 후 13,800토큰을 45.142초에 임베딩했으며 절단은 없었다. 이 시험은 검색 품질 측정이 아니고 벡터도 재사용하지 않는다. 전체 색인에 수 시간 이상이 예상되어 다른 GPU 작업 보존과 계산 우선순위를 사용자에게 확인했다. 질문·원문 처리·검수·코드 구현은 계속 진행한다.

## GPU 우선 실행 승인

사용자가 기존 작업의 재개 가능 여부를 확인한 뒤 이번 실험을 먼저 실행하도록 답했다. 점검 시 기존 작업은 이미 `paused_by_user` 상태였고 프로세스가 종료되어 있었다. 저장된 59개 벡터 청크(15,104행)의 연속성과 SHA-256을 확인했다. 기존 작업의 재개 코드와 체크포인트 무결성만 확인했으며 평가 결과·정답·검색 기록은 읽지 않았다. 추가 중단 신호나 기존 파일 수정은 하지 않았다. 이번 색인과 검색은 GPU float32로 실행한다. 기존 작업의 명시적인 일시 중지 상태는 그대로 보존한다.

## 표 배치 표본 확인

Poppler로 IS 표와 HG 사건 표를 이미지로 렌더링해 열·여러 줄 셀·각주 위치를 확인했다. IS 표에서는 최초 접수일이 상태 확인 시각과 다르며, 같은 대상의 상태 전후 관계를 원문이 명시하지 않는다는 각주를 확인했다. 따라서 동일 코드의 여러 출현을 연결해도 최신·유효 상태나 정정 방향을 추론하지 않는다. 이 표본 시각 검사는 전체 표의 사람 검수를 대신하지 않는다.

## 구현 검토와 표본 검수

검색 결과를 보기 전 코드 검토에서 BM25의 문서 토큰 중복 제거가 빈도를 없애는 문제, 한국어 조사가 붙은 완전 코드 경계, 매 요청마다 색인 정규화/관계 정규식을 다시 준비하는 문제를 발견했다. 이를 고쳐 표준 BM25 빈도를 보존하고, 준비 비용을 검색 시간과 분리한다. C의 단위 순서는 관계 유형이 아닌 업무 기록 종류와 출처 순서로 고정한다.

A 임베딩 초기에 체크포인트 목록이 최신 배치만 저장되는 구현 결함을 발견해 이 작업의 프로세스만 중단했다. 새 검색/채점은 수행하지 않았다. 연속 3배치 및 실패 후 재개 검사를 추가한 뒤 다시 실행한다. 파일 해시도 저장·확인한다.

B 초안은 49,026개 단위(원래 하나의 기록인 페이지 14,250개, 표 행 26,260개, 설명 8,273개, 원문 대체 243개)였다. 전체 18,000쪽의 비어 있지 않은 줄은 각 단위의 원문 행 범위에 모두 연결됨을 검사했다. IS 표본의 대상/날짜/상태가 시각적으로 확인한 표와 일치했다. 원문 대체 단위는 A와 같은 텍스트로 유지한다.

첫 16문항의 독립 검수에서는 인용의 충분성과 개발/검증 표현 중복에 관한 수정 요구가 나왔다. 검색 결과 없이 수정하고, 전체 세트의 검수를 마친 뒤 입력을 고정한다.

## 재개 및 독립 검토

3배치 중간 실패 후 이어서 실행하는 검사에서 완료된 배치가 모두 유지되고 남은 배치만 계산됨을 확인했다. 수정된 코드로 A를 재개했다. 버그가 있던 첫 실행 로그도 삭제하지 않고 보존했다.

원문 연결/관계/채점을 구현하지 않은 독립 검토자에게 새 코드와 새 원본만 제공했다. 질문·정답 파일은 제공하지 않아 검색 구현을 평가 문항에 맞추지 않도록 했다. 별도의 근거 검수자는 검색 코드·검색 결과를 보지 않는다.

## 독립 검토에서 발견한 행 경계 수정

검색 결과를 보기 전 독립 검토에서, 반복 코드 계열로 시작하는 설명 문장을 표 행으로 잘못 인식하는 경우를 발견했다. 487개 일반 코드 표 페이지에서 16곳의 코드 시작 설명 후보를 확인했다. 이 때문에 실제 예약으로 연결되는 기록 코드가 별도의 자기 사건으로도 등록되어 관계 조회가 불필요하게 모호해질 수 있었다.

일반 표 행은 첫 코드 뒤의 실제 두 칸 이상 간격과 세 개 이상의 열 형태가 있을 때만 인정하도록 범위를 좁혔다. 설명 문장은 기존 설명 단위로 보존한다. 수정 전 산출물은 로컬 `units-before-row-fix`에 남겼다. 수정 뒤 새 산출물을 재생성했고 18,000쪽 전체 줄 보존을 포함한 8개 검사를 통과했다. 아직 B 색인이나 질문별 검색은 실행하지 않았으므로 점수를 보고 규칙을 바꾼 수정이 아니다.

## 현재 색인 구성 확정

행 경계 수정을 적용하자 잘못된 코드 계열이 표의 주 열과 경쟁하던 62쪽도 해소돼, 최종 B는 49,548개 단위가 됐다. HG 13,650개, 초기 계약 600개는 기존 원문 페이지와 같은 하나의 기록이다. IS는 3,569쪽에서 표 행 26,746개와 설명 8,371개를 만들었고, 181쪽은 원문 페이지로 남겼다. 관계는 10,513개 사건/기록 앵커, 54,171개 코드, 출처가 있는 109,321개 연결이다. 수정 뒤 독립 검토자가 새로 구조화된 62쪽의 행 형태와 표본 머리말을 확인했다.

A 18,000행의 float32 벡터 생성이 완료되어 유한값·단위 길이·차원·전체 파일 해시를 확인했다. 이번 실행 안에서 A와 텍스트가 완전히 같은 B 단위만 벡터를 공유하며 새 기록은 다시 계산한다. A 생성 시간을 보존하려고 B 실행 전 최초 완료 매니페스트를 별도로 저장했다.

문항 작성 지연 때문에 개발과 검증의 작성자를 분리했다. 원문 HG 사건 번호의 짝수/홀수, 비-HG 자료의 범위와 실제 사건 키를 구분하며 교차 중복을 검수한다. 단순 인용 존재뿐 아니라 질문의 요청과 인용의 의미를 검토하고, 반복 규정의 허용 대체 출처도 같은 범위 안에서 확인한다.

## 실행·채점 독립 검토 후 보강

두 번째 독립 검토는 모델·검색·저장·재개 경계를 봤다. 현재 A/B 산출물에서 손상을 발견하지는 않았지만, 완료되지 않은 색인의 완료 배치를 별도 해시 없이 재사용할 수 있는 결함을 지적했다. 새 체크포인트는 배치별 SHA를 저장하고 재개 전에 검사한다. 완료 색인도 SHA가 없으면 읽기와 재개 모두 거절한다.

채점은 새 단위 파일을 함께 받아 후보 단위→후보 출처, 후보→리랭킹 순열, 최종 출처의 도달 가능성과 순서를 검증한다. 그 뒤 실제 원문 접두부·실제 토큰 수를 확인한다. 저장된 문항 해시가 고정 질문과 일치하는지도 참고 파일을 읽기 전에 검사한다. 정상 벡터처럼 보이는 다른 벡터로 바꾼 체크포인트와, 후보 밖의 유효한 원문 페이지를 끼운 결과가 거부되는 검사를 추가했다.

두 색인의 수치 계산 조건은 그대로 유지했다. 진행 중인 색인의 검증·메타데이터 코드를 보강한 변경이며, 임베딩 모델·리비전·입력·배치·정밀도를 바꾸거나 검색 점수를 보고 조건을 조정한 것은 아니다. 최종 질의 실행 전 실행 코드 지문을 다시 고정한다.

## 검색 실행 전 최종 검사

- 공통 Ruff와 개인 실험 Ruff/format 통과. 공통 tests와 개인 실험 tests를 함께 실행해 310 passed, 15 subtests passed. sdist와 wheel 빌드 통과.
- 두 독립 리뷰에서 원문 행 경계와 후보→원문 연결, 부분 벡터 체크포인트 무결성을 점검하고 지적을 수정·재검토했다.
- `code-freeze.json`에 검색 결과를 보기 전 코드 SHA를 고정했다. 문항 작성 및 독립 근거 검수는 진행 중이며 아직 평가 검색/채점은 하지 않았다.

## 질문을 나눠 실행하고 전체 저장 후 채점

- 사용자가 다른 GPU 작업을 중단하고 이번 작업을 이어가도록 알려왔다. 개발80개의 질문 ID/문장 파일을 먼저 SHA로 고정하고 `run-dev-v1` 검색을 시작했다. 검증80은 독립 작성·검수를 마친 뒤 별도 실행한다.
- 코드·모델·선택 규칙은 두 실행 모두 동일하다. 개발 검색 결과의 품질이나 순위는 열지 않고, 검증 질문 작성자·검수자에게도 전달하지 않는다. 모든480개 결과를 저장한 다음 한 번에 채점한다.
- 개발 골드의 인용을 개별 사실로 나누는 마지막 수정은 검색 결과와 무관한 원문 검수로 처리했다. 고정된 개발 질문 문장은 바꾸지 않았다.
- 실행 시작 시 별도 `table_rag` GPU 프로세스가 남아 있었다. GPU 사용 프로세스와 메모리를 5초마다 기록한다. 지연 수치는 관측된 실행 환경을 함께 밝히며 단독 점유 측정으로 표현하지 않는다. 다른 작업에 중단 신호를 보내지는 않았다.

## 최종 문항 분류와 대체 출처 검수

- 검색 점수를 열기 전에 독립 검수에서 VAL-043은 사건과 규정·예외, VAL-075는 간접 단서의 사건 조회로 분류를 정정했다. 검증은 실제 유형별11/8/11(2/3/6번), 나머지10개로 집계한다. 질문과 정답 사실은 유지했다.
- 같은 적용 범위의 일반 규칙은 새 원문 전체의 정확 문구를 대조해 안전한 대체 출처를 추가했다. 같은 금액이라도 다른 사건이면 대체 출처로 인정하지 않았다. 의미가 같은 표현의 전수 목록은 아니다.
- 예산은 모든 대체 출처를 동시에 담는 것으로 계산하지 않고, 사실마다 허용 출처 하나씩으로 구성할 수 있는 기본 근거 묶음을 검사한다.

## 전체 검색 완료 및 첫 채점

- 질문을 개발80, 검증56, 검증24로 나눠 실행했다. 각 묶음은 질문 ID/문장 해시를 실행 전에 고정했다. 이전136문항과 최종160문항에서 질문 내용 변화가 없음을 확인했다.
- 총480개 결과를 모두 저장한 뒤 합쳤다. 세 실행의 모델·코드·색인·검색/복원 조건 지문 일치를 검사하고 처음 채점했다. 검색 중 정답은 읽지 않았고, 작성·검수자에게 순위와 점수를 전달하지 않았다.
- 독립 원문 검수가 일반 규칙의 추가25쪽을 찾았을 때는 기존 동결골드를 보존하고 별도 보강골드로만 민감도를 채점했다. 이 추가에 따른 후보/최종 전체 근거 충족 및 사실 적중 수 변화는0이었다. 일부 MRR/nDCG만 달라져 별도 기록한다.
- 실행 검증: 후보단위→원문 연결, 최종원문 접두부/토큰수, 질문해시, A/B/C누락·중복 없음 확인. GPU 계산은 모두 종료했다.
