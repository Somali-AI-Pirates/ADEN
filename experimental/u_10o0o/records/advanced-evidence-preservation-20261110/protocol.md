# 요청별 근거 보존 후속 실험 — 실행 전 범위

2026-11-10. 활성 목표는 근본 원인을 따라 실험을 이어가고, 개선 신호가 있으면 검증 범위를 넓혀 결과와 과정을 남기는 것이다. 이전 작업은 진행으로 분류한다: 같은 대상 144문항과 혼합 6문항 진단이 검색 성공·식별 상태·후보 합성·문맥 배치의 차이를 실제 순위로 확인했다.

## 근거와 가설

직전 진단에서 규정 요청을 분리하면 벡터가 찾는 근거가 달라졌다. 그러나 두 검색기 상위 20쪽의 합집합에서 RRF 상위 20쪽만 먼저 남기면 규정 근거가 KURE 전에 없어졌고, HG 원본 5쪽의 선두 추가는 이미 찾은 규정을 9위로 밀어냈다.

새 모델·가중치 조합 대신 다음 두 단계만 비교한다.

1. 같은 검색 결과를 리랭커에게 보여 주기 전 줄이는 위치: RRF 20쪽과 합집합 최대 40쪽.
2. 이미 확보한 후보의 최종 선택: 기존 원문 조회·배치와 요청별 근거를 우선 남기는 선택.

## 지원 경계

- 개인 advanced_search의 현재 5:5 기본 실행, 운영 API, 문서·벡터·기존 결과를 유지한다. 새 개인 실험 실행기만 추가한다.
- 검색기·모델 리비전·5:5 가중치·RRF 상수 60은 고정한다. 각 검색기는 여전히 상위 20쪽을 반환한다.
- 후보 보존 실험은 합집합 최대 40쪽을 KURE에 입력한다. 기존 후보 20쪽과 계산량이 같다고 주장하지 않는다. 문항당 검색 횟수·KURE 쌍 수·로컬 지연을 분리해 기록한다.
- 요청별 결과를 합친 후보는 최대 20쪽, 최종 문맥은 최대 8쪽·8,000토큰이다. 같은 후보에서 선택 방식만 바꾸는 쌍을 만들어 배치 효과를 분리한다.
- 원본 요청의 대상·역할 연결은 기존 검증된 계획 스키마와 사건 조회를 재사용한다. 검색 또는 조립에 정답 페이지·인용·문항 ID별 예외를 넣지 않는다.
- 우선 독립적인 사건/규정/일반 요청을 지원한다. 이전 요청의 값이 필요한 종속 작업, 조건부 사건 집합, 유효하지 않은 계획은 기존 기준선으로 돌아가며 별도 표시한다. 지원하지 않는 경우를 성공 표본에서 빼 숨기지 않는다.
- 새 API 호출은 우선 0회다. 이전 질문만으로 만든 계획을 재사용하고, 새 질문에서 필요한 계획 호출 비용을 캐시 실행 시간과 구분한다. 이전 Luna+SQLite baseline과 현재 개인 기본 baseline을 같은 경로로 취급하지 않는다.

## 단계와 채택 판단

1. 혼합 6문항에서 원문 규정 절을 쓰는 진단으로 후보·선택을 분리한다. 이 수동으로 확인한 절 분리는 실행 가능한 자동 계획기의 성능으로 주장하지 않는다.
2. 개선 신호가 있으면 보관 자동 계획을 그대로 사용한 기존 24문항, 동료 304문항·일상 표현 40문항으로 확장한다. 같은 대상 144문항은 단일 사건·모호성 회귀 대조로 유지한다.
3. 최종 평균만 보지 않고 후보 전체 근거, 최종 전체 근거, 문항별 개선·하락 및 각 요청에 남은 출처를 본다. 계획 인식 오류와 검색·선택 손실을 구분한다.
4. 더 넓은 문항에서 개선이 재현되면 별도 미사용 질문으로 한 번 확인한다. 결과가 막히면 실패 위치를 기록하고, 확인되지 않은 개선을 채택하지 않는다.

입력·계획·코드·모델 지문과 순위·문맥을 저장한 뒤 정답을 읽는다. 기록은 experimental/u_10o0o/records/advanced-evidence-preservation-20261110에, 원문을 포함한 입력·결과는 artifacts의 별도 경로에 보관한다. 기본 실행의 채택 변경은 이번 목표에 자동으로 포함하지 않는다.

## 고정 비교군

| 이름 | 요청별 후보 구성 | 최종 선택 |
| --- | --- | --- |
| baseline | 개인 기본 실행의 원 질문 검색 | 기존 원문 조회·선택 |
| requests20 | 같은 요청 계획, 검증된 HG 역할 원문 또는 RRF20 → KURE | 합친 20쪽을 원 질문으로 다시 평가한 뒤 기존 원문 조회·선택 |
| requests20_pack | requests20과 같은 후보·조회 후 후보 | 요청별 KURE 순위와 검증 HG 역할을 교대로 배치 |
| requests40 | 요청 계획은 동일, 각 검색기 Top20의 합집합≤40 → KURE | requests20과 같은 기존 선택 |
| requests40_pack | requests40과 같은 후보·조회 후 후보 | requests20_pack과 같은 요청별 배치 |

후보 확장에서는 KURE 상위 3쪽 뒤를 **기존 RRF20 순서**로 채운다. 요청별 후보와 원 질문 후보를 합친 목록은 20쪽으로 제한한다. 새 선택기는 이 20쪽의 조회 후 후보에 없는 페이지를 넣을 수 없다. 유효한 요청 그룹이 2개 미만이면 기존 문맥을 그대로 쓴다.

같은 질문·페이지의 KURE 점수는 비교군 사이에서 공유해, 공통 후보의 재추론 편차를 후보 효과로 오인하지 않도록 한다. 실행 시간은 공유 계산을 사용한 로컬 진단 시간이다. 이를 독립적인 사용자 요청의 전체 지연이라고 보고하지 않는다. 모델 쌍 수는 실제 공유 실행량과 비교군을 독립 실행할 때 필요한 고유 쌍 수를 함께 기록한다.

## 실행 이력

- pilot-01: 검색 6문항×5조건의 순위와 문맥은 저장했으나, 마지막 채점에서 이전 혼합 진단 파일의 메타데이터형 근거 그룹을 일반 평가 형식으로 오인해 중단됐다. 검색 입력·정답·설정은 바꾸지 않고, 채점 어댑터만 HG/IS 요청별 primary 인용으로 명시해 수정한다. 실패한 폴더는 보존하고 pilot-02에서 재실행한다. pilot-01은 완료 결과로 사용하지 않는다.

- pilot-02: 완료. 기준선의 최종 문맥 지문 6/6이 직전 진단과 같았다. 전체 HG+IS 근거 충족은 baseline 1/6, requests20 2/6, requests20_pack 3/6, requests40 3/6, requests40_pack 4/6이다. 후보/선택 두 축에 개선 신호가 있지만 조건 사이의 개별 하락도 남아 있어 이 결과로 채택하지 않는다.
- pilot-02의 summary 페이지 Recall 필드는 합산값이다. 후속 실행에서는 같은 문항별 Recall을 문항 수로 나눈 평균으로 저장하도록 출력 집계만 수정했다. 요청·후보·선택 알고리즘은 그대로 고정한다.
- 보관 자동 계획은 broad 344건 중 225건이 현재 독립 요청 지원 범위에 있고, 종속·조건부 작업 100건과 원문 anchor 오류 19건은 기존 기준선으로 복귀한다. 전체 344개와 상태별 분모를 모두 기록한다. 이는 아직 새 계획기나 전체 종속 요청 경로의 검증이 아니다.

## 새 질문 검증의 사전 고정 (2026-11-10, 정답 열람 전)

확대 비교에서 requests40은 동료 304문항의 최종 전체 근거 145건, 일상 표현 40문항 19건으로 네 실험 조건 중 가장 높았다. 요청별 교대 배치는 각각 142건·19건으로 추가 이득을 보이지 않았다. 따라서 새 질문에서는 baseline과 requests40 두 개만 비교한다. 기존 순위·선택기와 모델은 바꾸지 않는다.

독립 작성자가 새 혼합 12개·두 사건 6개·규정 6개를 만들고, 다른 검수자가 원본과 기대 근거를 확인한다. 부모 실행자는 검색 저장 전 정답 내용을 읽지 않는다. 이미 증강에서 사용한 문서 집합이므로 미사용 문서 일반화라고 부르지 않는다. 새 질문·조합의 재현성 확인이다.

고정된 기존 질문 계획 프롬프트와 스키마로 GPT-6 Luna low를 질문당 한 번만 호출한다. 기존 키 재사용·예산 무제한 승인을 적용하며, 질문과 고정 지침 외 PDF·정답·검색 결과는 보내지 않는다. 답변 생성은 하지 않는다. 기존 request_plan의 25초·재시도 0회 설정을 명시해 실행한다.

새 실행기는 두 arm의 검색 및 KURE 계산 캐시를 공유하지 않고, 질문별 실행 순서를 번갈아 바꾼다. 준비·워밍업 시간을 분리한다. 기준선 로컬 검색 시간, 계획 호출 시간, 새 경로 로컬 검색 시간을 따로 저장하고, 동일 문항의 계획+검색 합계 p50·p95를 산출한다. 새 표본에서 점수가 떨어져도 그 결과를 이유로 질문·정답·설정은 수정하지 않는다.

새 질문의 live 측정은 계획 API를 먼저 병렬 수집하지 않고, 각 질문의 requests40 실행에서 계획1회 직후 검색을 이어서 수행한다. wall_ms는 이 실제 직렬 구간이다. 캐시 계획을 쓰는 재현에서는 wall_ms가 로컬 실행만 나타나며, 과거 계획 시간을 더한 serial_total_ms와 구분한다.
