# TableRAG 최적화 적용 후 실제 응답 6문항

CPU/GPU 잠금 분리와 GPU 리랭킹 배치 4를 개인 TableRAG의 cpu_gpu_rerank 경로에 적용했다. CPU 전용/shared_cuda의 기존 전체 잠금과 모델·프롬프트·추론 강도·검색/문맥 예산은 유지했다.

## 표본과 전체 시간의 정의

기존 v5의 성공 응답 280개 중 가장 빠른 2개·중앙값과 가까운 2개·가장 느린 2개를 새 실행 전에 고정했다. 과거 및 이번 비교 시간은 `retrieval_seconds + answers.table_rag.telemetry.seconds`다. 검색 단계에는 최초 검색, 계획 API, 후속 검색·SQL·문맥 조립과 모델 잠금 대기가 들어간다. 최종 답변 생성은 뒤에 더한다. 이전 실험의 seconds 필드는 다른 비교군 답변 생성까지 포함하므로 사용하지 않는다.

기존 280문항의 전체 p50/p95는 12.31/33.53초다. 단계별 p50끼리 더한 값이 아니라 문항마다 전체 시간을 합친 뒤 백분위수를 계산했다.

GPT-6 Luna medium으로 계획과 답변을 새로 생성했다. 저장된 계획이나 답변 캐시는 사용하지 않았다. 모델·색인을 미리 준비하고 원질문 6개로 로컬 검색을 워밍업했다. 워커는 이전과 같은 4개지만 전체 부하는 6문항이다. 모델 적재와 워커 진입 전 큐 대기는 포함하지 않는다.

## 판단

느린 두 문항의 로컬 검색 합계는 AS-SEM-32가 20.20→6.02초, AS-SEM-30이 25.47→5.96초로 줄었다. 계획과 검색도 각 6회에서 5회로 줄었으므로 감소분 전부를 잠금·배치 변경의 효과로 해석하지 않는다.
AS-DEV20은 같은 최종 문맥에서 로컬 검색이 4.21→1.08초로 줄었지만 계획 API가 3.88→7.85초로 늘어 전체는 12.37→12.47초였다. AS-S01-19는 계획·검색이 1회에서 2회로 늘고 SQL 조회도 추가됐다. 실행마다 API 시간과 계획 경로가 달라져 빠른 문항도 더 느려질 수 있다.
실제 기본 Retriever의 사전 원질문 검색은 6/6 모두 v5와 같았다. 이후 모델이 고른 하위 질문·최종 출처가 달라져 최종 문맥 해시는 1/6만 같았다. 참고 근거로 채점 가능한 5문항은 기존/신규 모두 3개 충족·2개 미충족이었다. AS-DEV12는 기존 평가 정의상 근거 채점 대상이 아니므로 N/A로 유지했다. 새 답변의 의미 정확도까지 같다고 주장하지 않는다.
현재 구성은 로컬 검색의 동시 처리 개선으로 적용했다. 전체 응답을 더 줄이는 문제는 LLM 계획 호출 지연과 반복 검색 횟수에 남아 있다. 이번 6건으로 새 전체 p50/p95나 운영 SLA를 제시하지 않는다.

## 해석 범위

이 6문항은 작은 동작·지연 확인이다. 과거 극단값을 고른 재측정이며 새 계획의 호출 횟수와 API 지연, 280문항/6문항 부하 차이가 함께 변한다. 시간이 줄어든 전부를 잠금·배치 변경의 효과로 돌리거나 이 표본으로 운영 p95를 계산하지 않는다. 동일 계획에서의 로컬 실행 효과는 앞선 280문항 동일성 검사와 15문항 반복 측정을 근거로 삼는다.

필수 근거 점수는 원본 페이지 기준의 기존 공식/카테고리 채점기를 그대로 사용했다. 생성 답변의 의미 정확도는 새 LLM 채점을 하지 않았다. 답변 호출 완료, 출처 형식 검사와 실제 답변 내용의 정확성은 구분한다.

실제 호출 22회, 답변 완료 6/6. 자동 재시도·추가 채점 호출은 없었다. 최종 문맥 해시가 과거와 같은 문항은 1/6이다. 세부 출처와 원문 질문/답변은 로컬 산출물에 보존했다.
