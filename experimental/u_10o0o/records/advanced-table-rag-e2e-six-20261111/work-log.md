# TableRAG 최적화 적용과 실제 응답 6문항 확인

## 범위 계약

사용자는 앞서 검증한 CPU/GPU 잠금 분리·리랭킹 배치 4 적용과 빠른 2개·중앙 2개·느린 2개의 실제 전체 응답 확인을 요청했다. 개인 table_rag의 cpu_gpu_rerank 경로에만 검증한 병렬 실행을 적용한다. CPU 전용·shared_cuda의 기존 전체 잠금, API 계약·검색 모델·정밀도·HG·후보20·최종8쪽·8,000토큰·프롬프트·추론 강도를 유지한다. 새 설정 계층이나 자동 OOM 대체는 추가하지 않는다. 기존 v5와 속도 실험 산출물은 수정하지 않는다. advanced_search와 운영 API는 범위 밖이다.

기존 v5에서 성공한 280개 응답을 retrieval_seconds + answers.table_rag.telemetry.seconds로 정렬했다. 가장 빠른 2개, 중앙값과 가까운 2개, 가장 느린 2개를 ID 동점 규칙으로 선택하고 새 실행 전에 artifacts/.../selection.json에 고정했다. 전체 실험의 seconds 필드는 다른 비교군 답변 생성 등도 포함하므로 사용자 응답시간으로 사용하지 않는다. 과거 전체 응답 p50/p95 12.31/33.53초는 각 문항의 검색+해당 답변 시간을 합친 뒤 백분위수를 계산한 값이다.

이번에는 저장된 계획을 재생하지 않고 실제 TableAgent와 답변 생성을 호출한다. 기존 사용자가 승인한 .env 키·비용 상한 없음 범위를 이어 사용하며, 같은 GPT-6 Luna medium·기존 프롬프트를 유지한다. 최대 계획 6회+답변1회씩, 총 최대42회다. 별도 LLM 채점·이전 비교군 답변 생성·자동 재시도는 하지 않는다. 질문과 근거는 기존 승인된 모델 호출 경로로만 전송한다. 원문·질문·답변은 로컬 artifacts에 보관하고 공유 기록에는 ID·수치·출처 식별자만 남긴다.

기존과 같이 워커 4개를 쓰지만 280문항 연속 부하와 6문항 부하는 다르다. API와 계획의 변동도 있으므로 이 6건의 시간 차이를 최적화만의 인과 효과나 새 전체 p95로 주장하지 않는다. 최종 문맥·계획 및 검색 호출 수도 함께 비교한다. 모델과 색인을 준비한 뒤 타이머를 시작하며 워커 진입 전 큐 대기는 제외한다.

적용 뒤 검증은 실제 Retriever에서 CPU/GPU 겹침과 같은 모델의 동시 실행 방지, 기존 저장 검색과의 동일성 확인, Ruff·전체 pytest·CLI 확인이다. 독립 에이전트는 금지된 부대 대화여서 자체 검토한다. 이전 속도 실험 기록은 당시 미적용 상태의 역사 기록으로 보존하고, 현재 상태는 TableRAG README와 이번 기록에서 안내한다.

## 적용과 자체 검토

기존 Retriever.search의 CUDA 경로에서만 전체 잠금을 풀고 임베딩·리랭커 각각의 잠금을 사용했다. calls 증가도 임베딩 잠금 안에서 수행한다. GPU 리랭커 배치는 4로 변경했다. CPU 전용과 shared_cuda는 기존 전체 잠금 안에서 실행하므로 모델 간 CPU 동시 실행을 새로 허용하지 않는다. benchmark/workflow의 새 protocol에는 잠금 범위와 배치를 명시한다. 과거 실행의 프로토콜은 그대로 보존한다.

기존 계측 클래스에서만 검사하던 CPU/GPU 겹침 테스트를 실제 기본 Retriever에도 적용했다. 각 공유 모델에 12개 요청을 동시에 넣어 encode와 predict가 각각 하나씩만 실행되는지, CPU 모드에서는 모델 간 겹침도 없는지 확인했다. 집중 테스트 11개가 통과했다.

자체 검토에서는 (1) 잠금 순서·공유 카운터·모델별 직렬화, (2) 기존 입력 지문·새 실행 경로·유료 호출 재시도 금지·키 미노출을 확인했다. 독립 리뷰는 부대 대화의 에이전트 금지로 수행하지 않았다. 공통 Ruff와 변경 파일의 명시적 Ruff가 통과했고, 전체 pytest는 517 passed, 15 subtests passed였다. 모델/패키지 의존성이나 배포 패키징은 변경하지 않았다.

## 실제 6문항 실행 완료

실제 기본 Retriever의 사전 원질문 검색은 6/6 모두 저장 v5의 후보·표·조회 경로와 일치했다. 새 질문 계획과 답변을 실행해 6/6 응답을 저장했고 총 API 호출은 22회였다. API 실패·자동 재시도·별도 모델 채점은 없었다. 모델 프롬프트와 추론 강도는 그대로였지만 하위 질문·계획 종료·최종 출처 선택은 새 모델 응답이므로 바뀔 수 있다. 최종 문맥 해시는 과거와 1/6 일치했다.

전체 응답은 빠른 구간 4.77→9.46초, 4.97→14.02초, 중앙 구간 12.25→15.20초, 12.37→12.47초, 느린 구간 59.55→42.35초, 60.34→34.07초였다. 표본을 새 측정값에 따라 교체하거나 추가 실행하지 않았다. 느린 구간의 계획/검색은 각 6회에서 5회로 줄었다. 실제 벽시계 시간도 separately 기록했고, 비교표는 이전과 같은 검색+답변 합산 정의를 사용했다.

모든 결과 저장 후에만 참조 근거를 읽었다. 초기 후처리는 예전 baseline의 runtime 지문이 현재 app/evaluation/metrics.py와 다르다는 이유로 중단됐다. 차이는 삼항식을 if/else로 펼친 기존 다른 작성자의 변경이었으며 이를 수정하거나 과거 지문을 덮어쓰지 않았다. 후처리에 필요한 기존 manifest가 v5 프로토콜의 해시와 같은지, 모든 참조 파일이 v5 score-manifest의 해시와 같은지 검증했다. 새 채점기로 기존 6개 출력의 단계별 점수가 당시 저장된 per-question 결과와 정확히 같다는 것도 검사한 뒤 새 출력과 비교했다. 검색/모델 실행을 재시도하지 않았다.

AS-DEV12는 참고 근거 정의상 일반 근거 충족 채점이 N/A라 그대로 남겼다. 나머지 5문항은 기존/새 실행 모두 충족 3개·미충족 2개였다. 답변 API 성공과 인용 ID 검사는 통과했지만 답변 의미의 정확도는 추가 모델 채점하지 않았다.

## 재현과 기록

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 MKL_NUM_THREADS=2 TOKENIZERS_PARALLELISM=false \
  .venv/bin/python -B -u -m experimental.u_10o0o.records.advanced-table-rag-e2e-six-20261111.run_sample
.venv/bin/python -B -m experimental.u_10o0o.records.advanced-table-rag-e2e-six-20261111.analyze
```

run_sample은 이번에 고정한 selection과 출력 경로 전용이다. 이미 시작한 protocol이 있으면 재호출을 거절한다. 완료한 v1에 실행하지 않는다. analyze는 저장된 응답과 검증한 참조 근거만 읽으며 모델을 호출하지 않는다. raw 질문·근거·답변·단계 체크포인트와 실행 코드 스냅샷은 artifacts/u_10o0o/advanced-table-rag-e2e-six-20261111/v1에 남겼다. 공유 기록에는 문항 ID·수치·출처 ID·지문만 저장했다.

적용 이후 CLI --help를 확인했고 Ruff·포맷 검사와 로컬 링크 검사를 통과했다. 최종 소스 해시와 실제 검증 결과는 verification.json에 기록한다. 커밋·푸시·운영 API 변경은 수행하지 않았다.
