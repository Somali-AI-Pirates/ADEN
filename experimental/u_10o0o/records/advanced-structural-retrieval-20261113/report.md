# 구조적 검색 개선 실험 결과
2026-11-13 · 완료 · 기존 기준선 유지

## 결론
이번 네 변경을 단독으로 기본 구성에 넣을 근거는 충분하지 않다. **V의 후보 관측 확대는 같은 후보에서 4문항을 회복했고 전체 근거가 충족되던 문항의 하락은 없었다.** 그러나 종료 상태가 크게 악화하고 추가 호출 때문에 지연이 늘었다. 이 구현을 그대로 채택하지 않는다. S는 검색 근거를 추가 확보하지 못했고, R·P는 회복과 손실이 함께 발생했다.

가장 명확한 구조적 문제는 **찾은 후보 중 일부를 계획자가 보지 못하고, 짧은 발췌에서 판단한 충분·부족 상태가 최종 원문에 실제로 들어 있는 근거와 어긋나는 것**이다. 한편 일반 검색을 넓히면 서로 다른 사건을 더 찾는 이점은 있으나, 해당 사건의 규정·날짜·역할을 함께 유지한다는 보장은 없었다.

## 무엇을 실행했나
A는 92e8c038a432c334400619ff38e603be5d863c2e의 DB 우선 통합 TableRAG를 동결한 대조군이다. 작업 중 갱신된 서버 코드를 섞지 않았다. 같은 공통 SQLite·원문·KURE-v3·KURE nano·Luna medium을 사용한다. 제품 설정과 기본 실행은 변경하지 않았다.

| 조건 | 변경 | 그대로 둔 부분 |
|---|---|---|
| A | 없음 | DB 우선, 페이지·표 5:5, 기존 도구 루프 |
| S | 기존 관측으로 요구별 출처를 선택하는 Luna 1회 추가 | A의 후보 20쪽과 관측 원문 |
| V | 후보 20쪽 각각의 관련 원문 발췌를 같은 선택기에 제공 | A의 후보·점수·원문, S와 같은 선택 로직 |
| R | 검색기별 Top 50의 고유 페이지 최대 100쪽을 한 번 리랭킹한 뒤 20쪽 반환 | 기존 질문·도구·종료 정책 |
| P | IS 원문 문단 8,048개를 보조 검색 단위로 추가 | 기존 페이지·표 유지, 최종 원본 페이지 복원 |

최종 후보 최대 20쪽, 최종 원본 최대 8쪽, SQL을 포함해 8,000토큰이다. 답변 생성은 없다. S/V는 저장된 A를 재생하는 후처리이며, 새 제품 경로의 전체 동작을 검증한 것은 아니다. V는 발췌 위치와 관측 범위를 함께 바꿨다. P는 BM25 통계와 검색 단위 구성도 함께 바뀐다.

공식 60 + 카테고리 220 + 새 40 = 서로 다른 320문항을 평가했다. 공식 추가 30문항은 3회 반복해 조건별 380건, 총 1,900건을 저장했다. A의 추가 90건은 같은 동결 런타임의 직전 저장 결과를 재사용했다. 새 실행은 A/R/P 1,050건과 S/V 후처리 760건이다.

## 후보에는 있었지만 계획자가 보지 못한 네 사례
V가 회복한 근거는 모두 A의 후보 20쪽 안에 있었다. A의 그래프가 실제 읽은 발췌에는 아래 페이지가 없었다. V가 후보별 발췌를 제공하자 선택되어 최종 원문에도 남았다.

## 근거 확보와 종료 판단은 별개였다
첫 반복 320문항에서, 근거가 충분하고 데이터가 답변을 허용하는데 허용되지 않은 보류 상태로 끝난 건수는 A 7, S 28, V 93, R 2, P 6이었다. 올바른 추가 확인·보류는 이 오류에 포함하지 않았다. 데이터의 허용 종료 상태와 일치한 전체 건수는 A 294, S 251, V 184, R 298, P 292였다.

V의 낮은 '근거 부족인데 충분 선언' 건수만 보고 안전성이 개선됐다고 판단하면 안 된다. 많은 질문을 지나치게 보류한 대가가 섞여 있다. 짧은 발췌를 읽은 모델의 인용 오류, 요구 해석, 충분 판정이 실제 최종 원문과 일치하지 않았다. 인용 문자열의 존재 검사만으로 이 차이를 해결할 수 없었다.

따라서 V에서 확인한 관측 개선은 살펴볼 가치가 있지만, **현재 선택기와 종료 상태 변경을 함께 제품에 넣는 것은 권하지 않는다.**

## R과 P가 기본 대안이 되지 못한 이유
- R은 카테고리 후보 전체 충족을 186/200 → 188/200으로 높였지만 최종은 183/200 → 182/200이었다. 같은 세트에서 후보가 충분한데 최종에 남지 못한 경우가 3 → 6개였다. 모호한 두 사건의 근거는 13/20 → 17/20으로 개선됐으나 번호 없는 한 사건은 20/20 → 18/20, 일상 표현은 34/40 → 32/40이었다.
- P도 카테고리 후보는 188/200이지만 최종은 A와 같은 183/200이었다. 일상 표현은 34/40 → 35/40으로 올랐으나 업무 규정은 18/20 → 17/20이었다. 새 보조 세트는 A보다 1문항 낮았다.
- P의 ADD09 두 번째 반복에서는 필요한 원문이 벡터 2·5위의 서로 다른 검색 단위로 잡혔지만 RRF의 20쪽에 남지 못했다. 문단을 추가해 발견했다고 최종 후보가 보장되는 것은 아니다.
- R의 ADD09 첫 반복에서는 해당 페이지를 리랭킹 풀의 51위까지 살렸지만 KURE 57위여서 다시 탈락했다. 후보 확대만으로 여러 요청의 근거를 모두 확보할 수는 없었다.

이 차이는 검색기·후속 질의·최종 선택이 연결된 실제 도구 루프에서 관찰했다. R/P의 후속 질의는 Luna의 판단에 따라 달라졌으므로, 같은 질의 목록의 순위만 바꾼 순수 재생 실험으로 해석하지 않는다.

**ADD02의 0/3은 세 번 모두 검색하지 못했다는 뜻이 아니다.** 예약 변경 절차 근거 자체는 A/S/V/R에서 2/3, P에서 1/3 확보했다. 마감 규칙도 검색됐지만 질문에 없는 적용 조건까지 확정할 수 없다는 판정을 모든 구성에 동일하게 적용했다. AS-DEV09에도 같은 기준을 적용했다.

추가 30문항의 근거 있는 29개 × 3회 전체 점수는 A/S/V 82/87, R 83/87, P 81/87이다. 이전 보고서 A 84/87과 달라진 2건은 ADD02의 적용 범위 판정이며 **A 검색 결과가 바뀐 것이 아니다.** 이 수치 차이를 검색 성능 하락으로 해석하지 않는다.

## 평가를 어떻게 검수했나
모든 검색 결과 저장 후에만 참고 요구를 읽었다. 고유 최종 문맥 668개를 채점하고, 실패·인용 오류와 비교 상대 221개 문맥을 다시 검토했다. 이후 실패 문항의 후보 문맥을 확인했다. 최종 인용 검증 미완료는 0건이다.

- 표의 같은 행에서 이메일이 다른 열과 섞인 사례는 행 전체의 실제 문자열로 근거를 남겼다. 주소를 이어 붙인 가짜 인용은 만들지 않았다.
- SI 정정 창구만으로 신규 SI 제출 창구를 충족했다고 본 A의 AS-DEV06 판정은 실패로 정정했다. 반대로 같은 원문 규칙인데 한 조건만 실패로 본 판정도 맞췄다.
- STRUCT-HOLD-002는 잔액을 묻는 질문인데 참고답이 붙인 회수 절차의 명시적 지시까지 요구하던 과잉 채점을 수정했다. 모든 구성에 똑같이 적용했고 원래 엄격 채점도 보존했다.
- 같은 질문에서 검증된 완전한 근거가 후보 문맥에 그대로 포함되면 그 후보는 충분하다. Judge가 더 긴 문맥에서 같은 근거를 놓쳤다는 이유로 후보 실패로 처리하지 않았다.
- 모호한 적용 범위는 성공으로 강제하거나 분모에서 제거하지 않았다.

원시 응답·원문 인용·사후 수정은 로컬 artifacts에, 수정 사유·출처 ID·지문은 이 기록 폴더에 남겼다. 모델은 같은 Luna이며 사람의 독립 검수는 아니다. 비교 모델 이름은 의미 채점 입력에서 숨겼지만, 원문으로 판단하는 자체 검토까지 완전한 블라인드 사람 평가라고 주장하지 않는다.

## 시간·실행량
새로 실행한 290문항에서 관측된 p50/p95(초)는 A 8.01/20.56, S 17.33/34.72, V 19.50/39.98, R 9.01/21.51, P 8.25/18.38이다. S/V는 A 시간에 추가 선택 호출을 합한 후처리 합계다. 공유 CPU/GPU 환경의 측정이며 서비스 SLA나 독립 CPU 벤치가 아니다.

R의 KURE 쌍은 6,000 → 21,615로 약 3.6배였다. P는 문단 벡터 약 66MB를 추가했고 새 문단 임베딩은 약 115초였다. 새 벡터는 GPU bfloat16 연산 후 float32 배열로 저장했다. 품질·비용을 검색 단위 하나만의 효과로 분리한 실험은 아니다.

새 API 요청 저장 기록은 4,368회다. 여기에는 문항·평가 준비, 검색 계획, 선택, 채점·재검토 및 무효화된 V 입력의 호출도 포함한다. 응답 기록 없이 중단된 5회와 사용량 미확인 응답 2건은 따로 기록했다. 알려진 사용량은 입력 39,811,110·출력 2,123,382토큰이며 공급자 청구액이나 캐시 할인을 대신하지 않는다. 답변 생성은 0회다. 시간 초과한 R의 ADD27 세 번째 실행도 실패 결과로 보존하고 성공할 때까지 재시도하지 않았다.

## 다음 변경의 범위
기본 구성은 유지한다. 이후에는 다음 순서가 타당하다.

1. **관측과 최종 근거를 일치시킨다.** 후보에 이미 있는 표·원문을 계획자가 읽을 수 있게 하고, 표는 행·열·역할을 유지한다. V의 발췌와 선택기를 그대로 붙이는 대신 기존 도구 루프에서 미확인 근거를 실제로 읽는 범위부터 검증한다.
2. **충족 여부와 질문의 확정 가능성을 구분한다.** 모호함을 입증하는 근거가 충분한 경우와 금액·상태를 확정할 수 있는 경우는 종료 동작이 다르다. 짧은 발췌의 인용 실패를 최종 전체 원문의 부족으로 곧바로 바꾸지 않는다.
3. **후보 확대는 필요한 질문에 제한해 검증한다.** R에서 신호가 나온 복수 사건 후보 확보를 따로 보고, 이미 유일한 코드로 확정되는 DB 빠른 경로에는 비용을 추가하지 않는다.
4. **IS 규정의 표현은 따로 다룬다.** 이번 P는 원문 문단을 더한 조건이다. 적용 범위·효력·예외를 보존한 규정 색인이나 표 구조 복원을 검증한 것이 아니므로, 그 설계 전체가 효과 없다고 결론 내리지 않는다.

이 네 항목은 후속 제안이다. 이번 실행에서 추가로 조합하거나 기본값을 교체하지 않았다.

## 검증과 재현
- 공통 Ruff check 통과.
- 마지막 전체 pytest: 685개 + subtest 11개 통과. 기존 Qdrant local exact 모드 안내 경고 1건.
- 개인 실험 테스트 12개 통과, 개인 코드·분석 스크립트 Ruff 검사 및 포맷 확인.
- 동결 코드·데이터·모델 지문, 1,900건 수, 후보·쪽·토큰 경계, S/V 동일 후보 760건, V 원문 부분 문자열 16,902개 확인.
- 추가 실행한 저장소 전체 format 검사는 범위 밖 기존 96개 파일에서 실패했다. 다른 작업자의 공통 코드는 일괄 포맷하지 않았다.
- 제품·패키지 코드 변경이 없어 패키지 빌드·서버 배포 검사는 수행하지 않았다. 하위 에이전트·사람 독립 리뷰는 수행하지 않았다.

## 레퍼런스와 이번 결과의 관계
- [Elasticsearch RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion): 순위 결합은 서로 다른 검색기 점수를 비교하는 방법이다. 필요한 업무 사실을 보존하는 제약은 아니므로 후보·최종 단계를 따로 측정했다.
- [LangChain: Deconstructing RAG](https://www.langchain.com/blog/deconstructing-rag): 검색 표현과 답변에 제공할 원문을 분리하는 관점으로 P와 원문 복원을 구성했다. 문단을 추가하면 항상 좋아진다는 근거로 사용하지 않았다.
- [LangGraph: Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents): 정해진 처리 단계와 모델이 선택하는 도구 흐름을 구분한다. 이번 R/P의 후속 검색은 모델 결정이므로 순위 변경의 기계적 효과와 완전히 분리됐다고 주장하지 않았다.
