# IS 기록 키 조회 확장과 HG식 연결 가능성

2026-11-11. IS의 정확 기록 조회를 2종·11,073개 키에서 **24종·22,523개 키**로 확장했다. 최근 KURE-v3 5:5 + HG 날짜 조회 결과에 추가했지만 공식·카테고리 280문항의 최종 문맥은 모두 동일했다. 기록 조회 범위는 넓어졌으며 이번 평가의 정확도 개선은 없었다. 현재 기본 검색 설정과 운영 API는 변경하지 않았다.

## 구현 범위

[IS 기록 조회 모듈](../../advanced_is_record_lookup.py)은 기존 StructuredStore의 읽기 전용 연결, source_records, record_fields, source_pages와 원본 파일 지문을 재사용한다. 새 DB 파일이나 스키마 변경 없이 기존 색인으로 기록 필드를 조회한다. 과거 lookup_handbook의 두 키 조회도 그대로 유지한다.

- SI기록, VGM 대조, 업무 기록번호, 대조번호, 신청·승인 기록 등 원문에서 확인한 24종 키 열만 지원한다.
- IS 두 자리-세 자리-두 자리 형태의 완전 기록 코드를 사용한다. 대소문자, 동등한 하이픈과 하이픈 주변 수평 공백은 기존 BM25의 코드 표기 기준으로 정규화한다.
- 수정통지와 입금 기록 두 열은 원문이 ‘완전 코드 + 공백 + 주석’ 형식이다. 이 두 열에서만 이 형식을 허용하고 원문 셀 값을 보존한다. 주석에 다른 IS 키가 들어가면 확정하지 않는다.
- 질문에 명시된 최대 두 기록을 각각 조회한다. 여러 행에 매칭되거나 모르는 키, 불명확한 제외, 세 개 이상 기록이면 조회 보충 없이 원래 검색 결과를 유지한다.
- 부분 번호, 코드 접두사, 장비 종류, 코드 없는 간접 표현으로 기록을 추정하지 않는다.
- 검증된 기록의 원본 쪽을 기존 apply_sources와 문맥 선택기에 넘긴다. 표 행만으로 문맥을 바꾸지 않고 설명·조건·예외가 있는 원본을 유지한다. 최종 문맥에 이미 있으면 그대로 둔다.
- 후보 최대 20쪽, 최종 최대 8쪽, o200k_base 8,000토큰을 유지한다. 원문 조회 후 추가 리랭킹이나 답변 생성은 없다.

사용자가 확인을 요청한 IS03-003-01은 AS009 3쪽의 SI기록 행으로 조회된다. 이전 두 키 조회에는 포함되지 않던 종류다. 코드의 IS03 접두사나 숫자 구간으로 다른 기록을 묶지는 않는다.

## 고정 비교와 결과

대조군은 [직전 HG 비교](../advanced-kure-hg-role-ab-20261111/report.md)의 lookup 조건이다. KURE-v3 임베딩과 BM25 5:5, KURE nano 상위 3쪽 + 나머지 RRF, 개선 HG 날짜 조회를 사용한다. 기존 후보·리랭킹 결과를 재사용하고 IS 조회만 바꿨다. 이 대조군을 저장소 기본 설정으로 새로 채택한 것은 아니다.

세 조건은 IS 보충 없음, 기존 두 키 종류로 IS 보충, 확장 24종으로 IS 보충이다. 대조군 280개 문맥을 실제 조립기로 다시 만들고 저장된 페이지·순서·문맥 해시와 모두 일치함을 확인했다. 세 조건의 결과 저장이 끝난 뒤에만 참고 근거를 읽었다. 새 임베딩·리랭커·외부 API 호출은 0회였다.

공식 60문항 중 참고 근거가 있는 58문항을 채점했다. 카테고리 220문항은 근거형 200개와 범위 밖 대조군 20개다. 공식은 각 참고 근거 그룹의 충족, 카테고리는 기존 필수 사실 채점을 그대로 사용했다. 공식을 전부 동일한 단일 정답 쪽 비교로 바꾸지 않았다. 같은 book_id + page 기준의 페이지 Recall@8도 공식 86.64%, 카테고리 근거형 88.67%로 세 조건 모두 같았다.

기존 두 종류 조회는 상황형 4문항에 발동했고 확장은 6문항에 발동했다. 새 지원은 AS-S01-08의 대조번호와 AS-S01-10의 신청·승인 기록이다. **6문항 모두 이미 기준선의 최종 8쪽에 해당 원본이 들어 있었다.** 나머지 274문항에는 이번에 지원한 완전 IS 기록 키가 없어 보충이 발동하지 않았다. 공식 60문항과 일상 표현 40문항에는 이 키 조회가 발동한 문항이 없었다. 모든 280문항에서 최종 문맥 해시가 같았고 페이지 Recall의 증감도 없었다.

## HG처럼 여러 기록을 연결할 수 있는가

### 확인된 차이

HG는 검증된 사건 ID 하나에 약정·현장·대조·청구·수납의 다섯 역할이 연결된다. IS의 완전 기록 코드는 원본에서 해당 행을 식별한다. 3,750쪽의 검증된 레이아웃에서 지원 IS 기록 코드가 다른 페이지의 기록을 직접 참조하는 경우는 발견하지 못했다. 같은 IS 접두사나 표 양식은 업무 종류와 관련되지만 동일 사건의 증거로 사용하지 않았다.

### 좁은 범위에서 명시 관계가 있다

IS의 입금 기록과 수정통지에는 별도의 연결청구 열이 있다. 이 값으로 청구번호 열을 대조했다.

| 출발 기록의 연결청구 | 청구행이 1개 | 청구행이 여러 개 | 대상 청구행 없음 | 합계 |
|---|---:|---:|---:|---:|
| 수정통지 | 107 | 30 | 194 | 331 |
| 입금 기록 | 178 | 34 | 313 | 525 |
| 전체 | 285 | 64 | 507 | 856 |

유일하게 연결된 285개 관계의 대상은 239개 청구행이다. 청구번호 자체도 전체 1,061개 중 172개는 여러 행에 등장한다. 위 수치는 명시된 열과 값의 참조 일치이며 적용 시점·수납 확정·금액 계산의 정당성까지 검증한 결과는 아니다.

따라서 **IS 전체를 HG와 같은 고정 사건 묶음으로 만드는 근거는 부족하지만, 입금·수정통지 → 연결청구 → 청구 원본이라는 좁은 연결은 후속 실험 가치가 있다.** 이번 검색 비교에는 청구 연결을 사용하지 않았다. 실제 연결로 확장할 때에는 유일한 상대 기록, 기록 상태와 적용 범위를 확인해야 하며 64건의 다중 후보와 507건의 미매칭을 자동 확정하지 않아야 한다. HG처럼 무조건 다섯 역할을 확보하는 선택 규칙도 적용하지 않는다.

공유 예약·장비·계약 키는 별도로 원문에 나타나지만 같은 키만으로 같은 업무 사건의 모든 기록을 뜻한다고 볼 수 없다. 이번 조사에서는 키 열 종류와 값을 묶은 기준으로 10,669개가 여러 쪽에 나타났고 한 조합은 최대 14쪽에 걸쳤다. 이들을 통째로 최종 8쪽에 넣는 기능은 만들지 않았다.

## 판단

정확한 IS 기록을 원본과 함께 안정적으로 읽는 기능은 구성 가능하며 이번에 구현·검증했다. 현재 평가에서의 개선 근거는 없으므로 기본 검색을 교체하지 않는다. 공식 및 일상 표현의 남은 누락을 이번 키 조회로 해결했다고 해석할 수 없다.

다음 관계 실험은 명시 연결청구가 있고 상대가 유일한 표본부터 기존 원문 검색과 비교하는 것이 적합하다. 코드 없는 업무 설명은 별도의 의미 검색·메타데이터 식별 문제다. 표와 서술을 나누어 조회하고 함께 근거로 사용하는 방향은 [TableRAG](https://aclanthology.org/2025.emnlp-main.710/)의 문제 설정과도 관련이 있지만, 해당 논문의 다단계 LLM 실행을 이번 구현에 도입한 것은 아니다.

## 재현

저장소 루트에서 실행한다. OUTPUT은 기존 결과를 덮어쓰지 않는 새 경로여야 한다. 필요한 로컬 입력은 기존 StructuredStore 스냅샷, 정제본과 Poppler 캐시, 원본 PDF, 직전 KURE-v3 + HG 날짜 조회의 280문항 저장 결과다.

```
uv run --no-sync python -m experimental.u_10o0o.advanced_is_lookup_ab audit   --output artifacts/u_10o0o/is-lookup-replay/audit

uv run --no-sync python -m experimental.u_10o0o.advanced_is_lookup_ab retrieve   --output artifacts/u_10o0o/is-lookup-replay/results   --audit artifacts/u_10o0o/is-lookup-replay/audit/audit.json

uv run --no-sync python -m experimental.u_10o0o.advanced_is_lookup_ab score   --output artifacts/u_10o0o/is-lookup-replay/results
```

최종 로컬 산출물은 artifacts/u_10o0o/advanced-is-record-lookup-20261111/audit-v3와 v2다. 입력·스냅샷·소스 코드 지문은 원본 대조 및 실행 manifest에 남겼다. 이전 v1은 초기 22종 범위의 비교이며 최종 결과는 v2다. [실행 조건](run.json) · [채점 입력과 순서](score-manifest.json) · [진행 기록](work-log.md)

## 검증

- 공통 Ruff, 새 실험 3개 파일의 별도 Ruff와 서식 검사 통과.
- 공통 테스트 및 새 조회·기존 구조화 저장층·라우팅 테스트 321개, 하위 검사 15개 통과.
- 신규 테스트는 표기 변형, 출처·원문 값 보존, 기존 두 키 경로, 두 기록 순서, 중복·미검증·미지원 키, 제외, 부분 번호, 잘못된 주석, SQL 읽기 전용, 후보 20·최종 8·8,000토큰 내 원본 보충을 확인한다.
- 새 CLI 도움말, 전체 원본 감사, 280문항 조회 재현과 채점 실행 통과.
- 부대 대화의 위임 금지에 따라 자체 검토했다. 독립 에이전트 리뷰는 실시하지 않았다.
- 개인 experimental 파일만 추가했다. 운영 API·패키징·기본값 변경과 커밋·푸시는 없다. 공통 패키지 빌드는 이번 변경에 적용되는 검사가 아니므로 실행하지 않았다.
