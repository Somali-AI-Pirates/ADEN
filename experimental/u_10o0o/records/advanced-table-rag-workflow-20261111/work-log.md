# TableRAG 단계 분리·중간 근거 보존 실험

## 지원 범위와 실행 계약

사용자 요청: 첨부 해설의 검색 후 SQL 생성, 출처 있는 중간 답변, 실행 중 필수 근거 확인을 구성하고 같은 문항에서 실험한다. 기존 .env 키, GPT-6 Luna, 비용 한도 없음, 필요한 reasoning 상향에 대한 부대 대화 승인을 유지한다. medium으로 고정하며 질문·검색된 원문/표·SQL 결과를 모델에 제공한다. 정답은 모든 결과 저장 후 채점에만 쓴다.

기존 table_rag의 저장소·색인·하이브리드·KURE·HG 조회를 재사용한다. 별도 workflow 진입점에서 자연어 하위 질문 도구 → 해당 질문 검색 → 현재 스키마를 이용한 SQL 생성/실행 → 출처 검증된 중간 답변 → 근거 확보 상태를 보고 후속 질문/종료 순서로 실행한다. 새 SQL을 검색 전에 만들지 않는다. 계획자는 처음 질문에서 대상·요청별 필요 근거 목록을 만들며, 원질문의 인용 구간이 없는 필요 항목은 거절한다. SQL 한 번으로 가능한 집계는 불필요하게 쪼개지 않는다.

근거 확인은 모델의 의미 판정과 기계적 출처 대조를 결합한다. 문서 인용이 실제 관측 발췌에 존재하는지, SQL 인용이 실제 결과 셀인지 확인한다. supported 선언에 유효 근거가 없으면 충족으로 세지 않는다. 빠진 요청은 보충 검색하거나 보류하며, 최종 포장 후 상태를 다시 계산한다. 이를 정답 완전성의 형식적 증명이나 사람 검수로 부르지 않는다.

원문 후보는 20쪽, 원문 발췌는 최대 8쪽, 실제 답변용 근거 JSON 전체는 8,000토큰으로 제한한다. 확인된 중간 답변/SQL 결과는 모든 원본 페이지를 다시 넣지 않아도 출처 참조와 함께 보존한다. 따라서 전체 출처 수는 8개를 넘을 수 있다. 기존의 원문 8쪽 근거 지표와 추가 인용 발췌의 지표, 답변 정확도를 분리해 이 차이를 숨기지 않는다. 토큰 예산으로 검증 근거가 탈락하면 충족 상태도 낮춘다.

비교는 저장된 기존 KURE-v3 + HG 기준선, 이전 v5 TableRAG, 새 workflow다. 기존 두 검색 결과는 지문으로 확인해 재사용하고 새 workflow는 280문항을 실행한다. 답변 비교는 기존 기준선/새 workflow에 같은 새 답변 지침으로 생성하고 별도 가린 순서의 모델 채점을 수행한다. 이전 v5 답변 점수는 새 지침의 직접 비교로 섞지 않는다.

모델은 KURE-v3/ KURE nano 기존 리비전과 Luna medium을 유지한다. SQL 읽기 전용, 관측된 스키마만 허용, 2초 제한과 소수 연산, 최대 5회 하위 질문을 유지한다. 코드/실행/질문/색인 지문과 API 시작·응답 체크포인트를 남기며 자동 재시도하지 않는다. 최악의 계획·SQL·중간답변·최종답변·채점 약 5,880회 이내(실제 SQL 없는 단계는 감소)로 기록하며 사용자 승인한 무제한 비용 범위다.

이번에는 논리적 동일성이 검증되지 않은 여러 페이지/양식을 하나의 표로 자동 병합하지 않는다. 기존 원본 물리 표 전체를 조회하며 여러 표의 연결 의미는 여전히 별도 검증이 필요한 범위다. IS 별도 본문 색인/HG·HA 페이지 연결 조건도 유지한다. 논문과 다른 모든 요소가 사라졌다고 주장하지 않고, 요청한 단계 순서·중간 결과·근거 확인을 검증한다.

기존 기본 검색/API, 공유 .venv, 다른 실험 프로세스, v5 기록은 변경하지 않는다. 원문/질문/답변/셀값은 ignored artifacts에, 공유 기록에는 집계·문항 ID·출처 ID·지문만 남긴다. 독립 에이전트는 이 부대 대화에서 금지되어 자체 검토한다. 기준선 승격·커밋·푸시는 범위 밖이다.

## 연결 점검과 자체 리뷰

v1 첫 실행 전 기존 기준선의 실행 코드 지문 검사에서 공통 metrics.py가 달라졌음을 발견했다. 원본 v5에 보존한 해당 코드의 해시가 기준선 manifest와 일치하는지 확인했다. 현재 공유 파일은 수정하지 않고 저장 데이터/입력 지문과 원래 실행 코드 보존본을 검증하도록 새 실험의 로더를 구성했다.

v1 한 문항 실제 API 연결은 계획 → 하위 질문 검색 → 현재 스키마 SQL → 중간 답변 → 도구 결과 피드백 → 종료로 완료했다. 계획/SQL/중간 단계 4회와 양쪽 답변 호출을 확인했고 참고 정답은 열지 않았다.

검토에서 기각된 중간 주장이 다음 계획의 last_step에 다시 들어갈 수 있는 부분을 제거했다. 검증된 주장만 계획에 전달하고 SQL 오류/상태는 별도로 전달한다. 한 주장에 잘못된 인용이 하나라도 있으면 그 주장 전체를 제외한다. 최종 미충족 요청이 남아 있으면 답변의 answered 상태를 허용하지 않는 검사도 추가했다. 원문 8쪽보다 많은 인용을 반영한 보조 지표는 실제 출처 수에 맞춰 nDCG를 계산한다. 이 보완을 반영한 v2를 본 평가로 사용하며 v1 연결 점검 결과는 품질 집계에 섞지 않는다.

## 본 평가 시작

v2에서 검색·모델·프롬프트·근거 포장 조건을 고정했다. 원본 표/벡터 자산과 기존 기준선 결과는 해시로 검증했다. 실행 시작 코드 보존본을 protocol에 연결하고, 원문 8쪽과 보존 인용 지표를 분리한다. 모델 호출 4개 동시, 질문 임베딩 CPU 2스레드, 리랭커 GPU float32 배치 1로 기존 조건을 유지한다.

최종 자체 리뷰에서는 SQL 생성 순서, 실제 function_call_output, 출처 없는 주장, 다른 스키마 사용, SQL 오류, 전체 모집단 불확실, 예산 손실, 실패 후 중복 API 호출 방지와 정답 접근 게이트를 확인했다. 부대 대화 제한에 따라 독립 에이전트 리뷰는 수행하지 않았다.

Ruff 공통·개인 명시 검사 및 개인 format check를 통과했다. 공통/기존 개인/이전 TableRAG/새 workflow pytest 합계 506개와 subtest 15개가 통과했다. 본 평가 실행 이후 품질 결과를 보고 검색/프롬프트를 수정하지 않는다.

## 본 평가 완료와 사후 검사

v2 검색·양쪽 답변 280문항을 모두 저장하고 run.json의 complete와 출력 지문을 확인한 뒤에만 참고 근거를 읽었다. 검색 단계 API 1,369회 중 1,360회 완료, 9회 시간 초과였으며 자동 재시도하지 않았다. 양쪽 답변 560회는 모두 완료했다. 실행 중 사용자 GPU 사용 승인을 확인했으며, 이미 적용 중인 CUDA 리랭커를 유지했다. 질문 임베딩은 CPU, KURE 리랭커는 GPU였다.

저장 결과를 바꾸지 않고 score/report 후처리만 수정했다. 전체 출처 수는 원문 출처와 중간 근거 출처의 합집합으로 세고, 기존 기준선뿐 아니라 이전 v5 대비 문항별 변화도 내보냈다. 동결 코드와 AST를 대조하여 수정된 함수가 score와 report뿐임을 확인했다. 채점 코드 지문을 score-manifest에 별도로 남겼다.

처음 토큰 재검사는 저장 JSON의 정렬된 키 순서로 다시 직렬화해 실패했다. 저장 함수가 키를 정렬하면서 토큰 경계가 달라진 것이므로, audit.py에서 동결 Ledger.payload의 실제 입력 키 순서를 복원해 280개 모두 실행 당시 토큰 수와 일치함을 확인했다. 원문은 최대 8쪽, 실제 evidence JSON은 최대 8,000토큰이었다. 이 과정에서 실행 결과나 모델 입력은 바꾸지 않았다.

보존한 문서 인용 1,552개와 SQL 셀 인용 685개를 원본/저장 SQL 결과에 대조했다. 출처 참조는 최대 9개이며 8개를 넘은 문항은 1개였다. 이는 원문 8쪽에 추가 인용을 보존하는 설계에 따른 것으로 원문 지표와 추가 인용 지표를 분리했다. 답변의 허용 목록 밖 출처는 0개였고, 미충족 요청 때문에 답변 상태를 낮춘 경우는 5개였다.

이전 v5 대비 원문 근거 충족은 3개 개선·15개 하락했다. 15개 하락 중 6개는 검색/표 발견 단계, 1개는 합친 후보 20쪽, 8개는 최종 선택/예산에서 근거를 잃었다. 9개는 최초 검색에서 이미 필요한 근거가 있었다. 추가 인용으로 회복한 것은 두 사건 비교 1개이며, 모호한 두 후보 유형의 6개 손실은 회복되지 않았다. 새 흐름을 기준선으로 승격하지 않는다. 상세 단계 판정은 stage-diagnosis.md/json에 있다.

최종 보고서에는 모델 채점과 검색 채점의 의미를 구분한다. 인용/셀 일치 검사는 의미적 정답 보증이 아니며, 실행 중 모두 충족으로 본 211개 중 사후 참고 근거 미충족 15개도 그대로 공개한다. 별도 API 호출의 가린 X/Y 채점을 진행했으며 사람 검수로 표현하지 않는다.

## 사후 답변 평가 및 완료

가린 순서의 별도 채점 280회가 모두 완료됐다. 기존 기준선/새 workflow의 완전 답변은 공식 44/60→46/60, 카테고리 양성 155/200→163/200, 범위 밖 대조 19/20→20/20이었다. 같은 조건끼리만 비교하고 v5의 다른 답변 지침 점수는 섞지 않았다. 모호한 두 후보 유형은 양쪽 모두 4/20으로, 검색 근거와 실제 답변 의미를 구분해야 함을 확인했다.

새 검색의 p50/p95는 34.95/78.79초, 답변 포함은 38.60/85.91초였다. GPU 리랭킹을 적용한 로컬 검색 누적 p50 3.00초보다 API 누적 30.60초가 컸다. 검색 API는 문항당 평균 4.89회다. 공유 장비·4개 요청 동시 실행의 관측값으로 기록하며 통제된 운영 지연 측정으로 해석하지 않는다.

후처리 수정 후 공통 및 개인 Ruff, format 검사, 전체 pytest 506개와 subtest 15개를 다시 통과했다. 보고서·원문 출처 감사·문항별 변화·단계별 누락 분석을 읽어 수치와 링크를 확인했다. 최종 해석은 conclusion.md에 남겼으며 새 구성의 자동 채택은 하지 않았다.
