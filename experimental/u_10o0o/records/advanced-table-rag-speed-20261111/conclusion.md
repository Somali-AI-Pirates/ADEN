# TableRAG v5 속도 개선 실험 결론

**기존 검색 결과를 유지하면서, 여러 요청이 겹칠 때의 대기를 줄일 수 있었다.** 이번 환경에서는 CPU 임베딩과 GPU 리랭커의 잠금을 나누고 리랭커 배치를 4로 쓰는 구성이 가장 빨랐다. 기본 실행은 아직 바꾸지 않았다.

## 무엇을 바꿨나

기존 A는 한 요청의 임베딩부터 리랭킹까지 하나의 잠금을 유지한다. 이 때문에 다른 요청은 CPU와 GPU 중 하나가 비어 있어도 기다린다. B는 각 모델에 별도 잠금을 두어 앞 요청의 GPU 리랭킹과 다음 요청의 CPU 임베딩을 겹친다. C는 B에 리랭커 배치 4를 적용한다. 같은 모델에서 두 encode/predict를 동시에 실행하지는 않는다.

모델·정밀도·검색어·BM25·벡터·RRF·후보 20쪽·HG 조회·최종 8쪽·8,000토큰은 같다. 저장된 v5의 질문 계획과 SQL 순서를 재생했고, API 호출과 답변 생성은 하지 않았다.

## 결과와 시간

공식 60문항과 카테고리 220문항의 **494개 검색 순서·표 후보·조회 경로가 모두 같았고, 최종 문맥 280개와 SQL 값·출처도 모두 같았다.** 새 정답 채점은 실행하지 않았다. 근거가 같은지 대조한 결과이므로 이번 표본에서 검색 품질의 손실은 관측되지 않았다. 새 질문의 정확도나 새로 생성할 답변의 동일성까지 보장하는 결과는 아니다.

지연은 미리 고정한 15문항을 각 조건에서 3회씩 실행했다. 아래 p50/p95는 45개 관측값을 합쳐 계산했으며 서로 다른 45문항을 뜻하지 않는다. 한 문항 안의 여러 검색·SQL·최종 포장 시간을 포함하고 LLM 대기시간은 제외했다.

| 구성 | 단일 요청 p50 | 단일 요청 p95 | 동시 요청 4개 p50 | 동시 요청 4개 p95 |
|---|---:|---:|---:|---:|
| A: 기존 전체 잠금·배치 1 | 1.241초 | 5.349초 | 5.155초 | 21.202초 |
| B: 잠금 분리·배치 1 | 1.345초 | 5.448초 | 3.127초 | 12.256초 |
| C: 잠금 분리·배치 4 | **1.046초** | **5.204초** | **2.888초** | **11.507초** |

- 동시 요청 4개에서 B는 A보다 p50 약 39%, p95 약 42% 감소했다. C는 각각 약 44%, 46% 감소했다.
- C는 B에 비해 동시 요청 p50 약 8%, p95 약 6%가 더 줄었다. 큰 효과는 잠금 분리에서 나왔고 배치 증가는 추가 효과다.
- 단일 요청에서는 B의 이득이 없었다. C는 p50 약 16%가 줄었지만 p95는 약 3%만 줄었다. 요청 하나의 긴 꼬리 지연이 크게 해결된 것은 아니다.
- 동시 요청 4개에서 15문항을 모두 처리한 회차별 시간도 A 32.69/32.79/33.79초, B 19.51/19.31/21.22초, C 18.24/18.64/19.41초로 같은 경향이었다.

## 병목은 어디였나

동시 요청 4개일 때 기존 A는 검색 한 번당 전체 잠금을 평균 **3.01초** 기다렸다. C에서는 CPU 잠금 대기 0.86초, GPU 잠금 대기 0.30초로 나뉘었다. 대기가 사라진 것은 아니지만 서로 다른 자원을 쓰는 요청이 겹쳐 실행됐다.

단일 요청의 검색 1회 평균을 보면 CPU 임베딩은 약 0.52초, GPU 리랭킹은 A 0.61초·C 0.54초였다. BM25 약 0.003초와 벡터 점수 계산 약 0.006초는 이 표본의 주된 병목이 아니었다. 여기서 키워드 검색식을 다시 바꾸는 것은 이번 지연 문제의 우선 해결책이 아니다.

C의 리랭킹 점수는 최대 약 0.000024 차이가 있었지만 494개 검색의 순위와 최종 문맥은 바뀌지 않았다. B의 점수는 A와도 같았다. 배치별 연산 차이를 무시하고 모든 미래 입력의 순위까지 같다고 단정하지 않는다.

## 실패 조건과 측정 한계

배치 8은 220문항을 마친 뒤 긴 입력에서 GPU OOM으로 중단됐다. GPU 전체 8GB 중 기존 설정이 허용한 PyTorch 할당 상한은 약 978MiB였다. 배치 8이 8GB GPU에서 원래 불가능하다는 뜻은 아니다. 이번 메모리 조건에서는 채택 근거가 없다. 초기 긴 입력 3개를 통과한 것만으로 모든 패딩 길이의 메모리 안전성이 검증되지는 않았다.

v1 후반에 다른 GPU 작업이 나타나 해당 실행의 시간값은 최종 속도 판단에 쓰지 않았다. 검색 동등성 결과만 코드·입력 지문을 검증해 이어받고 속도는 v2에서 다시 측정했다. v2 반복 측정 중에도 다른 작업이 겹친 1회차를 제외하고 재측정했다. 채택한 회차의 관측 GPU 사용량은 최대 1,692MiB였다. 메모리 관측은 공유 호스트의 모든 간섭을 배제하는 검사가 아니며 CPU·열·전력 상태까지 완전히 격리하지 않았다.

측정 시점은 워커가 문항을 실행하기 시작한 때다. 실행 대기열에 들어오기 전의 대기는 포함하지 않는다. 4개 작업자가 API 대기 없이 계속 요청하는 조건이므로 실제 서비스의 요청 도착 간격과도 다르다. 15개 고정 표본의 p95는 운영 SLO 근거로 충분하지 않다.

**기존 전체 응답시간 12.31/33.53초가 이번 결과만큼 줄었다고 해석하면 안 된다.** 질문 계획과 답변 생성의 API 지연은 그대로 남으며 이번에는 측정하지 않았다.

## 적용 판단

현재 장비와 메모리 조건에서는 **잠금 분리 + 배치 4를 다음 적용 후보로 삼을 근거가 있다.** 우선순위는 잠금 분리이며, 모델이나 검색 정책 교체 없이 이번 입력의 결과를 유지했다. 단일 사용자 응답시간을 크게 줄이는 목표는 별도로 남는다.

실험은 여기서 완료했다. 기본 Retriever·운영 API·기준선 승격·커밋·푸시는 수행하지 않았다. 운영 적용 전에는 실제 API를 포함한 요청 도착 간격으로 종단 지연을 측정하고, 긴 입력과 목표 동시 사용자 수에서 메모리 여유를 확인해야 한다.

검증: Ruff, 포맷, CLI 실행, 전체 pytest **514개 + 서브테스트 15개 통과**. 독립 에이전트가 금지된 부대 대화이므로 독립 리뷰는 수행하지 않고 자체 검토했다.
