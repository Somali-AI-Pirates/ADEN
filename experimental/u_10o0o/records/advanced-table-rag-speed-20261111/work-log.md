# TableRAG v5 로컬 검색 지연 실험

## 범위와 고정 조건

사용자 요청은 성능 손실 없이 줄일 수 있는 부분의 실제 비교다. 새 개인 실험 모듈에서 저장된 v5 280문항·494개 검색어와 도구 호출 순서를 재생한다. 외부 모델 API, 답변 생성, 새 질문 계획은 호출하지 않는다. 기존 v5의 검색기·SQL·문맥 포장을 재사용하고, 기본 실행과 운영 API는 바꾸지 않는다. 이전 결과나 다른 작성자의 변경을 덮어쓰지 않는다.

비교는 A=기존 전체 잠금/배치1, B=임베딩·리랭커 잠금 분리/배치1, C=B/배치4, D=B/배치8이다. 임베딩은 기존 CPU bfloat16·2스레드, 리랭커는 같은 KURE nano GPU float32, 모델 리비전·검색 후보20·최종8쪽·8,000토큰·HG 조회·동점 정렬은 유지한다. CPU·GPU 모델은 각각 별도 잠금으로 보호하며 공유 모델에서 동시에 predict/encode하지 않는다. 검색 메모이제이션은 하지 않는다.

모든 조건에 같은 질문 순서를 주고, 4개 요청을 동시에 처리하되 한 질문의 하위 검색은 순서를 유지한다. API 대기 없이 로컬 작업을 재생하는 포화 부하이므로 실제 서비스 응답시간으로 부르지 않는다. 각 조건은 280문항 전체에서 후보 순서·표/조회 경로·문맥 해시와 SQL 보존을 확인한다. 조건 순서는 20문항 블록마다 순환해 시간에 따른 장비 부하 편향을 완화한다.

별도 지연 표본은 정답/지연을 보지 않고 세트별 ID 해시 순서로 3개씩, 총 15개를 고정한다(공식 개발·공식 추가·상황·일상 표현·업무 규정). 이 표본을 워밍업 뒤 1개/4개 동시 요청으로 조건별 3회 반복하고 순서를 순환한다. 대조 범위 밖 문항도 전체 280개 일치 검사에는 포함한다.

GPU 메모리는 먼저 기존 0.12 프로세스 비율을 사용한다. 다른 실험을 종료하거나 설정을 바꾸지 않는다. 배치가 해당 메모리에서 불가능하면 OOM을 기록하고 해당 조건의 측정을 중지한다. 지원하지 않은 배치를 성공으로 표시하지 않는다. GPU 여유가 확보된 경우에도 동일 비교의 메모리 조건을 임의로 바꾸지 않는다.

저장 코드와 현재 코드의 차이는 공통 metrics.py와 table_rag의 CLI/보고서뿐이며 v5 검색·모델·조회 구현은 같은 지문임을 확인했다. 초기 6개 검색에서 기존 Retriever와 계측 A의 결과를 대조한다. 새 클래스는 실험에 필요한 검색 실행 구간만 계측하고 기존 저수준 함수와 문맥 포장을 재사용한다. 독립 에이전트는 부대 대화에서 금지되어 자체 검토하며, Ruff·pytest와 CLI 실제 실행을 확인한다.

초기 GPU 확인: RTX 5060 Laptop 8GB 중 약 5.3GB 사용, 별도 nemotron_followup timing 프로세스 실행 중. 구현·검사를 준비하며 해당 벤치가 끝난 뒤 측정한다.

## 실행 전 자체 검토와 연결 확인

기존 GPU 사용 프로세스가 종료되고 약 354MiB 사용 상태를 확인한 뒤 시작했다. 검색 결과/순위 보존, CPU 임베딩과 GPU 리랭킹의 겹침, SQL 시간 필드와 값 비교의 구분, 표본 고정, 저장된 문맥 재생에 대한 집중 테스트 8개가 통과했다.

두 공유 모델에는 각각 잠금을 두어 같은 모델의 동시 encode/predict를 막는다. 조건은 서로 동시에 실행하지 않고 블록 단위로 순환한다. 계측 A와 원본 Retriever의 첫 6개 검색이 모두 같았다. 정답을 보지 않고 입력 토큰이 긴 기존 검색 3개로 워밍업했으며 A/B/C/D 모두 기존 메모리 비율에서 실행됐다.

v5는 SQL 결과의 seconds 값까지 근거 JSON에 직렬화한다. 새 실행의 초 단위 소수 자리수만 달라져 토큰 예산이 바뀌지 않도록, SQL을 실제 실행한 뒤 값·출처·상태의 일치를 확인하고 포장에만 저장된 seconds를 사용한다. 실제 SQL 소요 시간은 별도 기록한다. SQL 조회 결과를 캐시로 대체하지 않았다.

문항별 시간은 워커가 해당 문항을 실행하기 시작한 때부터 계산한다. ThreadPool 대기열에 아직 들어 있는 문항의 대기 시간은 포함하지 않는다. 따라서 4개 동시 조건은 4개 작업자가 계속 요청을 처리하는 부하이며, 모든 280개 요청이 한꺼번에 들어오는 운영 지연을 측정한 것이 아니다.

## 중단과 이어서 실행

v1은 A/B/C/D 각각 220문항·399개 검색까지 완료했다. 그 다음 배치 8이 긴 입력에서 CUDA OOM으로 중단됐다. 프로세스 메모리 상한은 전체 GPU 8GB가 아니라 기존 비율 0.12, 약 978MiB다. 합산 입력 토큰이 가장 긴 검색 3개의 사전 검사만으로 패딩된 배치의 최대 메모리를 보장하지 못했다. 배치 8이 이 GPU에서 언제나 불가능하다는 결론은 내리지 않는다. 이번 고정 메모리 조건에서는 미지원으로 기록했다.

또한 v1의 후반 블록에 다른 GPU 작업이 나타났다. 해당 프로세스를 중지하지 않았고 v1의 블록 시간을 최종 속도 비교에 사용하지 않는다. v1 결과는 보존하고 interrupted.json에 종료 이유와 각 조건의 완료 건수를 기록했다.

v2는 v1의 A/B/C 완료 검색만 이어받았다. 저장된 v5 지문, 검색·문맥 재생 함수의 AST, 나머지 실행 소스의 해시, 문항 순서와 하위 검색어 지문을 대조했다. 검색 구현이 그대로인 것을 확인한 뒤 각 조건의 남은 60문항을 실행했다. D는 이어서 실행하지 않았다. 결과적으로 A/B/C 모두 280문항·494개 검색이 끝났으며 기존 v5의 후보 순서와 최종 문맥이 전부 일치했다.

속도 비교는 이전 시간값을 이어받지 않고 v2에서 고정 15문항을 새로 반복한다. 2초 간격으로 GPU 사용량을 기록하고, 2,200MiB를 넘는 구간이 있으면 해당 회차를 제외하고 GPU 여유가 생긴 뒤 재측정한다. 이 기준은 다른 GPU 작업의 큰 메모리 점유를 발견하는 관측 규칙이며 전용 장비나 CPU 부하 격리를 보장하지 않는다. 상시 약 1.7GB 수준은 모델·드라이버 컨텍스트 등 전체 GPU 사용량으로, PyTorch의 약 978MiB 프로세스 할당 제한과 서로 다른 값이다.

## 코드와 검증 확인

실험 클래스의 BM25와 dense 검색은 공유 색인을 읽고 요청별 점수 배열을 만든다. CPU 임베딩과 GPU 리랭커에는 별도 잠금을 적용했다. SQL은 기존 조회 함수를 실제로 실행하며 응답 값·출처를 대조한다. 별도의 모델·검색 정책이나 불일치 시 묵시적 대체 경로는 추가하지 않았다. 6개 원본 검색과의 계측 동등성 검사도 다시 통과했다.

공통 Ruff와 실험 파일의 명시적 Ruff 검사, 포맷 검사가 통과했다. pytest는 공통 tests, 개인 실험 tests, TableRAG·workflow·speed 테스트를 함께 실행해 **514 passed, 15 subtests passed**였다. 검사는 GPU 대기로 지연 측정이 멈춘 동안 수행했고, 검사 직후 완료 지연 회차가 5개로 그대로인 것을 확인했다. CLI --help에서 run/report와 새 출력 경로, 선택적 --resume-from 인자를 확인했다. experimental은 패키징 범위 밖이고 패키징 파일은 바꾸지 않아 빌드는 추가하지 않았다.

재현 명령(저장소 루트):

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 MKL_NUM_THREADS=2 TOKENIZERS_PARALLELISM=false \
  .venv/bin/python -B -u -m experimental.u_10o0o.table_rag.speed run \
  --output artifacts/u_10o0o/advanced-table-rag-speed-20261111/v2 \
  --resume-from artifacts/u_10o0o/advanced-table-rag-speed-20261111/v1
.venv/bin/python -B -m experimental.u_10o0o.table_rag.speed report \
  --output artifacts/u_10o0o/advanced-table-rag-speed-20261111/v2
.venv/bin/python -B -m experimental.u_10o0o.records.advanced-table-rag-speed-20261111.analyze \
  artifacts/u_10o0o/advanced-table-rag-speed-20261111/v2
```

위 v2는 이번 실행 경로다. 새 재실행에는 사용하지 않은 다른 --output 경로를 지정한다. --resume-from은 이번처럼 메모리 오류로 중단된 동등성 검사에서 검증된 체크포인트를 잇는 용도이며, 지연 측정값은 이어받지 않는다. 처음부터 네 조건을 비교하려면 이 옵션을 생략한다. 동일 메모리 상한에서 배치 8은 다시 OOM이 날 수 있다.

## 완료 결과

v2의 18회 반복 측정이 완료됐고 runtime 지문 검사도 통과했다. 다른 GPU 작업과 겹친 1회차는 timing-excluded.json에 보존해 최종 집계에서 제외했다. A/B/C의 모든 반복 문맥도 각각 90/90(단일 45개 + 동시 45개)이 A의 문맥과 같았다. 문항별 차이 목록은 비어 있다. 배치 4의 점수 최대 차이는 약 2.384e-5이고 순위는 같았다.

기본 지연 표와 세부 분석은 실행 완료 후 report와 analyze 명령으로 만들었다. 상세 판단과 미검증 범위는 [결론](conclusion.md)에 기록했다. 공유 GPU의 영향을 받은 v1의 지연 분포는 summary.json의 품질 재생 계측에 남아 있을 수 있지만 속도 비교에는 사용하지 않는다. 최종 속도 판단은 analysis.json의 repeated_timing과 summary.json의 latency만 사용한다.

기준선과 운영 API는 그대로다. 새 실험 CLI·집중 테스트·실험 기록만 추가했고 모델 API 호출은 0회다.
