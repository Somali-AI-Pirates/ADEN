# Advanced 실험 코드·기록 종료 및 보존 목록

작성일: 2026-11-11

## 범위와 읽는 법

이 목록은 현재 작업 트리에서 확인된 **기존 Advanced 실험 코드와 기록**을 실험군별로 연결한다. 새 검색·모델 호출은 실행하지 않았고, 기존 보고서·결과·프로세스 기록만 읽었다. 이전 fresh A/B/C→D/E/F 비교와 TableRAG 연구 트랙은 이 목록의 결과 요약에서 제외했다. 옛 pattern-retrieval-v1은 별도 원본 실험이므로 포함했다. 이번 게시에서 추가 채택 결정을 내리지 않고, 작업 트리에 이미 반영된 코드 정규화 기본값과 그 근거를 함께 보존한다.

“완료”는 해당 비교를 실행하고 결과 보고서를 보존했다는 뜻이다. 기준선 채택이나 미사용 평가에서의 일반화가 확인됐다는 뜻은 아니다. 같은 질문 집합을 여러 번 사용한 수치는 각 보고서에서 개발·회귀 결과로 구분한다. 공개 연구와 제품 자료는 설계 배경이며, ADEN에서의 효과를 대신 증명하지 않는다. 각 실험의 전체 질문·원문·문항별 검색 trace는 해당 로컬 artifacts 경로에 보존돼 있다.

## 1. 원본 페이지·기록 단위·명시 관계 A/B/C

- **왜 했나:** PDF 원문 페이지를 그대로 검색할지, 사건 기록·표 행·문단으로 표현할지, 검증된 코드 관계로 관련 기록을 확장할지 같은 검색 모델·후보·리랭커 조건에서 분리해 보려 했다.
- **어디까지 완료했나:** 원본에서 다시 만든 검색 단위와 검증된 코드→사건→기록 관계로 개발·검증 각 60문항을 A/B/C로 실행하고, 각 세트의 일반 50문항을 채점했다. 단계별 결과·CPU 비교·검색 trace를 보존했다. 자동 검증과 CLI 실행도 보고서에 기록돼 있다.
- **중요 결과:** 검증 세트 최종 근거 충족은 A 50/50, B 47/50, C 49/50이었다. 개발은 A 48/50, B 43/50, C 46/50. B의 기록 단위화는 A보다 높지 않았고, C는 B보다 회복했지만 A를 넘지 못했다. 기본 검색으로 승격하지 않았다. 기존 평가 세트에서 새 A와 기존 기준선을 별도로 비교한 후속 시험에서는 공식 근거 충족이 A 18/58·기존 32/58, 카테고리 근거 충족이 A 127/200·기존 170/200으로 기존 기준선이 앞섰다.
- **한계:** 에이전트가 만든 소규모 세트가 같은 문서 양식에 의존한다. A 검증 50/50은 해당 질문에서의 관측값이며 실제 질문 전반의 일반화나 사람 검수를 뜻하지 않는다. A/B/C는 서로 데이터 단위 구성도 바뀌어 B/C 내부 변경 하나의 효과로 나눌 수 없다.
- **기록과 코드:** [A/B/C 보고서](../pattern-retrieval-v1-20261110/report.md) · [진행 로그](../pattern-retrieval-v1-20261110/process.md) · [실험 코드](../../pattern_retrieval/README.md) · [실험 계획과 레퍼런스](../../research/pattern-retrieval-fresh-20261110/plan.md#레퍼런스와-적용-경계) · [기존 A와 기준선 비교](../advanced-a-baseline-20261111/report.md)

## 2. IS 벡터 정제, SQLite 저장, Luna 해석과 IS 키 조회

- **왜 했나:** IS의 표·머리말 잡음이 벡터 검색을 방해하는지, 검증된 HG 사건·기록 관계와 표현 규칙을 SQLite로 옮길 때 기존 결과가 보존되는지, 질문 해석을 모델에 맡길 때 규칙 대비 실익이 있는지 확인했다. 별도로 IS의 원문에서 확인된 완전 기록 키를 구조 조회할 수 있는지도 점검했다.
- **어디까지 완료했나:** IS 입력 정제, HG 역할 연결·표현 규칙 SQLite 스냅샷 비교, 가짜 해석 응답의 분기 검사, GPT-6 Luna 질문 해석 비교, 24종 IS 키의 원문·SQL 조회 대조를 각각 실행했다. SQLite 동등성은 기존 메모리 조회와 220문항 모두에서 역할·순서·후보·최종 문맥 지문으로 확인했다. IS 키 인덱스의 22,523건은 출처 줄·행과 대조했다.
- **중요 결과:** IS 정제는 카테고리 최종 170/200을 바꾸지 않았고 일상 표현은 13/40에서 12/40으로 내려갔다. HG·규칙 SQLite 경로는 220문항에서 기존 실행과 같았고, 저장층 교체만의 품질 이득은 확인되지 않았다. Luna JSON 해석은 주 카테고리 최종 170/200으로 규칙과 같았으며 별도 30문항은 7/30→8/30이었다. 실제 응답 호출은 250회, API 지연 p95는 8.25초였다. 완전 IS 키 조회 추가는 공식 45/58에서 45/58로 같았다.
- **한계:** SQLite 역할 조회는 기존 대상 식별용 메모리 맵을 유지했고, 빠른 조회 측정만으로 운영 규모·동시성 이득을 주장할 수 없다. 가짜 응답 분기는 실제 모델 정확도를 평가하지 않는다. Luna 질문 해석의 미세한 30문항 차이는 채택 증거로 보기 어렵다. IS 조회는 확인된 전체 키 범위만 지원하며, 간접 의미 검색이나 표 전체의 이해를 증명하지 않는다.

## 3. IS 표 스키마 검색과 Luna 조건 조회

- **왜 했나:** IS에 반복되는 업무 표를 직접 찾고 원본 행과 연결한 뒤, 질문에서 검증 가능한 조건만 구조 조회하면 기존 페이지 검색이 놓치는 근거를 가져올 수 있는지 확인했다. 자유 SQL 대신 질문 계획을 제한된 필드로 받아 로컬 검증과 읽기 전용 SQLite 조회를 수행했다.
- **어디까지 완료했나:** 공식 60문항과 카테고리 220문항을 기존 결과와 대조했다. IS 파싱 행 27,715개를 190개 스키마로 구성하고 원본 페이지·행 범위 연결을 유지했다. Luna 계획 응답을 검증한 뒤 조회했으며 답변 생성은 하지 않았다.
- **중요 결과:** 전체 280문항의 후보와 최종 문맥 지문이 기존과 같았다. 공식 전체 근거는 45/58, 카테고리 정답 근거 보유 문항은 173/200으로 변화가 없었다. DB에서 찾은 5문항의 출처는 모두 기존 최종 8쪽에 이미 있었다. API 호출은 280회, p50 3.79초·p95 8.36초였으므로 이 실험에서는 검색 근거 개선 없이 추가 지연이 생겼다.
- **한계:** TableRAG 시스템 전체를 재현하지 않았으며 반복 추론·답변 생성·범용 SQL을 구현하지 않았다. 평가 세트의 표 기반 조회 적합성을 독립 검수하지 않았고 별도 미사용 검증도 없다. 5개 성공 조회는 기존 검색 문맥을 보완하지 못했으므로 이 결과로 표 질의 전반의 실패나 효과를 일반화할 수 없다.

## 4. HG 전용 조회, 전체 검색 복귀와 관계 확장

- **왜 했나:** AS057~AS120의 HG 사건 기록이 일반 BM25·벡터 색인에 들어 있는 것만으로 충분한지, 유일하게 확인된 사건은 SQLite 원문 관계를 따라 직접 조회하고 혼합·미확정 질문은 전체 검색으로 보내야 하는지 시험했다.
- **어디까지 완료했나:** 공식 60문항의 실제 Luna 도구 호출, 동료 304문항의 HG 분리 비교, 일반 5:5로 복귀하는 fallback 재채점, 검증된 관계를 이용한 추가 후보 확장을 보고서별로 실행했다.
- **중요 결과:** 공식에서 HG 분리·원문 조회는 32/58→43/58로 올랐고 HG 페이지를 인용한 묶음은 13/21→21/21이었다. 동료 304문항에서는 HG 분리만 쓰면 126/304→112/304로 떨어졌다. 확정되지 않거나 혼합된 질문을 전체 5:5로 복귀시킨 구성은 동료 전체 126/304를 회복했고 공식 43/58을 유지했다. 추가 그래프식 확장은 공식 43/58을 넘지 못하고 동료는 126/304→121/304, 절별 확장 설정은 109/304로 낮아졌다.
- **한계:** HG 분리 효과는 확인된 코드·역할 및 당시 공식 질문 범위에 한정된다. 동료 데이터에서는 HG 외 문서 근거를 잃는 사례가 있었고, fallback은 그 손실을 막기 위한 필수 경계로 드러났다. relation expansion은 전체 후보·최종 선택 정책과 결합된 특정 비교이지 전면 GraphRAG 평가가 아니다.

## 5. 질문 계획, 요청별 검색과 근거 보존

- **왜 했나:** 복합 질문에서 여러 대상과 기록 요청이 최종 8쪽에 함께 남지 않는 문제를 질문 계획·요청별 검색과 선택 단계에서 줄일 수 있는지 확인했다.
- **어디까지 완료했나:** 기존 기준선과 질문 계획 후 요청별 검색, 규칙 기반·병렬·순차 실행, 근거 역할 선택, 원질문 재리랭킹 ON/OFF, 기존 19개 일상 표현 실패의 첫 손실 단계, IS 벡터 창 후속 비교를 순서대로 기록했다. 마지막 단계에서는 기존 304·40문항 점수 재분석, 별도 24문항, 실제 API 포함 지연을 구분했다.
- **중요 결과:** 초기 요청별 검색 비교는 동료 304문항에서 126→151, 일상 표현 40문항에서 13→18로 관측됐다. 추가 질문 계획 API와 로컬 검색까지 포함한 p95는 3.87→11.05초, 별도 24문항 실제 비교에서는 기준선과 계획 검색 모두 19/24였고 p95는 2.62→6.63초였다. 새 24문항은 복합 질문 충족도 차이가 없어 기준선 교체 기준을 통과하지 못했다. 보존 실험에서는 요청40이 304문항에서 145, 일상40에서 19를 기록했지만, 최종 선택 ON/OFF는 동료에서 145→142, 일상에서 19→19, 별도 24에서 21→22로 일괄 제거 근거를 주지 않았다. IS 창 벡터 변경은 일상 최종 19/40→21/40이었으나 후보 완전 충족은 21/40 그대로였고, 두 근거 회복과 두 근거 유실이 함께 있었다.
- **한계:** 요청별 검색과 Luna 계획은 검색/API 호출량·지연을 늘린다. 기존 점수의 개선은 반복 사용한 세트의 개발 결과이며, 이후 별도 검증에서 같은 크기의 이득이 재현되지 않았다. 보관 세트의 라벨과 인용 일치 한계가 있어 각 실패를 전부 계획 오류나 최종 선택 오류라고 해석할 수 없다. IS 혼합 질문에서 규정 요청만 따로 검색한 4/6은 원인 진단이며 통합 문맥 성능 향상으로 계산하지 않는다.

## 6. 코드 표현, BM25 변형과 검색기 기여

- **왜 했나:** 검색 실패가 코드 표기 변형·부분 코드·토크나이저 차이 때문인지, BM25와 dense 벡터 중 어느 쪽이 근거를 찾고 어디서 후보가 잘리는지 확인했다. HG+IS 복합 질문에서 서로 다른 근거의 조회 흐름도 분리해 보았다.
- **어디까지 완료했나:** 완전 코드 정규화, Kiwi 보조 검색, 식별 정보의 대소문자·하이픈·공백 변형, BM25·벡터의 문항별 발견 여부와 이후 후보/최종 순위를 저장·재집계했다.
- **중요 결과:** 코드 표기 정규화는 공식 32/58·카테고리 170/200을 바꾸지 않았다. Snowflake 하이브리드에 Kiwi를 보조하면 공식 최종은 32→29였고, KURE-v3에서는 33/58 그대로였다. 검색기 기여 진단에서 일상 질문 정답 페이지 61쪽 중 BM25만 찾은 쪽 8, 벡터만 16, 둘 다 10, 둘 다 놓친 쪽 27이었다. 요청별 검색에서 후보 완전 충족은 21/40, 최종은 19/40이었다. 코드 표현 진단의 완전 코드·소문자·하이픈·공백 질문은 각각 24/24 최종 근거를 찾았지만, 그 결과는 BM25 직접 ID 일치가 주도했다. HG+IS 혼합 6문항에서 원질문은 IS 근거 1/6, 규정 절을 분리한 진단은 4/6이었다.
- **한계:** 직접 코드가 있는 질문의 성공은 간접 표현이나 사건 해석 능력을 보여주지 않는다. 완전 코드 정규화의 점수 변화가 없다고 모든 유사 표기/OCR 오류가 해결됐다고 할 수 없다. 규정 절 분리 결과는 최종 HG+IS 문맥을 한꺼번에 조립한 성능이 아니다.

## 7. 임베딩·리랭커·최종 페이지 수 비교

- **왜 했나:** 현재 Snowflake-ko+KURE nano 조합에서 임베딩 모델·리랭커·후보 폭·순위를 바꿨을 때 품질, 메모리, 지연의 실제 교환관계를 확인했다.
- **어디까지 완료했나:** Snowflake-ko 대 KURE-v3, KURE-v2 선택 정책과 입력 길이, 후보 20/40·범위 필터, Nemotron 대 KURE-v2, Top-k 절단, HG 역할 선택을 보고서와 지연 기록에 보존했다.
- **중요 결과:** KURE-v3 임베딩은 기존 Snowflake보다 공식 32→33/58, 카테고리 170→173/200, 일상 표현 13→15/40으로 소폭 상승했다. 대신 문서 재임베딩은 약 24.5분, 벡터 크기는 약 2배였다. KURE-v2에 범위 필터+후보40을 더하면 category 173→176/200, 일상 15→18/40, 공식은 36/58로 같았고 p95는 base20 약 274ms에서 약 786ms였다. Nemotron 범위 필터+40은 일상 21/40·카테고리 179/200이었지만 공식 34/58이었고, 당시 장치 설정의 p95는 약 2.27초였다. KURE-v3와 HG 날짜 조회·역할 선택 조합은 공식 33→45/58, 카테고리 173/200 그대로였다.
- **한계:** 표본과 기준선이 다른 개별 KURE 실험 수치를 하나의 연속 순위표로 합치지 않는다. GPU 구성, 문서 벡터 준비와 실제 요청 지연의 범위가 다르다. 기존 평가를 반복 사용했으며, 모델별로 동일한 운영 트래픽이나 미사용 검증에서 일반화한 결과가 아니다. 품질 개선을 유료 답변 품질이나 end-to-end 시스템 결과로 옮겨 해석하지 않는다.

## 8. bigram-id-normalized 기준 업데이트와 공식 누락 위치

- **왜 했나:** Kiwi를 사용한 검색기에서 Bigram과 완전 식별자 토큰을 분리·결합하는 변경이 식별자와 일상 표현을 모두 해치지 않는지, 제목 보너스 및 원문 페이지 단위 기준선이 유지되어야 하는지 확인했다.
- **어디까지 완료했나:** 코드 정규화 비교, 기존 기준선의 공식 누락 위치 재집계, 완전 ID Bigram-ID의 기본 실행 기록과 공식 누락 위치 재집계를 완료했다.
- **중요 결과:** 현재 개인 Advanced 기준선 이름은 bigram-id-normalized이며, 제목 보너스를 적용한다. 공식 채점 대상은 32/58, 카테고리 유효 질문은 170/200이었다. 공식 실패 근거 36쪽을 순위로 재구성했을 때 BM25·벡터 모두 Top20 밖 18쪽, 한쪽 Top20에는 있었으나 RRF20 밖 3쪽, 후보에는 있으나 최종 8쪽 밖 15쪽이었다.
- **한계:** BM25 완전 코드 표기 정규화 자체는 0/280 문항의 최종 충족을 바꾸지 않았다. 초기 조건이 다른 보고서를 기본값 교체 근거로 취급하지 않는다.
- **기록과 코드:** [정규화 BM25 기준선·누락 진단](../advanced-normalized-baseline-20261111/report.md) · [완전 ID 표기 정규화](../advanced-bm25-code-normalization-20261111/report.md) · [기본 실행 안내](../../README.md#현재-advanced-구성) · [기록 선택 기준](../decisions.md)
