# 최종 답변 프롬프트·보류 사유 보완 결과

2026-11-13. **검색은 유지하고 최종 답변 지침·충돌 전달·사용자용 판단 이유를 보완했다. 공식 60문항에서는 문맥 충실도는 높아졌으나 종합 답변 품질의 우위는 확인하지 못했다.** 경계 질문에서는 지원 범위 안내와 구체적인 보류 이유가 개선됐다. 점수가 낮아진 최초 보완안과 후속 조건도 모두 보존했다.

현재 로컬 코드는 아래 D다. 실험 종료 후 사용자가 로컬 커밋과 Notion 기록을 요청했으며 분리 검증은 [커밋 인계 기록](commit-handoff.md)에 남긴다. 운영 배포·푸시는 하지 않았다. 이 구현을 ‘기존보다 정확도가 높아진 운영 확정본’으로 발표하면 안 된다.

## 1. 무엇을 바꿨나

- 해운 Advanced의 예약·서류·운송·계약·비용·정산을 지원 범위로 명시했다. 일반적인 질문은 존댓말로 간결하게 답하고 실제 취소·메일·송금·실시간 조회를 수행했다고 말하지 않도록 했다.
- 적용 대상·기준 시각·정정 효력, 요청과 승인, 권한자와 실제 서명자, 미결과 0, 청구 기재액과 독립 검산을 구분했다.
- 확인된 부분은 출처와 함께 답하고, 빠진 항목·충돌·보류 이유는 구체적으로 설명하도록 했다. 기존 HTTP/SSE의 `reason`을 고정 문구 대신 모델의 업무상 설명으로 채운다.
- 검색 단계의 충돌 항목·종료 사유를 별도 전달한다. **자유 서술 검색 요약은 최종 원문에 없는 사실을 유입시킬 수 있어 답변 입력에서 제외**했다. 원래 요약은 사후 진단 기록에만 남긴다.
- 인사·업무 외·혼합 질문·욕설·실행 요청·문서 주입·이전 답변의 잘못된 값에 대한 경계를 명시했다. 원래 검색 상태를 더 확정적인 상태로 올리지 못하는 코드 검증은 유지했다.

수정 파일과 호환 경계는 [구현 검토](implementation-review.md)에 정리했다. 제품의 기준 프롬프트는 [answer.txt](../../../../app/rag/prompts/answer.txt)이며, 기존 B/C 평가의 다른 프롬프트와 구분한다.

## 2. 비교 설계와 진행

공식 개발 30 + 추가 확인 30 = **60문항 전체**를 실행했다. 57개로 줄이거나 실패 문항을 제외하지 않았다. 추가로 합성 최종 문맥을 가진 경계 질문 20개를 사용했다.

| 조건 | 답변 단계의 변경 | 실행 수 |
| --- | --- | ---: |
| A 기존 | 기존 지침·세 필드 출력·고정 사유 | 80 |
| B 최초 보완 | 상세 지침 + 검색 요약·충돌 + 모델 사유 | 80 |
| C 지침 보완 | B + 부가 설명 억제·날짜 추정 금지·업무 종류 확인·주장별 인용 | 80 |
| D 최종 | C에서 자유 서술 검색 요약 전달 제거, 충돌·종료 사유만 유지 | 80 |

공식 문항마다 현행 제품 그래프를 한 번 실행해 후보·최종 원문·SQL·상태를 저장했다. **80개 입력에서 네 조건이 실제 모델에 보낸 근거가 모두 같음을 대조했다.** 그래프·검색기·근거 조립·검색 계획 지침·기록 DB·SQL 저장소·검색 정책 7개 파일의 작업 전후 지문도 모두 일치했다. 답변 입력의 지침과 진단은 비교 대상이므로 다르다.

KURE-v3·KURE nano·Luna medium, DB 우선, 현행 Qdrant exact·5:5 하이브리드, 후보 20쪽·최종 최대 8쪽·8,000토큰을 유지했다. 참고답은 검색·생성 후 Judge에만 사용했다. Ragas에는 실제 최종 원문·SQL과 저장 답변·이유만 넣었다. 원격 Langfuse에는 게시하지 않았다.

B의 회귀를 본 뒤 C를 추가했고, C에서도 자유 서술 요약의 사실 유입을 확인해 D를 추가했다. 따라서 C/D는 **동일 공개 세트에서의 개발·회귀 확인**이며 미사용 검증이 아니다. 조건당 생성은 1회, 자동 재시도는 없었다. 모델·설정·데이터·코드 지문은 [provenance.json](provenance.json), 변경 시점과 근거는 [protocol.md](protocol.md)에 있다.

## 3. 공식 60문항 결과

Judge는 Luna low의 사실·조건·근거·판단 4축 이진 판정이다. 아래는 수정하지 않은 원점수다. Ragas 0.4.3 Faithfulness도 Luna low로 별도 실행했다.

| 지표 | A 기존 | B 최초 보완 | C 지침 보완 | D 최종 |
| --- | ---: | ---: | ---: | ---: |
| 사실 | 51/60 · 85.0% | 48/60 · 80.0% | 51/60 · 85.0% | 48/60 · 80.0% |
| 조건 | 58/60 · 96.7% | 56/60 · 93.3% | 59/60 · 98.3% | 58/60 · 96.7% |
| 근거 | 55/59 · 93.2% | 53/60 · 88.3% | 57/60 · 95.0% | 54/59 · 91.5% |
| 판단 | 60/60 · 100.0% | 58/60 · 96.7% | 58/60 · 96.7% | 56/60 · 93.3% |
| Ragas Faithfulness 평균 | 0.796 | 0.869 | 0.877 | 0.864 |

A/D의 근거는 각 1개가 해당 없음이다. 공식 문항의 채점 불가·생성 오류는 네 조건 모두 0개다. Ragas는 각 60개가 채점됐다. ‘근거’는 답변의 중요한 주장을 실제 인용이 뒷받침하는지의 Judge 점수이며 검색 Recall이나 전체 근거 충족률이 아니다.

D의 개발/추가 확인 사실 점수는 각각 24/30, 24/30이다. Ragas는 각각 0.873, 0.856이다. 상세 분모·상태·지연과 전체 조건은 [summary.json](summary.json), 문항별 점수·변화는 [per-question.json](per-question.json)에 보존했다.

**해석:** 문맥에 기대어 설명하는 정도와 사유 구체화에는 개선 신호가 있지만, 필요한 업무 항목을 모두 답하는 능력까지 좋아졌다는 근거는 없다. C의 자동 점수가 더 높아도 원문 밖의 계산 날짜를 검색 요약에서 가져온 경로를 그대로 채택하지 않았다. D는 이 입력 경계를 줄인 구현 선택이지 최고 점수를 얻은 프롬프트의 선정이 아니다.

## 4. 실제 차이와 평가 오류

- `AS-ADD23`: 최초 산입일과 최초 유료일을 구분해 A의 표현 오류를 회복했다.
- `AS-DEV13`: B/C가 최종 원문에 없는 달력 기간을 검색 요약에서 가져왔다. D는 이 날짜를 확인할 수 없다고 밝혔다. 다만 청구액·요율에서 유료일수를 역산하는 문제가 남아 있어 전체 계산 검증 성공으로 집계하지 않는다.
- `AS-DEV02·06`: 최종 문맥에 없는 신규 제출 창구를 확정하지 않았다. 부분 보류는 근거 충실성 측면에서 타당할 수 있지만 원래 정답의 필수 항목은 여전히 채우지 못했다.
- `AS-DEV12`: 대상뿐 아니라 업무 종류까지 물어야 하는데 이를 안정적으로 수행하지 못했다.
- `AS-ADD08`: 실제 인용을 확인하면 주장이 뒷받침되고 Judge의 설명도 그렇게 적었지만 점수는 0이었다. `AS-DEV14·30`에서도 질문 밖 문구를 다시 적지 않았다는 감점 등 불일치가 있었다.

자동 채점 오류를 근거로 모든 하락을 무시하지 않았다. 반대로 점수를 올리기 위해 없는 창구·날짜를 추측하도록 바꾸지도 않았다. **실제 누락·근거 부족·자동 판정 불일치를 분리한 [문항별 검토](case-review.md)**를 다음 검수의 출발점으로 삼아야 한다. 원점수 교정이나 독립 사람 검수는 하지 않았다.

## 5. 경계 질문 20개

인사·사용법·업무 외·혼합 질문·욕설·실제 업무 실행 요구, 부분 답변·충돌·효력 시점, 권한자/서명자, 미결/0, SQL 미리보기, 정상 범위 제한, 사용자/문서 주입, 이전 답변·진단 오염을 확인했다.

| 항목 | 기존 A | 최종 D |
| --- | --- | --- |
| 자동 Judge 판단 | 18/20 | 19/19, **1개 평가 불가** |
| 생성·출력 검증 오류 | 0/20 | 0/20 |
| 지원 범위 질문 | 자료가 없다는 이유로 기능 설명도 보류 | 해운 문서 확인·안내 범위 소개 |
| 모호한 완료 질문 | 대상 식별만 질문 | 대상과 확인할 업무 단계 함께 질문 |
| 부분 답변·충돌 | 본문은 설명하나 reason은 고정 문구 | 확인된 값·보류 항목·판단 이유를 연결 |
| 금액 조작·문서 명령·이전 답변 오염 | 원문 값을 유지 | 원문 값을 유지 |
| 실제 메일·송금 요구 | 실행했다고 주장하지 않음 | 실행 불가와 가능한 안내를 구분 |

D의 `EDGE-02`는 Judge가 `not_applicable`과 숫자 점수를 동시에 반환해 스키마 검증에 실패했다. 원래 응답은 저장되어 있으며 재시도하지 않았다. 이 문항의 Ragas도 사실 주장 여부가 확정되지 않고 문맥이 비어 평가 불가다. 이를 100% 성공으로 표시하지 않는다.

Ragas 경계 평균은 A 0.657(16개), D 0.620(18개)이다. 서비스 기능 소개나 지원 범위 안내는 시스템 지침의 내용이고 PDF 근거가 없는 경우도 있어 이 평균을 업무 사실 질문과 합치지 않는다. 단순 공격을 두 조건 모두 무시한 결과를 새 방어의 추가 효과로 계산하지 않는다. 실제 비밀키를 문맥에 넣은 시험이나 정식 공격 데이터 전체 재평가는 수행하지 않았다.

## 6. 호출·지연·실행 비용

| 공식 60문항 답변 단계 | A 기존 | D 최종 |

검색을 다시 실행한 시간이 아니라 **동결 근거로 답변을 생성·검증한 구간**이다. 조건당 생성 동시성 3, 평가 동시성 4이며 일부 평가는 생성과 다른 외부 호출을 함께 실행했다. 실행 시각과 서버 부하가 같지 않고 반복도 없어 지연 차이를 프롬프트 길이 하나의 효과로 단정하지 않는다.

전체 실행은 검색 계획 118회 + 본 비교 답변 320회 + Judge 320회 + Ragas 내부 호출 592회, 별도 연결 시험 답변 2회다. 총 **1,352회**의 API 요청을 기록했다. 사용자 승인한 기존 키·비용 상한 없음 조건을 사용했다. 사용량은 로컬에 저장했으며 검증한 과금 단가가 없어 달러 비용을 추정하거나 0으로 쓰지 않았다. 최초 Judge 시험은 저장 후 화면용 집계 키 오류가 났으나 채점 파일을 재사용해 추가 호출하지 않았다.

## 7. 검증과 완료 범위

- Ruff 공통 검사·개인 실험 스크립트 검사 통과.
- 전체 pytest **695개 + 하위 검사 11개 통과**, Qdrant 로컬 테스트 경고 1개.
- lock 검사, 실험 CLI 도움말, 패키지 빌드 통과. 휠에 최종 프롬프트와 변경 제품 코드가 현재 파일 그대로 포함됨을 확인.
- 실제 답변 320개 모두 생성·상태·출처 ID 검증 성공. 80개 질문의 근거·후보·문맥 지문이 네 조건에서 동일함을 확인.
- 단계별 로그, 지문, 이전 지침·실행 코드, 동결 근거·원문·답변·평가를 보존했다. 민감한 원문과 답변 전문은 `artifacts/u_10o0o/advanced-answer-policy-20261113/`에만 있다.
- 독립 에이전트 사용이 허용되지 않은 사이드 대화이므로 자체 리뷰만 했다. 사람 검수·운영 배포·원격 trace 확인은 완료 범위가 아니다.

상세 명령과 남은 범위는 [검증 기록](verification.md)을 참조한다.
