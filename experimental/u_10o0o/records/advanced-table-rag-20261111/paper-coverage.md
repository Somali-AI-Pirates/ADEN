# TableRAG 논문과 이번 구현의 대응

기준 자료: [TableRAG, EMNLP 2025](https://aclanthology.org/2025.emnlp-main.710.pdf), [저자 공개 코드](https://github.com/yxh-y/TableRAG). 논문 §3.2·§3.3와 Appendix C/G의 구성 요소를 현재 실험 코드에 대조했다.

| 논문에서 다루는 부분 | 이번 구현 | 확인 방법과 경계 |
|---|---|---|
| 문서와 표 내용을 검색 단위로 구성 | 원본 18,000쪽에 IS Markdown 표 3,750개를 추가 | 설명·열 이름만 임베딩한 이전 실험과 다르다. HG/HA는 원본 페이지 검색에서 표로 연결한다. |
| 검색된 표 내용에서 원본 표·스키마로 이동 | 표 ID와 원본 book_id/page/행 범위 연결. 페이지가 검색돼도 해당 물리 표의 스키마를 찾는다 | 원본 표는 페이지·절·열 순서·행 사이의 내용으로 구분한다. 같은 열 이름만으로 여러 페이지를 합치지 않는다. |
| 테이블명·열 이름·타입·예시 제공 | 실제 표 제목·절·열 이름과 최대 3개의 원문 예시, 검증 가능한 날짜/소수/단위/상태 보조 열 | 복합 셀을 억지로 숫자나 날짜 하나로 바꾸지 않는다. 불명확하면 원문 TEXT와 NULL을 유지한다. |
| 관계형 저장소에서 전체 표 연산 | 21,126개 물리 표, 100,889개 원본 행을 SQLite에 저장. 관측된 표에만 SELECT/WITH 실행 | 전체 표에서 집계한 뒤 결과 미리보기를 제한한다. 최종 8쪽 제한을 SQL 입력 8행 제한으로 오해하지 않는다. |
| 필요할 때 질문 분해 | Luna가 초기 근거를 보고 solve_subquery 또는 finish 선택 | 단일 표의 조건·집계는 불필요하게 분해하지 않도록 지시했다. 분해 개수는 실제 선택이며 고정하지 않는다. |
| 하위 질문별 검색과 리랭킹 | 요청된 하위 질문마다 실제 5:5 검색·KURE 실행 | 결과를 합친 뒤 원질문으로 다시 리랭킹하지 않는다. 서로 다른 요청의 후보는 순환 순서로 최대 20쪽을 남긴다. |
| 앞선 결과를 이용한 다음 질문 | 도구 결과의 원문 발췌·실제 스키마·SQL 값·오류를 다음 Responses 호출에 반환 | 앞에서 확인된 식별자나 수치를 다음 질문에서 사용할 수 있다. 가상 의존 질문 테스트와 실제 함수 호출 점검을 수행했다. |
| SQL 생성·조건·정렬·집계·조인 | LLM이 스키마에 맞는 읽기 SQL을 제안하고 Python/SQLite가 실행 | 날짜 종류, 비용 종류, 통화와 상태를 구분하도록 지시한다. Decimal 연산 함수와 실행 시간 제한을 적용했다. SQL 실행 성공이 의미 정확도를 보장하지 않는다. |
| 중간 근거 종합과 상충 확인 | 매 다음 계획 호출에서 문서/SQL 결과와 이전의 짧은 사실 요약을 읽고 다음 작업 결정 | 별도의 검증 모델을 하나 더 호출한 구조는 아니다. 같은 계획 호출에 대조 지침이 있으며 검증 의미 정확도는 보장하지 않는다. |
| 빈 결과·오류 이후 진행 | SQL 오류/빈 결과를 그대로 반환해 다시 조회하거나 문서 근거로 종료 | 읽기 범위 위반·출처 없는 상수 SELECT·중복 결과 열 이름은 오류로 반환한다. |
| 반복 종료 | finish의 sufficient / needs_clarification / insufficient, 최대 5회 도구 실행 | 무한 반복하지 않는다. 모델 시간 초과는 저장하고 현재 검색 결과를 남긴다. |
| 최종 답변 평가 | 양쪽 최종 문맥으로 별도 새 답변 생성, 이후 가린 X/Y 순서로 모델 채점 | 계획자가 본 모든 자료를 최종 답변에 몰래 전달하지 않는다. 같은 최대 8쪽·8,000토큰을 적용한다. 사람 검수와 구분한다. |

## 실행 흐름

질문 → 원본/표 하이브리드 검색 → Luna 판단 → 필요한 하위 질문의 검색 및 SQL → 그 결과를 Luna에 반환 → 후속 조회 또는 종료 → 최대 8쪽·8,000토큰으로 근거 조립 → 별도 답변 생성.

평가 참고 정답은 위 흐름에 들어가지 않는다. 280문항의 검색·답변을 모두 저장한 뒤에만 채점 단계에서 연다.

실제 도구 이름은 solve_subquery와 finish다. solve_subquery 안에서 Python이 검색과 SQLite 조회를 실행한다. 따라서 이전처럼 LLM이 JSON 계획만 내고 DB 결과를 전혀 받지 않는 구조가 아니다.

## 논문 재현과 구분할 부분

이 구현은 논문의 검색·표 매핑·조건부 분해·SQL·피드백 흐름을 프로젝트에 적용한 것이다. 논문 자체의 모델, 평가 데이터와 점수를 그대로 재현한 실험은 아니다. MySQL 대신 읽기 전용 SQLite를 사용하며, 한국어 코드 보존 BM25·KURE-v3·KURE nano·기존 HG 원본 조회를 유지한다.

정해진 최종 8쪽 안에 모든 원본 출처가 남지 않는 SQL 결과는 답변 근거에서 제외한다. 따라서 많은 페이지에 흩어진 전체 모집단 집계를 언제나 완수한다고 주장하지 않는다. 표를 의미별로 자동 합치거나 조인 키의 의미를 사람이 검수한 것도 아니다.

독립 질문 계획 정답이 없어 “분해 정확도”라는 숫자는 만들지 않는다. 대신 저장된 요청·호출·SQL·출처 흐름, 후보와 최종 근거 충족, 실제 답변의 별도 모델 채점을 구분해서 제시한다. 원문 셀·산술 대조 30건과 집중 테스트는 구현 정확성 검사이며 자연어 질문 전체의 정답률을 대신하지 않는다.

최종 결과와 지연은 [비교 보고서](report.md), [호출 기록](telemetry.json), [로컬 지연](timing.json)에서 확인한다. 검증 결과는 [verification.json](verification.json)에 있다.
