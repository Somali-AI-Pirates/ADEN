# TableRAG 누락 보완 재실험

2026-11-11. 사용자는 논문 대조에서 확인한 누락을 모두 구현하고 재실험하도록 요청했다.

## 범위 계약

기존 KURE-v3 5:5 + 개선 HG 조회를 대조군으로 보존한다. 원본 표 경계, 표 본문과 스키마 연결, 실제 값 예시·자료형, 조건부 질문 분해, 하위 질문별 검색·리랭킹, SELECT SQL 연산, SQL/문서 결과의 모델 피드백과 중간 결과 종합, 종료 판단을 새 개인 실험에 구현한다. 마지막 답변과 표 연산도 검사하여 페이지 Recall과 구분한다. 이전 1회 표 설명 조회 결과와 기본 advanced_search/운영 API/공유 스냅샷은 수정하지 않는다. 신규 실행 경로는 table_rag 패키지다.

원본 물리 표는 source_id·section·열 순서·행 위치의 연속성으로 구분한다. 다른 페이지나 절을 묵시적으로 합치지 않는다. 동일 양식을 전체 범위에서 조회할 경우에도 범위를 명시한 UNION으로 처리한다. 원문 문자열은 보존하고 수치·날짜·단위·상태를 검증 가능한 보조 열로 제공한다. 셀에 여러 값이 있거나 상태가 불확실하면 숫자를 임의 채우지 않는다. 출처 없는 값은 생성하지 않는다.

기존 18,000쪽 페이지 임베딩은 그대로 재사용한다. 이번 수정 대상인 IS의 Markdown 표 본문은 새 검색 단위로 임베딩하고 페이지/표/스키마를 연결한다. HG·HA를 포함한 파싱 완료 표는 동일 읽기 전용 SQL 저장소에 원본 경계대로 보존하고, 기존 원본 페이지 검색에서 연결 가능하게 한다. 이 검색 표현 차이는 보고서에 명시한다.

LLM은 GPT-6 Luna medium으로 고정한다. 기존 키 사용·예산 무제한·필요한 추론 강도 상향 승인은 유지한다. 이번 명시 요청에 따라 질문뿐 아니라 선택된 원문 발췌·표 예시·조회값을 제공한다. 평가 정답은 모든 검색/답변 완료 후 채점에만 사용한다. 공개 기록에는 원문·질문·정답·실제 셀값·비밀키를 넣지 않는다.

최대 5회의 하위 질문 도구 실행과 종료 판단을 둔다. SQL은 허용된 원본 표에 대한 읽기 전용 SELECT만 실행하고 실행 시간/연산량 상한을 둔다. DB 연산은 최종 8쪽과 별도로 전체 해당 표를 대상으로 한다. 결과 미리보기의 잘림은 표시하며 집계는 미리보기 전에 수행한다. SQL 오류·빈 결과는 모델에 반환해 다음 질문을 판단하게 한다. 도구 밖 쓰기·파일/네트워크 접근·확장 로딩은 불가하다.

각 검색 호출 후보 20개, 합친 최종 페이지 후보 20쪽, 최종 문맥 최대 8쪽·8,000토큰을 적용한다. 내부 검색을 여러 번 하기 때문에 전체 처리량이 대조군과 같다고 주장하지 않는다. 최종 답변은 양쪽 모두 동일한 새 호출과 같은 최종 예산으로 생성하고 채점한다. 내부 중간 요약은 별도로 남긴다.

검증은 기존 공식 60 + 카테고리 220, 별도 합성 SQL·의존 질문 분해·종료·출처 테스트를 사용한다. 기존 평가 세트의 점수를 본 뒤 규칙/프롬프트를 조정하지 않는다. 초도 실행 점검은 형식·출처·SQL/루프 연결만 확인한다. 모든 결과를 저장한 후 채점한다. 독립 에이전트는 부대 대화에서 금지되어 자체 검토한다. 커밋·푸시·기준선 승격은 하지 않는다.

## 구현·초도 검증

- v1/v2는 API 평가 이전의 표 경계 검증 시도다. v2에서 전체 물리 행 문자열로 다중 줄 셀을 검증하면 열이 서로 섞여 IS 셀이 잘못 탈락하는 문제를 발견했다. 원본 열 좌표를 재파싱해 값·행 범위를 대조하도록 수정한 v3를 평가용으로 사용한다. 초도 산출물은 보존하며 품질 비교에 넣지 않는다.
- v3는 원본 120개 PDF의 해시를 확인했다. 물리 표 21,126개, 원본 행 100,889개를 적재했고 원본 재파싱·DB 왕복 대조에서 탈락한 행은 0개다. IS Markdown 검색 단위는 3,750개다. 원본 값 17,357개는 날짜, 37,689개는 단일 소수 값으로 확인됐고 나머지는 원문 문자열을 유지한다.
- HG·HA·IS에서 각각 10개 표를 ID 해시 순으로 골라 원래 record_fields 셀에서 별도 계산한 기대값과 SQL 결과를 대조했다. 값·단위·집계 30/30 통과. 이 검사는 자연어 질문을 SQL로 바꾸는 모델의 의미 정확도 검사가 아니다.
- 실제 GPT-6 Luna medium에 가상 원장 100행의 합계를 물었다. solve_subquery 함수 호출 → 전체 표 SQL 실행 → 함수 결과 반환 → finish의 2회 API 흐름을 확인했다. 100건·USD 505.0이 일치했다. 실제 평가 정답을 사용하지 않은 연결 점검이다.
- 집중 테스트는 SQL 집계·조인·CTE·UNION·읽기 제한·시간 제한·출처·표 경계·소수/날짜/미결·후속 질문·오류 피드백·종료·토큰/쪽 예산을 포함한다.
- 별도 모델 실험이 GPU를 사용 중이라 해당 프로세스는 건드리지 않았다. 새 표 임베딩은 GPU 메모리 사용 비율 0.22와 GPU 가중치 1,000MiB로 제한한 GPU/CPU 분산 실행, 배치 1·CPU 스레드 2를 사용한다. accelerate/psutil은 /tmp 별도 경로에 설치했고 공유 .venv는 수정하지 않았다.
- 부대 대화의 에이전트 사용 금지에 따라 implementation-final-review는 자체 검토로 수행한다. code-change-verification의 저장소 Ruff/pytest와 개인 실험 검사를 따로 실행한다. 공통 검사는 experimental을 포함하지 않으므로 별도 경로의 검증 결과를 구분한다.

## 평가 조건 고정 전 최종 점검

기존 완전 코드 보존 토크나이저와 제목 보너스 0.25를 새 표 본문 색인에도 유지했다. 새 경로는 sparse/dense 각각 50개 → 5:5 RRF(k=60) → 20개 전체 리랭킹이다. 대조군의 후보 폭·Top 3 보존 정책과는 차이가 있으므로 최종 보고서에서 단일 기능의 인과 효과라고 해석하지 않는다. 두 경로의 최종 페이지/토큰 예산은 동일하다.

초도 SQL 결과의 중복 열 이름이 값을 덮어쓸 수 있는 부분은 별칭을 요구하도록 막았고, 원본 표를 전혀 읽지 않는 상수 SELECT는 근거 조회로 인정하지 않는다. 너무 큰 스키마는 이름/값을 임의 잘라 전달하지 않고 해당 턴에서 제외한다.

공통 pytest 284개 + subtest 15개가 통과했다. 개인 기존 테스트 182개와 신규 20개를 함께 실행해 202개 통과했으며, 이후 재개/정답 접근 차단 검사 2개를 더해 신규 집중 검사는 22개 통과했다. Ruff 공통 검사·개인 명시 검사·개인 format check도 통과했다. Python 패키지 배포 대상은 변경하지 않았다.

IS 임베딩과 독립적인 기준선 답변 생성은 동시에 진행했다. 이 선행 답변도 입력/문맥/모델/프롬프트 지문으로 확인한 뒤 재사용한다. 모델 API의 실패는 저장하며 자동 재시도하지 않는다. 500 오류를 점수 실패나 성공과 혼동하지 않고 호출 실패로 별도 집계한다.

원문 페이지와 그 페이지의 Markdown 표가 서로 다른 검색 단위로 나오더라도 후보 쪽 수는 한 번만 센다. RRF 순위에서 페이지별 최고 단위를 먼저 고른 뒤 최대 20개만 리랭킹한다. 이 중복 제거를 추가한 집중 테스트까지 신규 검사는 23개다. 최종 8쪽 문맥과 SQL 출처/토큰 예산 검사는 동일하게 유지한다.

원본 스냅샷의 표로 파싱된 100,889행만 관계형 표로 적재한다. 서술형 26,633블록, 외부 인용 2블록 등은 원본 페이지에서 계속 검색한다. 모든 PDF 표를 사람이 독립 검출/검수했다는 뜻은 아니다.

공식/카테고리의 참고 정답을 열기 전에 검색·답변 출력을 모두 저장한다. 답변 모델 채점은 두 조건 모두 판정 가능한 공통 문항을 같은 분모로 집계하고, API 실패·판정 불가를 따로 남긴다. 선행 기준선 답변은 280건 저장됐으며 279건 완료, 1건 InternalServerError였다. 이 실패도 그대로 보존한다.

## 본 평가 실행 환경 변경: v4

v3의 실제 연결 점검에서는 CPU 리랭킹 검색이 대략 12초 이상 걸렸다. 정답이나 점수를 읽기 전에 같은 KURE nano float32로 가상 문서 20쌍을 CPU/GPU 비교했다. GPU 1.09초, CPU 19.78초, 최대 점수 차이 0.00000668, 순위 일치였다. GPU 최대 할당은 약 647MiB였다. 처음 GPU 예산을 너무 작게 준 점검은 메모리 한도 오류로 종료됐으며 다른 프로세스에는 신호를 보내지 않았다.

본 평가 경로는 v4다. 질문 임베딩은 CPU bfloat16·2스레드, 리랭킹은 GPU float32·배치 1·프로세스 GPU 예산 비율 0.12로 고정한다. 벡터 색인·질문·스냅샷·프롬프트·추론 강도·검색 조건은 그대로 사용한다. v3의 완료/진행 결과와 API 체크포인트는 보존했고 부대 실험 프로세스만 중단했다. v3는 품질 집계에 넣지 않는다. 중단 시 진행 중이던 호출의 실제 과금은 응답 로그만으로 확정하지 않는다.

v4는 GPU 조건으로 280문항을 처음부터 실행한다. 기준선 답변 280건은 동일 질문·문맥·모델·프롬프트 지문을 확인해 재사용한다. v3의 새로운 경로 답변/검색 결과는 재사용하지 않는다. 기존 별도 임베딩 실험 프로세스나 공유 .venv는 변경하지 않았다.

## 최종 기준선 정합성 보완: v5

v4의 검색·답변 280개를 모두 저장한 뒤, 품질 채점 전에 선택한 기준선과 HG 조회 함수의 차이를 확인했다. 공통 complete_sources에는 이전에 채택한 두 날짜의 역할·규격 생략 처리가 포함되지 않았다. 기존 date_target 규칙을 그대로 새 패키지의 hg.py에 두고, 해당 조건에서만 원본 연결을 적용했다. 새로운 평가 정답에 맞춘 규칙을 추가한 것은 아니다.

기준선의 저장된 후보/리랭킹 점수를 같은 HG 함수에 넣었을 때 순위와 최종 문맥이 280/280 같았다. 날짜 보완은 14문항에서 필요했다. v4의 원질문과 모든 후속 질문을 검사해 영향을 받는 14문항은 v5에서 재실행했다. 나머지 266문항은 해당 분기가 모든 검색에서 거짓이며 나머지 검색 함수가 같음을 확인하고 출력 파일 해시와 함께 재사용했다. v4의 별도 품질 점수는 확인하지 않았다. proof와 전체 출력 지문을 고정한 후 v5만 채점했다.

완료된 실행 코드 77개는 executed-code에 원래 상대 경로로 복사하고 원래 해시와 전부 대조했다. protocol.executed.json과 run.executed.json도 보존했다. 현재 protocol의 runtime_files는 같은 SHA의 보존 코드로 연결하고 original_path를 남겼다. 검색 결과·답변 파일은 수정하지 않았다. 이는 보고서의 상대 경로 처리, 로컬 지연의 문맥 비교, 표 서식을 고치기 위한 사후 처리 분리다. 실행 전후 지문과 현재 보고서 생성 코드 지문을 각각 남긴다.

## 결과와 남은 실패

공식 입력은 60문항이며 근거 채점 대상 58개에서 최종 전체 근거 충족이 45→50개로 늘었다. 카테고리 입력은 220문항이며 음성 대조 20개를 제외한 200개에서 173→183개다. 일상 표현 40개는 15→25개다. 전체 개선은 16문항, 하락은 AS-SEM-37 한 문항이다. 업무 규정 최종 충족은 18/20으로 같지만 후보 충족은 19→18로 낮아졌다.

모든 후속 검색의 합집합과 최종 후보를 나눠 점검했다. 채점 대상 258개 중 233개는 최종 충족했다. 남은 25개는 전체 검색에도 근거가 없는 19개와 후보 20쪽 통합에서 잃은 6개다. 후보가 모두 충분한데 최종 8쪽에서만 잃은 문항은 없다. AS-SEM-37은 조회 합집합 64쪽에는 근거가 있지만 통합 후보 20쪽에서 빠진 경우다. 결과를 본 뒤 후보 결합·프롬프트·검색 규칙을 다시 조정하지 않았다.

계획 API는 503회, 실제 검색은 494회, SQL은 27회(정상 26회, 오류 1회)였다. SQL 근거는 26문항의 최종 문맥에 들어갔다. 계획 API p50/p95는 3.44/5.12초, 전체 검색 관측값은 8.88/26.74초다. 공유 장비와 4개 요청 동시 실행의 대기가 포함돼 있다. 비용 사용량 표는 최종 v5 결과에 연결된 호출만 집계하며 중단된 v3/v4 추가 실행 비용 전체를 뜻하지 않는다.

별도 답변 채점은 X/Y 순서를 가린 같은 Luna medium 호출이다. 판정 가능한 공통 분모에서 완전 답변은 공식 46/60→54/60, 카테고리 양성 167/199→175/199, 음성 19/20→19/20이다. 채점 API 한 건은 InternalServerError로 제외했다. 기준선 답변 생성도 한 건 실패해 결과에 그대로 남겼다. 카테고리 양성의 근거 없는 주장 표시는 20→21로 줄지 않았다. 사람 검수나 분해 의미 정확도를 측정했다고 표현하지 않는다.

20문항의 별도 로컬 지연 측정은 API 없이 저장된 하위 질문을 순서대로 재생했다. SQL 근거도 실제 실행 시점의 순서대로 합쳤다. 기준선 비교에서 메타데이터 source_id 유무가 문맥 차이로 오인되지 않도록 문맥 해시로 확인했다. TableRAG 20/20, 기준선 16/20이 저장본과 같았다. 기준선 네 건의 새 실행 차이는 정확도 평가에 쓰지 않았으며 속도 비교의 한계로 남겼다.
