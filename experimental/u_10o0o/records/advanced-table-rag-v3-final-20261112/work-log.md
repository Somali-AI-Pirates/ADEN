# KURE-v3 B 최종 선택과 잔여 오류 원인 분석

2026-11-12 사용자 요청: KURE-v3 B를 최종 선택으로 채택하고, 남은 오류가 리랭커 때문인지 확인한다.

## 범위 계약

개인 TableRAG의 새 기본 run에 기존 B 정책(추가 확인 지침·관측된 선택 출처 보존)을 적용한다. 임베딩 KURE-v3, KURE nano, 입력 2048/2048, 검색별·최종 후보 20쪽, 최종 8쪽·8000토큰은 유지한다. 실행 프로토콜과 실제 사용 프롬프트를 함께 갱신한다. 기존 A/B 실험 기록과 KURE-v2 비교, 독립 workflow 실험, advanced_search 및 운영 API는 유지한다. 기존 출력의 재개는 프로토콜 불일치로 거절하는 계약을 따른다. A 재현은 저장된 실행 스냅샷과 명시적 preserve_evidence=False 경로를 사용한다.

오류 진단은 직전 보정 결과의 v3 B 중 실제 부족 8개·모호성 13개 및 별도 모호성 대조군에서 충분 판정한 2개를 대상으로 한다. 원문 후보·저장 순위·관측 본문·출처 선택·최종 문맥을 대조한다. 정답은 진단에만 사용하고 새 검색 입력에는 사용하지 않는다. 새 API 호출·새 전체 벤치·리랭커 교체·후보 확장은 이번 범위가 아니다. 결과에 맞춰 점수나 과거 출력을 덮어쓰지 않는다.

실행 코드 변경은 새 기본 run의 정책 연결과 프로토콜 기록으로 한정한다. 독립 에이전트는 사용하지 않고 자체 검토한다. 문서 정합성, 의미 있는 경로 검증, Ruff·공통 및 개인 테스트를 수행한다.

## 분석 결과와 구현

- 보정 후 비충족 21문항을 실제 부족 8개와 모호성 13개로 나눴다. 별도 모호성 대조에서 충분 판정한 2개도 확인했다.
- 실제 부족 중 5개는 필수 페이지가 후보에 있었다. 저장된 후속 관측과 복원한 최초 관측을 대조하니 해당 본문·스키마가 전달된 경우는 모두 0회였다. 상위 8개만 보여주는 제한과 리랭킹 순위가 결합한 결과다.
- 모든 진단 검색의 입력·출력 후보 집합이 같고, 후속 조회 경로는 fallback이며 저장된 점수 내림차순임을 확인했다. HG 조회에 따른 순위 변화와 구분했다.
- 해당 후보 입력은 445~846토큰으로 절단되지 않았고, 최종 문맥은 3330~6409토큰이었다. 선택 출처 유실도 없다.
- SY4-adv-018은 다른 예약을 포함하고도 네 요청을 모두 충족했다고 종료했다. 후보 3위가 리랭킹 9위로 밀린 현상과 별개로 대상 검증이 빠진 문제를 기록했다.
- 신규 run만 보존 정책과 실제 B 프롬프트로 연결했다. 프로토콜 지문과 selection_audit 저장을 맞췄다. 예전 A 결과를 reuse-proof로 상속하면 B 실행에 섞일 수 있어 새 run은 이를 실행 전 거절한다. 과거 실행 스냅샷·결과는 보존했다.
- 실제 run 진입점에 가짜 외부 검색/API를 연결한 검사에서, 병합 상위20 밖의 선택 출처가 최종 문맥에 남고 기록된 프롬프트와 실제 호출 지침이 일치함을 확인했다. 이전 A 결과 상속 거절도 확인했다.
- 자체 리뷰에서 README의 병합 설명과 과거/현재 구분을 수정했다. 독립 리뷰는 이 대화의 경계에 따라 수행하지 않았다.
