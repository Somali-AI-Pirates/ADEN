- **Judge 기준 문항:** 단계마다 거짓 전제 20문항과 공식 문항 무작위 24개(seed 7)입니다. 전체 문항 평균이 아닙니다.

**효과가 컸던 순서**

1. **식별자 그래프 확장(고급 전용 효과).** 고급 R@8을 0.761에서 0.940으로 올렸습니다.
   - 고급 문서는 예약 하나의 기록(계약, 실제 사건일, 승인·감액·정정)이 연속된 4~5개 문서에 같은 쪽 번호로 나뉘어 있습니다.
   - 리랭커는 같은 기록의 다른 문서보다 비슷한 다른 기록을 높게 매깁니다.
   - 그래서 질문의 예약·장비 번호(없으면 1위 청크의 페이지 머리 번호)를 공유하는 다른 문서의 청크를 문서당 1개씩 위로 올렸습니다.

3. **질문 분해(LLM 1회).** 혼자서는 효과가 작습니다. 다양화와 함께 쓸 때 다른 문서를 후보에 끌어와 효과가 납니다. Basic은 0.896에서 0.956, 고급은 0.947에서 0.983이 됐습니다.

## 1. 지킨 조건

- **main 무변경:** 최신 main(361d92f) 기준 로컬 브랜치에서 작업했고, `app/`·`shared/` 코드는 수정하지 않았습니다. 실행 중에 검색 함수만 바꿔 끼웠습니다.
- **로컬 색인:** 벡터 검색은 로컬 GPU 정확 검색(행렬곱)으로 했고, 팀 Qdrant Cloud에는 접속하지 않았습니다.
- **정답 파일 사용 범위:** 검색이 모두 끝난 뒤 채점에서만 읽었습니다. 색인, 검색, 질문 분해, 생성에는 PDF와 질문 문장만 썼습니다.
- **k 고정:** 같은 비교 안에서는 모든 방식이 같은 k로 최종 문맥을 받습니다(기본 8, 4~12도 함께 기록).
- **공식 성능이 아님:** 공식 평가 문항은 개발용으로 썼으므로 비공개 시험 성능으로 볼 수 없습니다. 과적합을 확인하려고 development와 additional을 나눠 보고, 직접 만든 거짓 전제 세트로도 따로 봤습니다(4장).
- **API 사용:** OpenAI는 질문 분해(질문당 1회), 답변 생성, Judge에만 썼습니다. 답변 평가는 최종 후보 1개와 base만 비교했습니다.

## 7. 속도 (캐시 없이 측정)

단계마다 공식 질문 12개로 쟀습니다. GPU(RTX 5060 Laptop) 리랭커를 썼고, 질문 분해는 매번 LLM을 실제로 호출했습니다. 검색만의 시간이며 답변 생성은 별도입니다.

| 단계 | base 검색 p50 | 최종 검색 p50 | 그중 분해 LLM | 그중 리랭커 |
|---|---|---|---|---|
| Basic | 0.26s | 4.07s | 2.36s | 1.80s |
| 중급 | 0.26s | 3.76s | 2.07s | 1.52s |
| 고급 | 0.26s | 3.93s | 2.27s | 1.68s |

- 최종 후보는 검색이 질문당 약 3.5~3.8초 늘어납니다. 절반 이상은 질문 분해 LLM 호출이고, 나머지는 하위 질의마다 리랭커를 다시 돌리는 시간입니다.
- **LLM 없는 버전** `base+graph6+mmr0.2`는 검색 시간이 base와 거의 같습니다(약 0.3초). Recall@8은 Basic 0.896, 중급 0.868, 고급 0.947이라 최종 후보의 이득 대부분(특히 고급)을 비용 없이 얻습니다.
- 리랭커 줄이기 방안: 하위 질의는 리랭크하지 않고 후보만 보태기, 후보 풀 상한 줄이기. 측정은 하지 않았습니다.
- CPU 리랭커(팀 기본 설정)라면 리랭커 시간이 약 7배라(어제 측정) 질문 분해 버전은 실사용이 어렵습니다.

## 8. ANN 실험 (FAISS, 고급 e5-small 22,355 × 384, CPU 1스레드)

| 색인 | 설정 | ANN 재현율@20 (정확 검색 대비) | 검색 시간/질문 | main 파이프라인 R@8 |
|---|---|---|---|---|
| 정확 검색 (Flat) | — | 1.000 | 4.75ms | 0.761 |
| HNSW | M16, efC100, ef64 | 0.668 | 0.09ms | 0.763 |
| HNSW | M32, efC200, ef128 | 0.838 | 0.18ms | 0.761 |
| HNSW | M32, efC200, ef512 | 0.931 | — | — |
| HNSW | M64, efC400, ef512 | 0.979 | — | — |
| HNSW + int8 | M32, ef64 | 0.763 | 0.20ms | 0.761 |
| IVF-PQ | nlist256, nprobe32 | 0.336 | 0.22ms | 0.753 |

- **HNSW 재현율이 보통보다 훨씬 낮게 나옵니다.** 동점을 고려해도 거의 같으므로 중복 벡터 탓이 아닙니다. 양식 페이지가 많아 점수 분포가 촘촘해서 그래프 탐색이 어렵습니다. 0.98을 넘기려면 M64·ef512가 필요했습니다.
- **그래도 최종 R@8은 거의 그대로입니다.** BM25와 리랭커가 Dense 후보 누락을 메웁니다.
- **결론:** 이 규모(수만 청크)에서는 정확 검색이 4.8ms라 ANN이 필요 없습니다. 팀 Qdrant Cloud(HNSW 기본값 m16/ef_construct100)로 고급을 올릴 때는 `hnsw_ef`를 높이거나 `exact=True`를 쓰는 것이 안전합니다.

## 10. 한계

- 문항 수가 적습니다. Recall은 단계당 76~78문항, 답변은 44문항이라 ±0.05 안팎의 차이는 우연일 수 있습니다.
- 공식 평가 문항으로 설정을 골랐습니다. 비공개 시험에서는 효과가 작을 수 있습니다. 거짓 전제 세트는 독립적으로 만들었지만 같은 문서 모음입니다.
- **식별자 그래프는 이 데이터의 구조(하이픈 식별자, 페이지 머리의 기록 키)에 기댑니다.** 다른 도메인(금융·제조)이나 식별자가 없는 질문에서는 효과가 없을 수 있습니다. 대신 해가 될 때도 작습니다(중급 −0.02).
- Basic의 정답 페이지@8 하락(0.700 → 0.605)은 다양화의 대가입니다. 이번 답변 표본에서는 사실·조건 점수가 오히려 올랐지만, 페이지 근거가 중요한 문항에서는 손해일 수 있습니다.
- 답변 평가는 질문 분해와 리랭커 결과를 캐시에서 재사용했으므로 응답 시간이 실제보다 짧습니다(7장 참고).
- 로컬 GPU 정확 검색과 fp16 리랭커를 썼습니다. Qdrant Cloud + CPU fp32인 main과는 순위가 조금 다를 수 있습니다(Basic base R@8: 어제 0.793, 오늘 0.784, 공식 56문항 기준).
