# TableRAG SQL 사용 검증 설계 (초안, 2026-11-13)

## 1. 목적

additional 30문항 평가(#62·#63)에서 모델이 표 조회 도구 `query_tables`를 한 번도 선택하지 않았다. 원인은 SQL 엔진 고장이 아니라 도구 선택과 평가 범위였다.
- 표 스키마는 30문항 모두 첫 관측에 제공됐다.
- SQL 저장소·지표 테스트 21개와 실제 번들의 읽기 전용 조회는 정상 동작했다.
- 정답 파일에 SQL 기대값(`expected_sql_results`)이 한 건도 없어, SQL 정확도 지표는 전부 '해당 없음'이었다.

이 설계의 목표는 SQL 호출률을 억지로 올리는 것이 아니다. **표를 조건으로 걸러 집계해야 정확히 답할 수 있는 작은 개발 문항**으로 다음 세 가지를 따로 확인하는 것이다.
- SQL을 선택하는지
- SQL 결과가 맞는지
- SQL 결과가 최종 답변에 반영되는지

## 2. 범위

- 포함:
  - 개발용 SQL 문항 8개(`SQL-DEV01~08`)
  - 기대값 확정 방법
  - 단계별 측정 지표
  - 실행 절차와 해석 규칙
- 제외:
  - additional 최종 세트 수정 (최종 세트를 오염시키지 않도록 additional·development의 근거 페이지 146쪽은 문항에 쓰지 않았다)
  - 계획 프롬프트나 도구 동작 변경(B·A 담당)
  - SQL 사용 강제

## 5. 기대값 확정 방법

1. 질문마다 기준 SQL을 정하고, 에이전트와 같은 엔진(`TableStore.query`, 읽기 전용)으로 실행한다.
2. 손으로 예상한 값과 SQL 결과가 다르면 `build_references.py`가 파일을 쓰지 않고 멈춘다. 현재 기준 SQL 11개가 모두 일치한다.
3. **남은 단계: 원문 페이지와 사람 대조.** 표는 PDF에서 파싱한 결과라, 파싱 오류가 있으면 기대값도 함께 틀린다. 문항마다 해당 PDF 쪽을 열어 표와 기대값을 확인하고, `status`를 `draft`에서 `reviewed`로 바꾼다.

## 6. 측정 지표(문항별, 단계별)

| 단계 | 지표 | 판정 방법(실행 기록 기준) |
|---|---|---|
| 1 | SQL 선택 | planner 호출 중 `query_tables`가 있는가 |
| 2 | SQL 실행 성공 | `sql_results`에 `status=ok`가 있는가 |
| 3 | SQL 결과 정확 | 기대값(숫자는 Decimal로 정규화, 단위 포함)이 성공한 SQL 결과의 셀 값에 모두 있는가. **열 이름은 비교하지 않는다** |
| 4 | 최종 문맥 반영 | `included_sql_results`에 성공한 결과가 남았는가 |
| 5 | 답변 반영 | 답변 본문에 기대값이 모두 나오는가(숫자·단위 정규화) |
| 6 | 함정 위반 | `answer_must_not` 패턴이 답변에 나오는가(SQL-DEV03) |

- **기존 `final_sql_expected`는 보조로만 기록한다.** 이 지표는 모델이 쓴 SQL 결과의 열 이름까지 기대값과 정확히 같아야 1점이다. 별칭은 모델이 정하므로(`AS total`과 `AS s`), 값이 맞아도 0점이 될 수 있다. 3단계는 값만 비교하도록 따로 계산한다.
- 답변 품질 전반은 필요하면 기존 Judge(3회)와 필수 사실 근거 평가로 보완한다. 이 문항들의 핵심은 위 6단계다.

## 7. 해석 규칙

| 관찰 | 해석 |
|---|---|
| SQL 미선택, 답변 정확 | 작은 표를 원문 읽기로 해결했다. SQL이 꼭 필요하지 않은 문항일 수 있다(표가 최대 9행이라는 제약) |
| SQL 미선택, 답변 틀림 | 도구 선택 문제 후보. 같은 실패가 반복되면 계획 프롬프트 개선을 B·A에 제안한다 |
| SQL 선택, 실행 실패 | SQL 작성·스키마 이해 문제(오류 종류 기록) |
| SQL 성공, 결과 틀림 | 조건·집계 작성 문제 |
| SQL 결과 맞음, 최종 문맥에 없음 | 문맥 구성 문제(출처 페이지가 후보·최종에 없음) |
| SQL 결과가 최종 문맥에 있음, 답변 틀림 | 답변 생성의 반영 실패 |

8문항은 진단용 표본이다. 비율을 성능 수치로 일반화하지 않는다. 같은 문항으로 반복하거나 코드 버전을 비교할 때는 문항과 기대값을 고정한다.

## 8. 실행 절차(예정)

```bash
python experimental/Damsebi/sql-check/build_references.py
python -m app.evaluation.scripts.run_table_rag run --questions experimental/Damsebi/sql-check/sql-dev-questions.json --experiment-id table-rag-sql-dev-<날짜>
# 6단계 지표 집계 스크립트(미구현)로 runs.jsonl을 집계한다
```

- 예상 호출: 생성 8문항(문항당 planner 2~6회 + answer 1회). Judge를 붙이면 문항당 1회 × 반복 횟수
- 실행 코드는 최신 main을 쓴다. #64 이후의 검색 동작을 기준으로 한다.
- 기록: `artifacts/experiments/table-rag/<실험 ID>/`, 집계는 `experimental/Damsebi/sql-check/`

## 9. 위험과 한계

- 표가 작아서 LLM이 원문을 읽어도 풀 수 있다. 따라서 SQL 선택률은 'SQL이 필요해서 쓴 비율'이 아니라 'SQL을 선호한 비율'에 가깝다. 정확도(5단계)를 함께 봐야 한다.
- 기대값은 파싱된 표에서 나왔다. 사람의 원문 대조 전에는 초안이다.
- 개발 문항이므로 프롬프트를 고칠 때 이 문항으로 조정할 수 있다. 그렇다면 최종 확인에는 별도의 고정 문항이 필요하다.
- 여러 문서에 걸친 대규모 집계는 도구 한도(5회) 때문에 현재 구조의 평가 대상이 아니다. 필요하면 도구 설계 단계에서 다뤄야 한다.

## 10. 다음 단계

1. 8문항 기대값을 원문 페이지와 사람이 대조한다.
2. 6단계 지표 집계 스크립트를 구현한다. 모델 호출 없이 runs.jsonl만 읽으며, 가짜 기록으로 자체 점검한다.
3. 최신 main으로 8문항을 실행하고 집계한다.
4. 결과에 따라 도구 선택 개선이 필요한지 B·A와 논의한다.
