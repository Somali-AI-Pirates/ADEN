# Judge v3·검산 진단과 B/C 통합 검증 (2026-11-11)

C 담당 범위에서 Judge 출력을 구조화하고, 검산 진단과 HTTP 평가 클라이언트를 추가했다. 현재 사용할 수 있는 근거 공급 경로로 B 생성과 C 평가·관측의 연결을 실제로 확인했다. 기준 커밋은 최신 main `d93e3e4`(PR #49 반영)다.

A의 공식 Advanced 색인은 아직 없다. 이 문서의 B/C 실행은 고정 근거를 쓴 **B/C 통합 검증**이며 검색 성능 비교가 아니다. 보안 비교만 이전 비교 작업(#46)의 임시 로컬 색인으로 실제 검색을 했다.

## 요약

- Judge 출력의 필수 필드·타입을 검증한다. 구조가 틀리면 네 항목을 모두 평가 불가로 두고 사유를 남긴다. 이번 재채점·실행의 채점 125건에서 구조 오류와 호출 실패는 0건이었다.
- 검산 진단 `calculation_checks`를 공식 네 점수와 분리해 추가했다. 대상별 complete/incomplete/not_applicable/unavailable, 부족 근거, 실제 문맥 근거 ID를 남긴다.
- 채점 기준 v3를 확정했다(`5c29900b…`). 저장 답변 9개 사례와 검증용 가상 사례 5개로 v2+새 스키마와 비교했다. 규칙이 빠진 문맥과 단순 조회에서 v2+새 스키마는 검산 complete를 매겼고, v3는 incomplete·not_applicable로 반응했다.
- 근거 부족을 정확히 밝힌 답변(M19 c3)은 v3 수정 1·확정본 4회 모두 사실 0·조건 1·근거 1·판단 1, 검산 incomplete였다. 다른 대상·기간 규칙을 쓴 답변(가상 3a·3b)에는 조건 0이 매번 유지됐다.
- PR #49 생성기는 M19 근거 부족 조건에서 "검산 미완료"와 "청구서상 금액"을 구분해 답했다. 근거 충분 조건에서는 실제 약정으로 독립 계산해 청구액과 대조했다.
- AS-DEV19 근거 부족 조건에서는 "검산 미완료"를 밝히지 않고 산입 경계를 잘못 단정했다. B 요청사항으로 남긴다.
- API와 평가 CLI는 같은 질문·설정·근거로 근거 후보, 최종 문맥, 두 해시, 토큰 수, 1차 모델 입력, trace 관측이 모두 일치했다. HTTP 클라이언트 시간은 서버 미들웨어 시간보다 10~25ms 길었다.

## 2026-11-12 리뷰 반영

- `http_benchmark` 기본 제한 시간을 120초에서 150초로 올렸다. 서버가 모델 호출 제한(60초)을 시도마다(최대 2회) 쓰므로 120초에서는 재시도 끝에 성공한 요청이 클라이언트에 timeout으로 남을 수 있다. 측정은 `--timeout 180`으로 했고 모두 12초 안에 끝나 다시 실행하지 않았다.
- 두 `config_hash`를 구분했다. manifest는 설정 파일 해시, 실행 기록·trace는 절대 경로가 들어간 실행 설정 해시라 PC마다 다르다. 계산식은 유지하고 PC 간 대조 항목을 [평가 가이드](../../docs/guides/c-module-guide.md#공식-비교-재현-증거)에 적었다.
- AS-DEV19 재현 자료를 원래 실패 입력 그대로 묶었다(B 요청사항 1).
- B 요청사항 2는 응답 계약 확장 대신 서버 로그(request_id·예외 종류) 보완으로 낮췄다.
- HTTP 답변은 채점하지 않았고 점수는 평가 CLI 답변에 대한 것임을 분명히 했다.

## 입력 → 생성 → 검증 → 채점 → 저장 → Langfuse

1. 질문 파일의 `id`·`question`만 실행에 쓴다. 참고 정답은 채점 단계에서만 읽는다.
2. 공통 `app.service.bootstrap:query_adapter`가 `load_resources()`로 자원을 준비한다. 고정 근거 공급기가 후보·최종 청크를 주고, 서비스가 `build_context`·`validate_context`로 최종 문맥을 만든다(`provided_context=true`). 실행(`793e86b`, #50 병합 전)에는 `experimental.Damsebi.evidence_sources:stored_evidence`를 썼다. #50 병합 후에는 같은 공급기가 `app.service.evidence:stored_evidence`로 공통화됐고, 이번 고정 근거 4건이 공통 공급기에서도 같은 모델 문맥 해시·토큰 수를 만드는 것을 확인했다(모델 호출 없음).
3. B `generate_answer`(PR #49 프롬프트, #43 출처·날짜 검증, #48 재시도)가 답변을 만든다. 시도별 입력·출력·사용량을 실행 기록과 trace에 남긴다.
4. C `grade_all`이 Judge v3(구조 검증·검산 진단)와 RAGAS Faithfulness로 채점한다.
5. `runs.jsonl`·`scores.jsonl`·manifest를 저장한 **뒤에** `<평가 세트>.<지표>` 점수를 trace에 게시한다.
6. trace 저장(`verified`)과 점수 수신을 Langfuse API로 조회해 확인한다.

- 기존 v2 프롬프트를 그대로 쓰고 새 파서로 저장 답변 9건을 채점했다(`judge-cases-20261111-p0v2`). 네 항목 36칸이 모두 구조 검증을 통과했다. v2 출력에는 `calculation_checks`가 없어 진단 9건은 의도대로 `unavailable`("Judge 출력에 calculation_checks 없음")이었다.

- M19 원래 문맥(chsopo89 2026-11-09 기록)에는 산입 규칙이 있는 약정 페이지(AS095 p.149)가 없었다. 이미 근거 부족 조건이므로 충분 조건은 원문 청크에서 확인한 AS095·AS096을 더해 만들었다. 규칙을 만들어 넣지 않았다.
- 원문으로 직접 계산하면 M19 보관료는 산입 7일(2030-03-13~03-21 평일)·무료 2일·유료 5일·USD 265, 반납지연료는 6일·무료 1일·유료 5일·USD 165로 청구액과 같다.
- **필수 근거가 없다는 것을 정확히 밝힌 답변(c3)**: 검산 incomplete, 근거 1·판단 1로 정직한 설명과 확인한 청구·수납 사실을 인정했다. 조건도 1이다. 사실 0은 참고 정답이 요구한 사건일·산입 일수를 답하지 못했기 때문이다(판정 이유에 "문맥에 사건 일자가 없음"을 구분해 적음).
- **근거 없이 검산 완료처럼 제시한 답변(c2·c4·c4b)**: 근거 0·판단 0은 "문맥에 없는 규칙으로 검산 완료를 단정"의 정의에 맞는다. c2의 조건 0은 문맥에 없는 산입 경계를 추정한 것이라 타당하다. c4의 조건 0은 v3 확정 1회차 사유가 "검산 완료처럼 제시"뿐이라 v3 규칙(이 판단은 진단·근거·판단에서 함)과 맞지 않는 **남은 불일치**다. 2회차 사유는 "문맥에 있는 실제 반출일 누락"(조건 확인 누락으로 타당)과 "검산 완료로 제시"가 섞였고, v3 수정 1 1회차는 "실제 반출일 누락"만이었다.
- c5(규칙을 더한 문맥의 청구서 산식 답변)는 기준·회차에 따라 complete와 incomplete가 갈렸다. 사건일과 청구서 산식만으로 규칙 적용 과정을 드러내지 않은 경계 사례다.
- c6(단순 금액 조회)은 v2+새 스키마가 검산 complete를 매겼고 v3는 not_applicable이다.

v3 초안과 수정 1에서 고친 점:
- 초안: 근거 부족을 정직하게 밝힌 c3에 조건 0("검증하지 못했다고 밝힘")을 주고, c4·c4b는 같은 "검산 완료처럼 제시"로 조건·근거·판단을 모두 0으로 했다. → 수정 1에서 조건의 판정 범위를 정리했다(c3 조건 1로 안정).
- 수정 1: 다른 대상 규칙(가상 3a·3b)의 사실 0 사유가 근거 사유("뒷받침되지 않음")였다. → 확정본에서 사실은 사실·수치가 맞는지만 보게 했다. 확정본의 3a·3b 사실 0 사유는 "이 규칙이 이 건에 적용된다는 추가 주장이 문서와 모순"으로 바뀌었다. 사실 정의의 "덧붙인 사실이 틀리면 0"에 해당한다.

## 검증용 가상 사례를 이용한 Judge 동작 검증

`judge-synthetic-20261111`. 실제 프로젝트 데이터·M19 검증·검색 평가와 분리했다. 모든 문서·예약·장비·계약이 가상이며 ID에 `SYN-`을 붙였다. 질문·답변·참고 정답은 고정하고 규칙 문서(S1)만 바꿨다. 참고 정답의 근거 그룹에는 원계약만 넣었다. 문서마다 대상·유효 기간·산입 방법·무료일수·요율을 원문으로 검수했고, 적용 가능한 문서의 규칙으로 계산하면 8/3/5일·USD 160이 되는지 코드로도 확인했다(`experimental/Damsebi/judge_synthetic.py`). 검수는 작업자가 했고 사용자 검수 전이다.

| 사례 | 규칙 문서 | v2+새 스키마 r1 · r2 | v3 확정 r1 · r2 |
| --- | --- | --- | --- |
| 1 원계약 | SYN-CONTRACT p.1 | 1·1·1·1 complete · 같음 | 1·1·1·1 complete · 같음 |
| 2 대체 근거 | SYN-CONFIRM p.4(같은 대상·기간, 다른 표현의 확인서) | 1·1·1·1 complete · 같음 | 1·1·1·1 complete · 같음 |
| 3a 다른 대상 | SYN-CONTRACT-B p.1(다른 예약·장비·계약, 같은 규칙) | 0·0·0·0 incomplete · 같음 | 0·0·0·0 incomplete · 같음 |
| 3b 다른 기간 | SYN-TARIFF-2030 p.1(2030년 반출분 전용) | 0·0·0·1 incomplete · 0·0·0·0 incomplete | 0·0·0·0 incomplete · 1·0·0·0 incomplete |

- 대체 근거(2)는 참고 정답의 근거 목록에 없는 문서인데도 complete로 인정됐다. v2+새 스키마에서도 같았으므로 **기존 동작 유지 검증**이다.
- 다른 대상·기간 규칙(3a·3b)은 매번 incomplete로 감지했고 조건 0(적용 범위 오류)이 유지됐다. 근거 0은 인용 문서가 이 건을 뒷받침하지 않기 때문이고, 판단 0은 적용 규칙 없이 검산 완료를 단정했기 때문이다.
- 규칙 없음(4)은 사실 1을 유지했다. v3는 확인되지 않은 규칙을 단정한 데 조건 0, 판단 0을 줬고 v2+새 스키마는 조건·판단 1이었다.
- **실제 문서의 동등한 대체 근거 사례는 미검증이다.** M19와 development 계산 문항(AS-DEV17·19·21·23·27·29)은 사례마다 산입 규칙·요율이 "비용 조건 약정" 한 페이지에만 있었다. development 정답의 근거 그룹에도 다른 문서의 대체 후보가 없었다.

## HTTP 측정과 API·CLI 대조

같은 환경변수(`ADEN_CONFIG=configs/advanced.yaml`, sufficient 고정 근거)로 기존 FastAPI 앱을 띄우고 `http_benchmark`로 두 질문을 3회 순차 요청했다(단일 클라이언트, 동시 요청 없음).

| 질문 | HTTP 성공 | 클라이언트 중앙값 | 서버 미들웨어 중앙값 | 평가 CLI service(1회) |
| --- | ---: | ---: | ---: | ---: |
| AS-DEV19 | 3/3 (200) | 9,083 ms | 9,072 ms | 8,696 ms |
| M19 | 3/3 (200) | 11,646 ms | 11,636 ms | 10,616 ms |

- 클라이언트 시간은 요청 직전부터 응답 본문 수신까지다(6,897~11,878 ms). 같은 request_id의 서버 미들웨어 로그 시간과 차이는 10~25 ms였다. Judge·RAGAS 채점 시간은 포함하지 않았다. 측정 때 클라이언트 제한 시간은 `--timeout 180`이었다. 기본값은 이후 120초에서 150초로 올렸다(서버의 모델 제한 60초 × 최대 2회 시도보다 길어야 함). 6건 모두 12초 안에 성공해 기존 측정에는 영향이 없다.
- 위 Judge·RAGAS 점수는 평가 CLI 실행(`bc-fixed-*`)의 답변에 대한 것이다. HTTP 6건은 별도 생성 요청이며 채점하지 않았다. HTTP 응답 시간과 답변 품질의 관계를 보려면 그 HTTP 답변과 같은 request_id의 문맥(trace의 `final-context`)으로 채점해야 한다.
- 평가 CLI의 `latency_ms`(service)는 HTTP를 거치지 않은 서비스 함수 시간이다. 별도 요청이라 같은 요청의 비교가 아니며, 모델 응답 시간 변동이 이 차이보다 크다.
- 6건 모두 응답의 request_id로 계산한 trace가 Langfuse에서 `verified`였다.
- API(1회차)와 CLI(충분 조건) 대조는 두 질문 모두 10개 항목이 일치했다: 질문, 검색 방식, 실행 설정 해시(trace·실행 기록의 `config_hash`, 같은 PC라 비교 가능), 근거 후보 순서, 최종 문맥 청크, `final_context_hash`, `model_context_hash`, 문맥 토큰 수, 1차 시도 모델 입력, trace 필수 관측. 서버 trace의 request_id도 API 응답과 같았다. 모델 출력 문장은 비교하지 않았다.
- 서버 측정은 로그 파일(`artifacts/bc-api-server-sufficient.log`)과 trace로 했다. API 응답 자체에는 서버 시간·설정 해시·오류 종류가 없지만 지금 측정은 로그와 Langfuse로 할 수 있다(B 요청사항 2).

- 가상 사례 Judge: v2+새 스키마 2회, v3 초안 2회, 수정 1 2회, 확정 2회.
- B/C 고정 근거 실제 생성·Judge·RAGAS·게시와 서버 수신 대조, API·CLI 대조, HTTP 3회, 보안 4응답.

## 미검증·한계

- 실제 문서의 동등한 대체 근거 사례.
- A 공식 색인의 실제 검색과 세 방식 비교(이번 결과로 방식 우열을 말하지 않는다).
- Judge 판정의 회차 변동: 같은 기준 2회에서 c2·c4b·가상 3b의 일부 항목이 0↔1로 갈렸다. c4 조건 0의 사유가 v3 규칙과 맞지 않는 회차(확정 1회차)가 남아 있다.
- B/C 생성은 조건별 1회, HTTP는 2문항 3회다. 응답 시간은 이 PC·현재 모델 응답 상태의 측정이다.
- 생성·Judge·RAGAS가 모두 `gpt-6-luna`라 자기 평가 경향이 있을 수 있다.
- 가상 사례 문서는 사용자 검수 전이다.
