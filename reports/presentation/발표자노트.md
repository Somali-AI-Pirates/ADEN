## 03. 한 질문의 답이 여러 문서에 흩어져 있다

**핵심:** 한 업무의 날짜·금액·적용 조건은 여러 기록에 나뉘어 있을 수 있습니다.

**예상 시간:** 38초

**설명 대본**

왜 여러 곳을 찾아야 할까요? 대상 코드는 접수 기록에, 실제 처리일은 현장 기록에, 금액은 청구서에, 적용 조건은 규정에 있을 수 있습니다. 따라서 단어가 비슷한 페이지 하나를 찾는 것만으로는 같은 건의 전체 경위를 확인하기 어렵습니다. 질문이 가리키는 대상을 식별하고 필요한 기록을 함께 모아야 합니다. 화면의 세 상자는 처리 순서가 아니라, 한 질문에 필요한 서로 다른 근거를 보여 줍니다.

**근거**

- [다문서 업무 조건과 출처 보존 요구](../../docs/project-brief.md) — 위치: 7,20-22,43-46

**예상 질문**

- **Q. 왜 검색 결과 한 쪽만으로 답하기 어렵나요?**
  A. 사건 정보와 적용 규칙이 다른 문서에 있고, 예약·접수·확정이나 예정·실제처럼 비슷해 보여도 구분해야 하기 때문입니다.

## 05. 하나의 PDF를 두 경로로 읽는다

**핵심:** 검색용 페이지와 구조화 기록·표를 서로 다른 경로로 추출합니다.

**설명 대본**

PDF는 목적에 따라 두 도구로 읽습니다. pypdf와 Poppler는 모두 PDF에서 글을 추출하는 도구입니다. 검색용 페이지는 pypdf로 글과 줄 배치를 추출해 원문 쪽 단위로 보관합니다. 구조화 경로는 Poppler의 layout 출력을 사용해 표의 행과 열 위치를 살립니다. 두 작업은 같은 PDF를 읽고 원본 파일 지문을 확인합니다. 그래서 검색 페이지와 DB 기록이 같은 원본으로 연결됩니다.

## 06. 원문 값에 종류와 출처를 붙여 저장한다

**핵심:** 날짜·금액·상태를 구분하면서 원문 값과 위치를 함께 저장합니다.

**예상 시간:** 50초

**설명 대본**

먼저 PDF에서 읽은 값을 보겠습니다. 화면의 날짜와 금액은 구조 설명용 예입니다. 반납 예정일은 실제 처리일과 다른 필드에 두고, 청구액은 정확한 수치와 통화로 나눕니다. 수납액이 미결이면 0원으로 바꾸지 않고, 수치는 비워 둔 채 상태를 저장합니다. 이렇게 정리한 값마다 어느 책의 몇 쪽, 어느 행에서 읽었는지 연결합니다. 따라서 계산하기 쉽게 바꾼 뒤에도 원문을 다시 확인할 수 있습니다.

**근거**

**예상 질문**

- **Q. 미결 값을 SQL에서 0원으로 계산하나요?**
  A. 아닙니다. 미결은 상태로 보존하고 계산할 숫자는 NULL로 둡니다. NULL을 0으로 해석하지 않습니다.

## 07. records.sqlite3는 대상과 원문을 연결한다

**핵심:** 기록 조회 SQLite는 대상과 속성·기록 역할·원문 쪽을 연결합니다.

**예상 시간:** 42초

**설명 대본**

기록 DB는 네 가지 관계로 이해하면 됩니다. entities는 찾으려는 사건이나 기록이고, keys는 그 대상을 찾는 코드입니다. attributes는 확인된 날짜·규격 같은 속성, sources는 어느 원문 쪽에 어떤 역할의 기록이 있는지를 담습니다. 이렇게 연결하면 여러 페이지에 나뉜 같은 대상의 기록을 함께 찾을 수 있습니다.

**근거**

- [기록 DB 수량과 HG·HA·IS 구성](../../artifacts/advanced-table-rag/records.json) — 위치: counts,families

**예상 질문**

- **Q. 이것은 GraphRAG인가요?**
  A. 아닙니다. 관계를 SQLite의 명시적 키와 외래 연결로 저장한 조회 색인입니다. 그래프 데이터베이스나 GraphRAG로 부르지 않습니다.

## 09. tables.sqlite3는 표별 계산과 출처를 맡는다

**핵심:** 표별 계산 구조와 행별 원문 쪽·줄 연결을 저장합니다.

**예상 시간:** 40초

**설명 대본**

표를 계산하는 DB는 기록 DB와 역할이 다릅니다. 사람이 읽는 원래 열 이름은 카탈로그에 보관하고, SQL에서는 c0, c1처럼 내부 열 이름을 씁니다. 금액처럼 확인 가능한 값에는 단위 정보를, “미결”에는 상태를 붙일 수 있습니다. lineage라는 연결표가 각 행의 PDF 쪽과 줄을 가리키므로 합계의 근거도 원문으로 돌아가 확인할 수 있습니다. NULL은 숫자값이 없다는 표시이고, 미결이라는 이유는 별도 상태에 남습니다.

## 10. 질문에 따라 세 가지 조회 경로를 사용한다

**핵심:** 기록 키·문서 맥락·표 계산에 맞춰 조회 경로를 선택합니다.

**예상 시간:** 55초

**설명 대본**

준비한 자료는 질문의 목적에 따라 세 경로로 사용합니다. 특정 코드의 처리일은 기록 DB에서 날짜 종류와 원문 쪽을 확인합니다. 적용 규정을 묻는 질문은 키워드와 의미 검색으로 관련 문서를 찾습니다. 표의 합계를 물으면 먼저 카탈로그에서 표를 찾고, 발견한 표에만 SQL을 실행해 계산합니다. SQLite 안의 텍스트 검색 기능인 FTS5로 표 카탈로그를 찾습니다. 이 경로와 전체 페이지·표 검색 문서를 찾는 BM25는 서로 다른 색인입니다. 이제 두 번째 단계인 근거 확보로 넘어가, 문서 검색이 어떻게 동작하는지 보겠습니다.

**근거**

- [기록 키 조회와 표 카탈로그 FTS5](../../app/rag/records.py) — 위치: 296-399
- [페이지·표 검색, 결합, 리랭킹](../../app/rag/retrieval.py) — 위치: 260-297
- [읽기 전용 SQL·Decimal·원문 출처](../../app/rag/table_store.py) — 위치: 230-278
- [DB 우선과 하이브리드 경로](../../docs/design/architecture.md) — 위치: 44-45

**예상 질문**

## 26. BM25 토큰·점수·제목 보너스 상세

**핵심:** BM25는 단어를 쪼개 찾고, 하이픈 코드 전체와 부분을 함께 색인합니다.

BM25는 문서 안에서 자주 나오는 단어와 문서 집합에서 드문 단어를 반영하고, 문서 길이 차이를 보정합니다. k1은 단어 반복의 효과가 커지는 정도를 제한하고 b는 길이 보정의 강도입니다. 제목 보너스는 본문 검색 후보 안에 있는 문서에만 더해집니다.

## 27. SQLite는 계산 결과에도 원본 출처를 연결한다

**핵심:** 두 SQLite 파일은 사건을 연결하는 조회 인덱스와 원본 표를 계산하는 저장소로 나뉩니다.

**예상 시간:** 질의응답용 — 본 발표 시간에 포함하지 않음

**설명 대본**

**예상 시간:** 질의응답용 — 본 발표 시간에 포함하지 않음

**설명 대본**

참고한 TableRAG는 EMNLP 2025 연구입니다. 논문은 질문을 나누고 텍스트를 찾은 뒤 SQL을 만들고 실행하며, 중간 결과를 결합하는 과정을 반복합니다. ADEN은 같은 코드를 그대로 복제하지 않았습니다. 기록과 코드가 명확한 자료는 공통 SQLite에서 먼저 조회하고, 규정과 원문 설명은 페이지·표 하이브리드 검색으로 찾습니다. 모델은 다섯 개의 제한된 도구 중 필요한 것을 한 번에 하나씩 사용하고 최대 다섯 작업 뒤 근거를 조립합니다. 원문 읽기는 이미 검색된 출처에서만 가능하고, SQL은 발견한 표에 대해서만 실행합니다. 마지막에는 별도 답변 생성과 인용 검사를 합니다. 그래서 설명할 때는 ‘TableRAG 연구를 기반으로 한 프로젝트 적용’이라고 하고, 논문을 그대로 재현했다고 말하지 않습니다.

핵심 연구는 세 가지입니다. BM25는 단어 점수의 기반, RRF는 서로 다른 검색 순위를 합치는 방법, TableRAG는 문서 검색과 표 계산을 함께 사용하는 구성에 참고했습니다. 본문에는 해당 역할에 필요한 요점만 요약했고, 전체 논문과 구현 문서는 아래 근거 링크로 확인할 수 있습니다. 각 논문이 우리의 세부 설정이나 최종 성능 전체를 보증하는 것은 아닙니다.

**예상 질문**

- **Q. GraphRAG를 도입했나요?**
  A. 아닙니다. 명시 코드와 원문 출처를 SQLite 관계로 연결했습니다. 별도 지식 그래프 인덱스나 graph database는 사용하지 않습니다.
- **Q. 새 체크아웃에서도 재현할 수 있나요?**
  A. 같은 코드 커밋, 설정, 모델 리비전, 데이터 manifest와 평가 문항을 맞춰야 합니다. 발표 노트에는 기존 실행 기록과 검증된 서버 예시를 연결했습니다.
- **Q. 왜 답변마다 Ragas가 안 돌아가나요?**
  A. 사용자 응답 지연과 평가 데이터 유입을 피하도록 답변·문맥을 먼저 저장한 뒤 평가 CLI에서 별도로 실행합니다.
