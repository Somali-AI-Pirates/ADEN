# 요청 처리·자원 연결 가독성 정리 — 2026-11-06

## 범위와 호환 경계

사용자가 승인한 단순화 방향을 API·서비스·자원·검색 캐시·테스트와 개발 가이드에 적용한다. HTTP 경로·상태 코드·요청 ID·답변·출처 및 평가 RunRecord 필드와 같은 문맥 보안 비교를 유지한다. HTTP 운영 기록은 요청 ID·메서드·경로·상태 코드·응답 생성까지의 시간을 실제 로그에 남긴다. 상세 RunRecord는 기존 서비스·평가 경로에서 관리하며 사용자가 제공하지 않는 `run_record_sink` 옵션을 제거한다. 기본 검색 방식은 서비스 진입점에서 한 번 확정한다. 전체 제품 설치를 지원하며 과거의 A/B/C 부분 설치는 지원하지 않는다. 실제 외부 자원은 테스트에서 가짜로 대체하고 서비스 파이프라인은 재사용한다. BM25·리랭커는 자원별 캐시를 소유하며 첫 사용 시 준비하는 동작을 유지한다. 데이터·색인·평가 파일·인증정보·개인 실험은 변경하지 않는다.

기존 대안은 공통 `answer_query()`와 평가 어댑터·`load_resources()`다. 새 범용 등록 체계·의존성 컨테이너·기록 스키마를 추가하지 않는다. 진행 중인 기존 자원 초기화 리팩토링과 공백 변경을 보존한다.

## 작업 순서

1. HTTP 요약 로그와 서비스·평가 상세 기록의 책임을 나누고 실제 요청 경로를 단순화한다.
2. 부분 설치용 동적 연결을 제거하고 자원 준비·해제와 검색 캐시 소유자를 명확히 한다.
3. 외부 자원만 가짜로 사용하는 API·서비스·검색 테스트로 계약·격리·동시성·오류·정리를 확인한다.
4. 설계·계약·개발 가이드에 이 방식의 작성 규칙과 지원 경계를 반영한다.
5. 자체 검토 후 프로젝트 최종 린트·테스트·CLI·샘플·배포 파일 검사를 수행한다.

이 보조 대화에서는 위임이 허용되지 않아 독립 리뷰를 수행할 수 없다. 자체 점검에서 수명주기·동시성과 HTTP·평가 계약을 각각 확인하고 그 한계를 보고한다.

## 반영 결과와 검증

- `refactor/runtime-readability`에서 미사용 HTTP sink·부분 설치용 동적 연결·자원에 주입하던 고정 검색/해시 함수를 정리했다. HTTP는 실제 요약 로그, 서비스·평가기는 기존 상세 RunRecord를 사용한다.
- 검색 기본값을 서비스 진입점에서 확정하고 입력 객체를 보존한다. BM25·리랭커는 실행 자원별 상태와 잠금으로 한 번 준비하며 종료 때 참조를 해제한다. 서비스·평가 호출 및 HTTP 응답 계약을 관련 문서에 맞췄다.
- 외부 클라이언트만 가짜로 대체한 API·서비스·평가 통합, HTTP 오류별 로그·비밀 원문 제외, 앱별 자원/캐시 격리, 최초 동시 초기화와 실패 후 재시도, 생성·최종 조립 실패 중 정리를 확인했다.
- Python 3.13에서 `python -m ruff check .`, `python -m pytest -q tests` 통과: 테스트 147개·하위 테스트 9개. 다른 Python 버전 검증은 수행하지 않았다.
- CI와 같은 CLI 도움말 6개·정제본 `--check`, 새 ID의 가상 일반·보안 평가, sdist·wheel 빌드와 배포 리소스 포함/제외 검사를 통과했다. 상세 RunRecord·보안 동일 문맥 계약은 기존 평가 통합 테스트로 확인했다.
- 문서 16개의 내부 링크·앵커 175개, `git diff --check`와 실제 앱 진입점의 HTTP INFO 로그 설정을 확인했다.
- 수명주기·동시성과 HTTP·평가 계약을 자체 검토했다. 독립 리뷰는 수행하지 않았고 실제 모델·Qdrant·Langfuse 호출이나 RAG 품질 검증도 하지 않았다.
