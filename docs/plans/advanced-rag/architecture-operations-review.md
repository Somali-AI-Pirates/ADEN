## 1. 평가와 보존할 부분

현재 구성은 실험 재현과 데이터·SQL 검증에 필요한 기반을 갖추고 있다. 다만 실제 설정의 기준 위치가 분산돼 있고, 일부 함수에 서로 다른 책임이 모여 있어 제품 코드를 읽고 변경하는 비용이 크다. 로컬 인프라 실행과 운영 정책도 명시할 필요가 있다.

우리 규모에는 하나의 FastAPI 애플리케이션 안에서 책임을 나누는 **모듈형 모놀리스**가 적합하다는 판단이다. 파일·추상화 계층을 일괄 늘리기보다, 설정을 바꾸거나 도구 하나를 고칠 때 영향 범위를 예측할 수 있게 만드는 것을 목표로 한다.

다음은 이미 구현돼 있거나 채택된 기반이며, 구조 정리 과정에서 보존한다.

- 기본 TableRAG API·CLI·평가 경로의 공통 `RagService` 재사용.
- Pydantic 도구 입력 검증, LangChain 모델 연결, LangGraph 실행 흐름.
- 읽기 전용 SQL, 실행 제한, Decimal 계산과 원본 출처 연결.
- 번들의 모델·데이터 지문, 벡터 정렬 검사, 데이터 구축 재개 검증.
- 요청 ID, 요청별 원자적 결과 저장, 외부 추적 오류의 분리.
- 오프라인 데이터 구축·온라인 질의·저장된 결과 평가의 구분.

개선 과정에서 DB 우선 분기, 페이지·표 5:5 하이브리드, 리랭킹, 후보·최종 문맥 예산을 동시에 바꾸면 구조 변경의 회귀를 판단하기 어렵다. 먼저 현재 정책을 고정하고 구조만 정리한다.

## 2. 확인한 문제와 수정 제안

우선순위는 이 검토의 제안이다. 작업 일정이나 채택 결정은 아니다.

| ID | 우선순위 | 확인 내용 | 영향 |
| --- | --- | --- | --- |
| R1 | 높음 | YAML과 TableRAG 코드·환경변수의 설정 경로가 분리됨 | 설정 파일만 보고 실제 모델·검색 조건을 파악하기 어려움 |
| R2 | 높음 | 그래프의 도구 실행 함수에 검증·저장소 호출·결과 변환·기록이 집중됨 | 도구 하나의 변경과 테스트에도 많은 실행 맥락이 필요함 |
| R3 | 높음 | 요청 상태에 실행 객체와 콜백이 함께 들어감 | 상태 재생·검사·향후 저장 범위를 이해하기 어려움 |
| R4 | 중간 | 기존 검색과 TableRAG 경로의 설정·공통 기능 소유권이 불명확한 부분이 있음 | 사용처와 변경 영향을 추적하기 어려움 |
| R5 | 높음 | Qdrant 연결이 Cloud의 HTTPS·API 키 조건을 전제로 함 | 로컬 Docker 주소만 바꿔서 동일 경로를 실행할 수 없음 |
| R6 | 중간 | 로컬 인프라와 운영 준비·자원 제한·보존 정책의 보완이 필요함 | 환경 재현과 장애 대응이 작업자 판단에 의존함 |
| R7 | 중간 | 데이터 구축 파일에 여러 구축 단계가 집중됨 | 파서·DB·벡터 중 한 단계만 변경하기 어려움 |
| R8 | 높음 | 로컬 lock 기반 설치와 CI의 pip 설치가 다름 | 의존성 해석 결과가 같다고 보장할 수 없음 |

### R1. 실제 적용 설정의 기준 위치 통합

검토 시점의 [Advanced YAML](../../../configs/advanced.yaml)과 [검색 코드](../../../app/rag/retrieval.py), [모델 코드](../../../app/rag/model.py), [서비스 초기화](../../../app/rag/service.py)의 차이는 다음과 같다.

| 항목 | YAML에 보이는 값 | TableRAG 실행 경로 |
| --- | --- | --- |
| 임베딩 | Snowflake-ko | KURE-v3의 고정 모델 설정 |
| 추론 강도 | low | medium |
| 검색 방식 | naive | BM25·벡터 5:5 RRF와 리랭킹 |
| 실행 장치 | embedding_device | ADEN_TABLE_RAG_DEVICE |
| 벡터 저장소 | qdrant_collection | ADEN_TABLE_RAG_VECTOR_BACKEND와 별도 컬렉션 설정 |

각 값이 기존 경로와 새 경로에서 따로 사용될 수 있다는 점 자체가 버그라는 뜻은 아니다. 문제는 활성 경로에 적용되지 않는 설정도 같은 파일에 있어 운영자가 효력을 오해할 수 있다는 점이다. `load_service()`도 환경변수를 직접 읽고 `.env`를 로드한다.

제안:

- YAML에는 버전 관리할 모델·검색 정책, 환경변수에는 배포별 주소·경로·장치·비밀값을 둔다.
- manifest는 실제 데이터·벡터의 모델 리비전과 스키마를 증명하는 자료로 유지한다.
- 시작 지점에서 우선순위를 명시해 한 번 합성·검증한 설정 객체를 만든다.
- 모듈은 설정을 다시 읽지 않고 필요한 값과 의존성을 전달받는다.
- 활성 경로에서 쓰지 않는 설정은 분리하거나 적용 범위를 명확히 표시한다.
- 비밀값을 제외한 실제 적용 설정을 시작 로그와 실행 기록에 남긴다. 임베딩 설정과 번들 지문이 다르면 준비 단계에서 실패한다.

모든 내부 상수를 외부 설정으로 노출할 필요는 없다. 고정된 제품 정책과 배포 시 바꾸는 값을 구분한다. [FastAPI Settings](https://fastapi.tiangolo.com/advanced/settings/)의 타입 검증과 의존성 주입을 참고한다.

### R2·R3. 그래프 제어, 도구 실행, 요청 상태 분리

[graph.py](../../../app/rag/graph.py)의 `_execute()`는 검토 당시 약 300줄에서 도구 인자 검증, 기록·검색·SQL 호출, 관측 범위 검사, 결과 변환, 상태·추적 갱신을 함께 수행했다. 줄 수보다 서로 다른 변경 이유가 한 함수에 모여 있다는 점이 문제다.

같은 파일의 `AgentState`에는 질문·검색 결과 외에 `planner`, `stage`, `record_index` 같은 실행 객체도 들어 있다. 현재 저장 기능이 고장 났다는 주장은 아니며, 요청 데이터와 런타임 의존성의 경계가 흐리다는 관찰이다.

제안:

| 책임 | 권장 경계 |
| --- | --- |
| 단계 이동·종료·반복 한도 | 그래프 구성과 노드 제어 |
| 각 도구의 입력과 실행 결과 | 타입이 명확한 도구별 처리 함수 |
| SQLite·Qdrant 접근 | 수명과 오류 계약이 있는 저장소 객체 |
| 최종 출처·토큰 예산·문맥 | 근거 조립 모듈 |
| 질문·관측·종료 상태 | 요청별 State |
| 모델·저장소·설정·추적 연결 | 생성자 주입 또는 LangGraph Runtime context |

기존 도구와 실행 순서를 유지한 채 분리한다. 모든 도구에 상속 구조나 별도 클래스를 만드는 것은 목표가 아니다. LangGraph 공식 문서도 DB 핸들 같은 의존성을 state 밖의 runtime context로 전달하는 방법을 제공한다. [Runtime context](https://docs.langchain.com/oss/python/langgraph/graph-api#runtime-context)

LangChain은 모델·프롬프트·도구 계약에 활용한다. RRF, Decimal, SQL 검증 같은 계산·경계 검사는 읽기 쉬운 Python 함수로 유지해도 된다.

### R4. 기존 경로와 공통 기능의 소유권 명확화

[API 수명주기](../../../app/api/lifespan.py)와 [라우트](../../../app/api/routes.py)는 기존 자원 경로와 TableRAG를 구분한다. 기존 일반·보안 평가와 B/C 개발 경로도 남아 있다. 따라서 기존 경로를 사용하지 않는다고 단정해 삭제해서는 안 된다.

TableRAG의 API·CLI·평가가 공통 서비스를 사용하는 것은 이미 구현돼 있다. 추가로 필요한 일은 다음과 같다.

- 경로별 설정·호출자·지원 계약을 표로 정리하고, 문서의 기본 흐름과 기존 흐름을 명확히 구분한다.
- [근거 조립](../../../app/rag/evidence.py)이 사용하는 기존 문맥 구성처럼 실제로 공통인 기능에는 분명한 소유 위치를 부여한다.
- [데이터 구축](../../../app/ingestion/table_rag_builder.py)이 검색 모듈의 비공개 코드 패턴을 가져오는 연결은 공통 코드 정규화 기능으로 정리한다.
- 사용처가 없는 경로는 확인 후 제거하고, 남는 경로는 별도 호환 범위로 유지한다.

공통 기능을 전부 `utils`에 모으거나 모든 모듈 앞에 인터페이스를 만들 필요는 없다. 저장소·외부 모델처럼 교체 또는 수명 관리가 필요한 경계에 한정한다.

### R5. Qdrant의 로컬·Cloud 연결을 같은 검색 경로로 지원

검토 당시 [Advanced 연결 검사](../../../app/rag/qdrant_index.py)의 `_connect()`는 HTTPS를 요구하고, [공통 연결 함수](../../../app/indexing/vector_store.py)의 `connect()`는 URL과 API 키를 모두 요구했다. 로컬 Docker 기본 주소와 무인증 개발 설정으로는 환경변수만 바꾸어 실행할 수 없는 상태다. 이 부분은 진행 중인 작업이므로 구현 전에 재확인한다.

제안:

- 검색 알고리즘과 연결 배포 형태를 분리한다. 로컬·Cloud가 같은 Qdrant 검색 어댑터를 사용한다.
- 로컬 개발용 HTTP·인증 선택과 운영용 TLS·인증을 명시적으로 구분한다.
- 로컬 포트는 기본적으로 loopback에 공개하고, Compose 내부 연결과 호스트 연결 주소를 구분한다.
- 이미지 버전을 고정하고 데이터는 영속 볼륨에 둔다. WSL 환경에서는 Qdrant 데이터에 Windows 바인드 마운트보다 named volume 또는 적합한 Linux 파일시스템을 우선 검토한다.
- 원격 연결 실패를 로컬 검색으로 조용히 대체하지 않는다. 비교·오프라인 용도의 NumPy 지원 여부는 별도 명시한다.

로컬 개발에 Docker를 쓰는 것은 Qdrant의 공식 권장 경로다. Cloud는 백업·업그레이드·모니터링 등의 운영 부담을 위임하는 선택이다. [설치](https://qdrant.tech/documentation/installation/) · [로컬 빠른 시작](https://qdrant.tech/documentation/quickstart/)

| 관찰한 구성 | 제안 및 확인할 사항 |

| 모델을 프로세스에 적재 | 단일 worker부터 메모리·처리량을 측정한다. worker 증설에 따른 모델 메모리 중복을 고려한다. |
| [실행 저장](../../../app/observability/run_store.py)이 로컬 파일 기반 | 영속 볼륨, 보존 기간, 디스크 사용량 경보, 백업·복구와 다중 인스턴스의 평가 접근을 정의한다. |
| 저장 실패가 요청 실패로 전달됨 | 현재 채택 계약이다. 기록의 필수성을 확인하기 전 완화하지 않는다. 필수 기록이면 내구성·용량 대응을 강화하고, 선택적 기록으로 바꾸려면 공개 오류 계약을 별도 검토한다. |
| [추적](../../../app/observability/tracing.py)에 상세 입출력·근거를 보낼 수 있음 | 운영용 기록 수준·마스킹·보존 기간을 명시한다. Langfuse 실패를 질의 실패와 분리하는 기존 처리는 유지한다. |
| [원본 제공 API](../../../app/api/chat.py)와 [Nginx 예시](../../../web/deployment/nginx.conf) | 실제 외부 인증 구성을 이번 검토에서 확인하지 못했다. 공개 배포 전 질문 API와 PDF에 동일한 접근 제어가 적용되는지 검증한다. |

FastAPI는 여러 worker가 모델 메모리를 각각 사용할 수 있음을 설명한다. [배포 개념](https://fastapi.tiangolo.com/deployment/concepts/)

### R7. 데이터 구축 단계별 책임 분리

[table_rag_builder.py](../../../app/ingestion/table_rag_builder.py)는 검토 당시 약 1,700줄로 원본 처리, 기록·코드 관계, 물리 표 DB, 벡터, 잠금·지문·재개 처리를 포함했다.

다음 정도의 단계별 분리를 제안한다.

1. 원문·레이아웃 추출과 출처 생성.
2. 공통 기록·관계·표 저장소 구축.
3. 임베딩과 벡터 정렬 검증.
4. 전체 단계 조립과 재개·공개 처리.

기존 진입점과 번들 형식은 유지한다. 구현을 나누는 과정에서 파일 포맷이나 데이터 정제 규칙까지 동시에 바꾸지 않는다.

### R8. 설치·CI 재현성 보완

[개발 가이드](../../guides/development.md)는 `uv sync --locked`를 안내하지만 [CI](../../../.github/workflows/ci.yml)는 PyTorch와 프로젝트를 별도 pip 명령으로 설치한다. `uv.lock`의 전체 해석 결과를 CI가 그대로 사용하지 않으므로 로컬과 동일한 버전 조합임을 보장할 수 없다.

제안:

- 로컬·CI의 lock 기반 설치와 지원 Python 버전을 맞춘다. CPU PyTorch의 소스·버전도 명시한다.
- 기존 Ruff·pytest·패키지·리소스 검사를 유지한다.
- 프런트엔드 타입 검사·테스트·빌드를 CI 범위에 포함한다.
- 작은 데이터로 실제 Qdrant HTTP 서비스 연결·영속성 경계를 검사한다.
- 기본 CI는 가짜 LLM 응답을 사용한다. 실제 모델·Ragas·Judge 평가는 승인된 별도 실행으로 유지한다.
- 변경된 도구의 공개 동작·출처·오류를 검사하고, 내부 호출 순서를 그대로 복제하는 테스트는 피한다.

[uv의 GitHub Actions 안내](https://docs.astral.sh/uv/guides/integration/github/)를 참고한다.

## 3. 권장 로컬 개발 구성

아래는 아직 구현되지 않은 제안이다. 현재 실행 명령은 빠른 시작 문서를 따른다.

| 구성 요소 | 로컬 개발 제안 | 운영에서의 판단 |
| --- | --- | --- |
| FastAPI | VS Code·uv에서 실행해 디버깅 | 고정 이미지·자원 제한, 자동 재시작·준비 상태 검사 |
| Qdrant | Docker + 영속 볼륨 | Cloud 또는 자체 운영. 백업·복구 책임을 기준으로 결정 |
| SQLite | 로컬 읽기 전용 번들 파일 | 앱 인스턴스에 검증된 스냅샷을 읽기 전용 마운트 |
| Langfuse | 선택적으로 켜는 Compose 또는 팀 공용 인스턴스 | Cloud 또는 자체 운영의 저장·업그레이드 비용 비교 |
| 임베딩·리랭커 | 고정 모델 캐시와 CPU/GPU 선택 | 요청 임베딩·리랭킹 자원은 Qdrant 배포와 별도로 산정 |
| Ragas·Judge | 저장된 실제 답변을 평가 CLI로 채점 | 일반 응답 경로와 분리된 품질 평가 |

### SQLite를 별도 DB 서버로 띄우지 않는 이유

SQLite는 앱이 파일을 직접 사용하는 내장 DB다. 검증된 기록·표 스냅샷을 읽는 현재 용도에는 적합하다. 컨테이너 배포라면 앱에 해당 파일을 마운트하면 된다. 여러 호스트에서 같은 DB 파일을 네트워크로 공유해 쓰는 방향은 기본안으로 삼지 않는다. 다중 서버의 공동 쓰기 요구가 생기면 서버형 DB를 별도 검토한다. [SQLite 사용 기준](https://www.sqlite.org/whentouse.html)

### Langfuse 자체 호스팅의 범위

Langfuse는 공식 Docker Compose로 실행할 수 있고 Cloud와 같은 SDK·통합 방식을 사용할 수 있다. 다만 웹·워커 외에 PostgreSQL, Redis/Valkey, ClickHouse, 객체 저장소 등이 필요하다. 개발자마다 항상 전체 구성을 실행하기보다 선택 실행 또는 팀 공용 환경을 권한다. 자체 호스팅하면 저장소 백업·업그레이드·용량 관리도 직접 맡아야 한다. [Docker Compose](https://langfuse.com/self-hosting/deployment/docker-compose) · [구성 요소와 규모 산정](https://langfuse.com/self-hosting/configuration/scaling)

Compose profile이나 별도 Compose 파일로 선택 실행을 지원할 수 있다. 현재 웹 개발 서버와의 포트 충돌을 피하도록 로컬 Langfuse 외부 포트는 예를 들어 3001을 사용할 수 있다. 이는 제안이며 현행 설정이 아니다. 로컬 프로젝트의 인증키는 Cloud 키와 별개로 준비한다. [Compose profiles](https://docs.docker.com/compose/how-tos/profiles/)

Langfuse를 로컬로 옮겨도 Luna API에 전달하는 데이터 경계까지 로컬로 바뀌는 것은 아니다.

## 4. 제안하는 구현 순서와 확인 기준

| 순서 | 작업 | 완료 확인 기준 |
| --- | --- | --- |
| 1 | 설정·초기화 경로 통합 | 활성 설정·시작 로그·실제 모델과 검색 조건이 일치하고 번들 불일치를 거절 |
| 2 | 로컬 Qdrant와 선택적 Langfuse 구성 | Cloud 계정 없이 로컬 인프라 구동. API를 로컬에서 수정·디버깅하고 SQLite는 파일로 사용 |
| 3 | 도구 처리·그래프 상태·저장소 경계 정리 | 같은 입력·고정 계획 응답에서 조회·SQL·후보·최종 출처가 유지됨 |
| 4 | 구축 단계·기존 경로의 소유권 정리 | 원본부터 구축·검사·서버·평가까지 같은 문서 흐름으로 재현 |
| 5 | CI·readiness·요청 제한·기록 정책 보완 | lock 기반 재현과 장애·자원 부족 때의 공개 동작을 검증 |

각 변경은 기존 동작과 비교 가능한 크기로 나눈다. 별도 서비스, 작업 큐, 모델 서버, 서버형 관계 DB 도입은 현재 요구가 아니라 측정 또는 공동 쓰기·확장 요구가 생겼을 때의 후속 판단이다.

구현 시 필요한 검증:

- 고정 모델·벡터·계획 응답을 사용한 서비스 재생: SQL 결과·출처·후보·종료 상태 비교.
- 로컬·Cloud Qdrant에서 같은 검색 정책 사용. exact 결과의 수치 오차와 동점 순위 규칙을 구분해 비교.
- 출처 밖 읽기·SQL 제한·최종 문맥 보존 등 기존 경계 테스트 유지.
- Langfuse 장애와 필수 저장 실패를 서로 다른 정책대로 처리.
- 필수 자원 미준비, 요청 대기 제한, 취소·종료 시 자원 정리 검사.
- 새 환경의 준비 문서, CI 설치, 데이터 영속성·복구 검사.

## 5. 검토 증거와 한계

이번 검토에서 수행한 것은 제품 코드·설정·문서·CI의 읽기, 공식 레퍼런스 확인, 개선 제안 문서화다. 기존 데이터나 실행 결과를 수정하지 않았다.

다음은 수행하지 않았으며 통과로 간주하지 않는다.

- 실제 모델·Qdrant·Langfuse 호출, 유료 평가.
- 처리량·p50/p95·메모리·장애 복구의 실측.
- 외부 배포 환경의 인증·네트워크·볼륨 구성 확인.
- Ruff·pytest·패키지 빌드의 재실행.
- 독립 에이전트 리뷰. 이 별도 대화의 제한에 따라 자체 점검만 수행했다.

문서 저장 후에는 내부 링크 대상, 문서 탐색 연결, 제안과 현행 동작의 구분, 문서 diff를 확인한다. 이 검사는 제품의 운영 안정성 검증을 대신하지 않는다.
