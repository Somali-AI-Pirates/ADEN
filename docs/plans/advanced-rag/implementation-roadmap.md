# TableRAG A 구현 로드맵

> 2026-11-12 현재 구현 기준은 DB 우선 통합 TableRAG다. [현재 구현 기록](unified-implementation-log.md)과 [빠른 시작](../../guides/quickstart.md)을 따른다. 아래 A 이식 내용은 초기 설계 기록이다.

[전체 설계](README.md)의 TableRAG A를 옮기는 단계와 검증 조건이다. 현재 실행 방법은 [개발 가이드](../../guides/development.md#advanced-tablerag-실행)를 따른다.

## 준비된 데이터에서 시작하기

현재 체크아웃에는 A(v5) 데이터 스냅샷과 로더를 준비했다. [데이터 사용법](../../guides/data.md#advanced-tablerag-데이터)에서 `load_corpus`로 문서, 정규화 벡터, 원본 출처 목록, 읽기 전용 표 저장소를 불러온다. 전체 TableRAG에는 HG 연결을 추가한 `a-v5-hg` 스냅샷을 쓴다. 0~2단계는 데이터 계약과 스냅샷 준비를 다룬다.

## 진행 원칙

- 한 번에 한 단계만 진행한다. 필요한 문서를 읽고 함수 한두 개의 입력·출력을 먼저 이해한다.
- 검색 이식의 시작점은 KURE-v3를 사용한 A(v5) 스냅샷이다. 재현 검증 동안 모델·프롬프트·색인·HG 규칙·예산을 고정한다. 모델을 교체한 결과는 별도 manifest와 실행 이름으로 기록한다.
- 순위나 출처가 바뀌면 리팩터링으로 묶어 넘기지 않는다. 의도한 변경인지 먼저 확인한다.
- 유료 호출 없이 확인할 수 있는 부분부터 만든다. 실제 호출은 별도의 연결 확인과 평가 단계에서 한다.
- 파일 수·클래스 수를 목표로 삼지 않는다. 완성한 동작이 다음 단계의 입력이 되도록 한다.

## 0단계 — 이식 기준을 고정한다

**목적:** 실험 디렉터리의 진행 중 변경과 제품 이식의 기준을 분리한다.

작성할 것:

1. TableRAG A 코드·프롬프트·HG 규칙·원본·표·페이지/표 벡터·모델 revision을 manifest로 묶는다. 현재 TableRAG 파일 중 Git 미추적 작업도 있으므로 HEAD 해시만으로 충분하지 않다.
2. 저장된 A 실행에서 명시 코드, 간접 HG 날짜, IS 절차, 표 집계, 두 사건, 근거 부족, 모호함, 오류를 포함하는 소규모 재생 표본을 고른다. 각 표본의 계획 응답·SQL·검색 질문·후보·최종 문맥을 고정한다.
3. 공식 60·카테고리 220의 질문 manifest와 참고답 manifest를 따로 보존한다. 수량·ID·파일 해시를 검사한다.
4. 현재 프런트엔드·API·평가 호출자를 찾아 전환 목록을 만든다. 타인의 코드와 실험은 삭제 대상에 넣지 않는다.
5. LangGraph를 런타임 직접 의존성으로 추가할 버전을 선택하고 기존 langchain-core/openai·Langfuse·Ragas pin과 함께 lock한다. langchain 상위 패키지는 실제 사용할 import에 필요할 때만 직접 선언한다. 설치 변경 후 네트워크 없는 import·가짜 graph·Ragas smoke를 먼저 확인한다.

**완료:** 모델 호출 없이 기준 파일과 해시를 읽을 수 있고, 어떤 실행을 재현할지 설명할 수 있다. 공식의 58은 페이지 근거 평가 대상 수이지 전체 질문 수가 아니라는 점을 확인한다.

## 1단계 — 타입과 출처 연결부터 작성한다

**목적:** 큰 payload와 dict를 계속 전달하지 않도록 경계 의미를 먼저 정한다.

작성할 것:

- LangChain Document metadata에 page/source/unit/table ID를 붙인다. 같은 원본 페이지와 그 페이지의 표는 unit ID가 달라도 같은 page ID를 갖는다.
- 검색 결과, SQL 결과, 최종 근거, 답변의 작은 타입을 작성한다. 외부 모델 입력·출력은 Pydantic으로 엄격하게 검사하고 내부 그래프 상태는 TypedDict 등 단순 타입을 사용한다.
- 원본 출처 ID ↔ 문서명·쪽 번호의 왕복 변환을 작성한다.
- 결과와 별도로 request_id·trace_id·설정 지문을 담는 실행 context를 둔다. 참고답과 평가 라벨은 넣지 않는다.

**확인:** 같은 페이지의 표 두 개를 복원해도 원본 쪽을 두 번 세지 않는다. 출처 없는 인용·잘못된 페이지 번호는 거절한다.

**완료:** 작은 가짜 데이터만으로 ‘검색 단위’와 ‘최종 인용 페이지’의 차이를 확인한다.

## 2단계 — 스냅샷과 안전한 표 조회를 옮긴다

**목적:** LLM 없이 원본 표를 정확하게 읽는다.

작성할 것:

1. 읽기 전용 TableStore를 옮긴다. 원본 해시·표 catalog·cell lineage·페이지 연결을 검증한다.
2. 명시한 물리 표의 스키마를 읽는 기능과 제한된 SELECT 실행 기능을 구분한다.
3. Decimal 문자열·단위·통화·날짜 종류·상태와 기존 계산 함수를 보존한다.
4. SQL 실행의 allowlist·SQLite authorizer·query_only·실행시간·행 제한·오류 반환을 작성한다.
5. 오프라인 스냅샷 구축 코드는 검증된 파서와 생성 절차에서 옮긴다. 서버 시작 때 PDF 재파싱이나 임베딩을 하지 않는다.

**확인:** 0과 미결, 예정일과 실제일, 서로 다른 통화, 잘린 미리보기, 허용하지 않은 표, 쓰기/ATTACH/PRAGMA 시도, 중복 열 이름을 검사한다. SELECT 전체 표 집계와 40행 미리보기를 혼동하지 않는다.

**완료:** 같은 SQL과 표 집합을 넣으면 A와 값·상태·열·출처가 같다. 스냅샷이 다르면 명확히 실패한다.

## 3단계 — 검색 한 번을 재현한다

**목적:** 반복 계획을 붙이기 전에 단일 검색이 A와 같아야 한다.

작성 순서:

1. 기존 코드 보존 토큰화·제목 보너스 BM25를 함수 단위로 옮긴다.
2. 고정 임베더·페이지/IS 표 벡터로 현재 정확 검색을 연결한다.
3. 5:5 RRF, 중복 페이지 처리, 동점 순서, 20개 제한을 옮긴다.
4. KURE 한 번과 HG 원문 보충을 옮긴다. HG 간접 날짜 처리도 포함한다.
5. 검색 반환값을 LangChain 검색 호출 경계에 연결한다. 프레임워크 추적을 위해 결과와 점수를 따로 재계산하지 않는다.

**확인:** A와 BM25/벡터 상위 결과, RRF 후보, KURE 입력·점수·순위, HG 분기·출처, 표 ID를 단계별로 비교한다. CPU/GPU 수치 차이가 있으면 점수 허용 오차와 순위 변경을 따로 기록한다.

**완료:** 재생 표본에서 후보·순위·원문 연결이 일치한다. 단순 최종 점수 일치만으로 통과시키지 않는다.

**관측 연결 시작:** 검색·DB 처리 시간, 절단, 요청 ID를 로컬 기록에 남긴다. Langfuse를 나중에 붙이더라도 여기서부터 결과 객체와 trace를 분리한다.

## 4단계 — 관측 발췌와 최종 근거를 만든다

**목적:** 모델이 보는 근거가 어디서 왔고 무엇이 제외됐는지 알 수 있게 한다.

작성할 것:

- 계획자용 관측: 원문 발췌, 실제 관측한 표 스키마, SQL 미리보기와 절단 표시.
- A의 여러 결과 순환 병합과 최종 후보 20쪽.
- finish 선택을 후보 안에서 반영하고 최대 8쪽·SQL 포함 8,000토큰으로 구성하는 함수.
- SQL 기여 원본이 남지 않거나 SQL 예산이 넘으면 제외하는 규칙.
- 최종 모델 문맥 문자열·입력 JSON·token count·hash를 저장하는 경계.

**확인:** SQL 원본이 9쪽인 경우, 일부 원본이 예산에서 빠지는 경우, 관측했지만 최종 후보에 없는 출처, 표와 페이지 중복, schema가 너무 큰 경우를 검사한다.

**완료:** 저장된 계획 선택을 넣었을 때 A와 최종 페이지 순서·SQL 포함 여부·문맥 지문이 같다. 검색 결과를 다시 리랭킹하거나 근거 보존 B를 추가하지 않는다.

## 5단계 — 가짜 모델로 도구 반복을 만든다

**목적:** 호출 비용과 모델 변동 없이 A의 제어 흐름을 구현한다.

작성할 것:

- solve/finish의 strict schema와 graph state.
- initial_search → plan → solve → plan, finish → assemble의 연결.
- 유효한 표는 앞선 관측에서만 가져오고, SQL과 table_ids를 검사하는 실행기.
- solve 최대 5회, 계획 최대 6회, 마지막 finish 강제, max_retries=0, 오류 시 종료 사유.
- 관측당 6,500과 누적 planner 입력을 구분한다. 전체 지침·스키마·history와 출력 여유가 확인된 모델 창을 넘으면 자동 요약 없이 명시적인 예산 오류로 끝낸다.
- 실제 tool_call_id를 보존하는 메시지 왕복.

**가짜 모델 시나리오:**

| 응답 흐름 | 확인할 행동 |
| --- | --- |
| 첫 호출 finish | 최초 검색만 하고 바로 조립 |
| sql=null → 새 스키마 → SQL | 새 표는 다음 계획부터 조회 가능 |
| 서로 다른 두 사건 | 요청별 관측과 SQL 출처를 섞지 않음 |
| 잘못된 도구 인자 | 시도 횟수 소모, 오류 관측 반환 |
| solve 다섯 번 | 여섯 번째 계획은 finish 전용 |
| 도구 둘·알 수 없는 도구·형식 오류 | 오류 상태와 종료 이유 기록 |
| 모델 timeout | 검색 근거 부족과 구분 |
| 동시 두 요청 | 관측 표·messages·선택 출처가 섞이지 않음 |

**완료:** LLM 호출 없이 A의 단계 순서와 상한을 확인한다. 상태기계 구현에는 새 판단 LLM이 필요 없다.

## 6단계 — 실제 계획·답변 체인과 Langfuse를 연결한다

**목적:** 같은 흐름을 LangChain 모델 호출로 실행하고 한 trace에서 확인한다.

- 계획은 bind_tools, 답변은 구조화 출력으로 연결한다. 계획과 답변 프롬프트를 각각 버전 고정한다.
- 제공자별 tool call ID·후속 메시지·reasoning 관련 불투명 필드의 전달이 SDK 경계에서 유실되지 않는지 확인한다. 이를 trace에 통째로 노출하지 않는다.
- 답변에는 질문과 최종 페이지·SQL만 보낸다. planner history나 gold를 넘기지 않는다.
- 실제 인용 ID·응답 상태·형식을 검사한다. 모델 사용량 누락은 0이 아닌 unknown으로 기록한다.
- Langfuse callback과 수동 span을 한 root에 연결하고 모델 호출을 중복 계수하지 않는다.
- 연결 검증은 1문항 → 서로 다른 경로의 소규모 표본 순으로 한다. 실제 호출·원문 전송·추적 저장은 그 실행의 승인된 범위에서 한다.

**완료:** 검색 → 계획 도구 → SQL → 최종 문맥 → 답변이 같은 요청 ID로 보인다. 논리 호출 수와 제공자 시도 수가 일치하거나 차이의 원인이 설명된다. 상세 항목은 [관측 설계](evaluation-observability.md)를 따른다.

## 7단계 — 평가 파이프라인을 구성한다

**목적:** 서버가 쓰는 함수를 그대로 평가하고 답변 품질까지 측정한다.

- 실행기는 질문만 받아 API와 같은 RAG를 호출한다. 모든 결과 저장 후 참고답을 읽는 score/grade를 별도 단계로 둔다.
- 검색 deterministic 지표, SQL 기대값, Ragas Faithfulness, 4축 Judge, planner/tool 진단, 오류·비용·지연을 연결한다.
- 처음에는 가짜 Judge와 저장된 결과로 데이터 계약을 검증한다. 이후 보정 표본에서 평가 모델을 고정한다.
- Langfuse에 이미 저장한 trace/observation과 점수를 연결하고 재전송 시 중복을 막는다.
- 정답 변경·대체 근거 인정은 별도 버전으로 남긴다. 원래 점수를 덮지 않는다.

**완료:** 질문 한 개의 입력 지문 → 검색·SQL·답변 → 지표별 점수·이유 → Langfuse 항목을 역으로 추적할 수 있다. 평가 오류는 서비스 오답과 구분된다.

## 8단계 — API를 얇게 연결한다

**목적:** HTTP 처리와 RAG가 서로의 내부를 알지 않게 한다.

- lifespan에서 자원 준비·종료, 준비 상태를 관리한다. 모델을 요청마다 로드하지 않는다.
- 라우트는 질문 검증·RAG 호출·응답 변환만 한다. 서비스에 HTTP payload를 넘기지 않는다.
- request_id가 헤더·본문·앱 로그·trace에서 이어지도록 한다. 접근 로그 중복을 확인한다.
- 요청 필드 변경은 실제 소비자 확인 후 동시에 전환한다. 검색 방식은 서버 설정·평가 설정으로 분리한다.
- 네트워크 호출은 async, 동기 모델·SQLite는 명시적인 제한 작업 실행으로 연결한다. async 함수에 무조건 to_thread를 겹쳐 붙이지 않는다.

**확인:** TestClient에서 정상·공백 질문·불필요한 필드·근거 부족·추가 확인·모델 오류·timeout·자원 미준비를 직접 요청/응답으로 확인한다. 같은 앱을 순서대로 두 번 시작/종료해 자원 재생성과 종료 1회를 확인한다.

**완료:** Swagger로 실행 가능하고, 두 동시 요청의 상태·ID가 섞이지 않는다. 추적 장애가 업무 요청의 성공을 거짓으로 바꾸거나 원문을 콘솔에 누출하지 않는다.

## 9단계 — 회귀·속도·선택 모델의 동작을 확인한다

세 작업을 분리한다.

1. **이식 동등성:** 고정된 계획·검색 입력을 재생하여 후보·SQL·문맥 비교. LLM의 새 출력을 재현성 실패로 혼동하지 않는다.
2. **실제 시스템 비교:** 같은 공식·카테고리 질문에서 A와 새 구현을 실행한다. 일상 표현·복합·모호 질문별 개선/하락과 추가 호출을 본다.
3. **선택 모델·장치 확인:** 0단계에서 선택한 모델의 검색 연산·입력 prefix·토큰 길이·dtype·장치가 실험과 같은지 확인한다. 이 단계에서 모델 후보 비교를 다시 시작하지 않는다. 나중에 교체하면 별도 변경으로 하나씩 비교하며, 고정 후보 rerank 진단과 다시 계획하는 전체 실행을 구분한다.

CPU/GPU·dtype·thread·배치·동시 요청 수를 고정한다. 모델 로드 시간, 요청 대기, 검색, SQL, 계획, 답변, 전체 응답의 p50/p95와 오류율을 기록한다. 표본 재사용 캐시는 품질 재생에만 쓰고 실측 지연에서는 질문별 계산을 재사용하지 않는다.

정확한 품질 하한·지연 목표·최대 동시성은 **실행 전에** 사용자와 기준을 적는다. 아직 운영 장비·SLO가 정해지지 않아 임의의 “p95 몇 초면 합격” 수치를 만들지 않는다. 이미 반복 사용한 공식·카테고리는 회귀용이며 미사용 검증이라고 부르지 않는다.

## 10단계 — 전환과 문서 정리

- 동일 검증이 끝난 후 제품의 기본 경로만 전환한다. 스냅샷·설정은 이전 버전을 보존하고 한 번에 교체하여 되돌릴 수 있게 한다.
- 운영 코드의 experimental import가 없는지, wheel에 필요한 프롬프트·catalog가 포함되는지 확인한다.
- 실제 호출처가 없는 기존 검색/서비스 코드를 제거한다. 과거 실험·결과는 보존한다.
- 실제 구현에 맞춰 시스템 설계·공통 계약·설치/데이터/평가 가이드를 갱신한다. 이 제안서를 현재 동작 문서로 대신하지 않는다.
- [개발 가이드](../../guides/development.md)의 Ruff·전체 pytest, 패키징 변경 시 build, CLI 변경 시 help·샘플, FastAPI 개발 실행을 검증한다. 유료 평가는 일반 CI에서 자동 실행하지 않는다.

**최종 완료:** 구현자가 각 단계의 입출력을 설명할 수 있고, 같은 진입점으로 API·평가·관측이 연결되며, 남은 품질/운영 한계가 보고서에 표시된다.
