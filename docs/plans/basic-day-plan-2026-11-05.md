# Basic 당일 작업 계획 — 3명

작업일: **2026-11-05, 한국시간**. 오늘은 Basic 해운 서비스의 필수 구현·비교·기록을 목표로 한다. 팀원 이름은 아직 제공되지 않아 A/B/C로 표시한다. 아래는 업무 배정안이며 실제 구현 완료나 담당자의 작업 착수를 뜻하지 않는다.

기준 설계: [시스템 설계](../design/architecture.md) · [공통 입출력·호출 계약](../design/contracts.md) · [Git 협업 규칙](../guides/git-workflow.md)

> 이 문서는 2026-11-05 당일 계획의 기록이라 그날의 `app/` 폴더 이름을 그대로 둔다. 2026-11-06에 패키지가 `member_a`·`member_b`·`member_c`·`shared`로 바뀌었으므로, 아래 담당 폴더는 [시스템 설계 §3](../design/architecture.md#3-폴더-구조)의 현재 구조로 바꿔 읽는다. `app/core/contracts.py`는 `shared/contracts.py`다.

## 1. 오늘의 범위

- 제공된 Basic 해운 PDF **15개, 총 360쪽** 전체를 처리한다.
- 예약·서류·처리 상태를 근거와 함께 답하고, 필요한 조건은 되묻고, 자료 부족은 보류한다.
- Naive / Hybrid / Hybrid + Reranking을 같은 API에서 선택한다.
- FastAPI·LangChain·`gpt-6-luna`·Langfuse를 연결한다.
- 일반 평가 질문은 **12개를 초기 목표**로 잡는다. 12개를 확정하면 세 방식의 **36개 결과 전체**에 검색 지표·RAGAS·Judge를 적용한다.
- 보안 질문 2개를 한 검색 구성의 기본/방어 프롬프트로 실행해 답변 **4개**를 비교한다.
- 시간·오류·입력/출력 토큰, 비교표와 실행 방법을 남긴다.

12개는 오늘의 작업량 제안이며 발제문 필수 개수가 아니다. 실제 제공 문항과 호출 시간을 보고 **최종 비교 실행 전에** 질문 수·ID·선정 이유를 확정한다. 채점 호출은 36개의 서비스 답변 생성과 별도로 발생한다.

오늘은 Basic의 문서 설명과 조건 판단에 집중한다. 요율·계약 조건이 없는 비용 계산은 필요한 자료가 없다고 설명하고 보류한다. 상위 난이도, 계산기, UI, 대화 메모리, 배포는 이후 작업이다.

## 2. 담당 배정

| 담당 | 역할 | 주 담당 파일·폴더 | 오늘 넘겨줄 결과 |
| --- | --- | --- | --- |
| **A** | **데이터·검색** | `app/ingestion/`, `app/indexing/`, `app/retrieval/`, `scripts/build_index.py`, `data/README.md` | 전체 PDF 처리 내역, 두 색인, 세 검색 방식의 `retrieve()` |
| **B** | **답변 생성·API·통합** | `app/core/`, `app/generation/`, `app/service/`, `app/api/`, `main.py`, `prompts/shipping_qa.txt` | `/query`에서 답변·상태·출처 반환, 정상/오류 처리, 모듈 연결 |
| **C** | **실행 기록·평가** | `app/observability/`, `evaluation/`, `scripts/run_benchmark.py`, `scripts/run_security.py`, `prompts/judge.txt`, `prompts/defense.txt`, `reports/` | Langfuse 기록, 일반·보안 평가, 비교표·결과 해석 |

**B가 통합 담당**을 맡는다. 공통 타입과 설정 파일의 변경을 모아 반영하고 모듈을 연결한다. A와 C는 자신의 함수와 필요한 설정을 전달한다. C는 로그 코드를 만들고 B가 API·생성 호출에 연결하므로, 두 사람이 `service/query.py`를 동시에 편집하지 않아도 된다.

공통 설정 `configs/basic.yaml`, 의존성 파일, `.env.example`, `.gitignore`는 B가 취합한다. A는 검색·모델 의존성, C는 평가·Langfuse 의존성을 초반에 전달한다. 루트 README의 실행 안내도 B가 정리하되 A와 C가 실제 실행 명령을 제공한다.

### A — PDF에서 검색 결과까지

1. Basic 해운 ZIP 2개를 같은 데이터 폴더에 풀고 PDF 15개·페이지 수를 확인한다.
2. `book_id`, 원본 파일명, 1부터 시작하는 페이지를 보존해 텍스트를 추출한다. 누락·빈 페이지·실패를 기록한다.
3. 페이지·문단·목록을 보존해 청킹하고 같은 청크로 벡터 색인과 BM25 색인을 만든다.
4. **Naive를 먼저 B에게 전달**하고, 동일한 반환 타입으로 Hybrid와 리랭킹을 추가한다.
5. `retrieve(question, mode, resources)`가 순서 있는 후보 목록을 반환하도록 한다. 평가 정답과 공격 정보는 검색 입력으로 사용하지 않는다.
6. 마지막에는 검색 실패 사례를 맡아 정정 문서 누락, 키워드 매칭, 출처·페이지 문제를 분석한다.

완료 기준: 모든 PDF의 처리 상태를 설명할 수 있고, 세 검색 방식이 같은 청크·임베딩·색인 기반으로 실행되며, 결과에 문서·페이지·청크 ID가 남는다. 최종 문맥 선택과 답변 생성은 B에게 넘긴다.

### B — 검색 결과에서 사용자 응답까지

1. 공통 타입과 최소 앱 골격을 먼저 공유한다. A·C와 함수 입출력을 맞추고 초기 계약을 확정한다.
2. `/health`, `/query`, 요청 ID와 Pydantic 요청·응답 검증을 연결한다.
3. 검색 후보에서 공통 k·토큰 예산에 맞는 최종 문맥과 `S1`, `S2` 출처 대응표를 만든다.
4. LangChain과 `gpt-6-luna`로 답변을 생성한다. 접수/확정, 요청/완료, 정정 적용 범위를 프롬프트에 명시한다.
5. `answered`, `needs_clarification`, `abstained`와 코드가 처리하는 `error`를 구분한다. 모델의 출처 ID를 실제 파일·페이지로 검증한다.
6. C가 제공한 추적 함수를 호출해 검색 후보·최종 문맥·실제 모델 입출력·시도별 토큰을 전달한다.
7. 모델 timeout·잘못된 출력·빈 입력을 확인하고, `/docs`에서 전체 흐름을 시연한다.

완료 기준: 같은 API에서 세 검색 방식을 바꿀 수 있고, 답변/추가 확인/보류와 시스템 오류가 구분된다. 인용은 실제 전달한 문맥에 연결된다. `main.py`는 앱 생성 함수를 호출하고 실행 순서는 `service/query.py`에 둔다.

### C — 첫 요청의 기록부터 최종 비교까지

1. 초기부터 Langfuse 연결과 실행 기록 형식을 준비한다. 실제 요청 하나에서 모델 입력과 출력이 보이는지 B와 확인한다.
2. 제공 질문 파일에서 `id`, `question`만 읽는 실행기를 만든다. 질문 선정안과 이유를 팀에 공유한다. 예약·서류·정정/조건 확인·자료 부족이 고르게 포함되도록 한다.
3. 첫 서비스 응답이 나오면 **한 문항으로 RAGAS와 Judge까지 미리 실행**하여 마지막 시간에 평가 연동 문제를 발견하지 않게 한다.
4. 고정한 일반 질문을 세 방식으로 실행하고 답변·상태·인용·최종 문맥·요청 ID를 저장한다. 그 후 정답·채점 기준을 결합한다.
5. 최종 문맥 청크의 문서 ID로 Hit@k·Recall@k를 계산하고, Faithfulness와 Judge의 사실·조건·근거·판단을 각각 기록한다.
6. 한 구성에서 보안 질문별 최종 문맥을 한 번 저장하고 기본/방어 프롬프트로 재사용한다. 실제 공격 노출과 업무 답변의 정확성을 확인한다.
7. `reports/`에 질문별 결과와 운영 지표를 정리한다. A·B에게 각 실패 사례를 전달하고 대표 사례 원문 확인을 함께 진행한다.

완료 기준: 선택한 일반 질문의 세 방식 결과 전체에 점수 또는 해당 없음/평가 불가 사유가 있고, 보안 4개 답변과 Langfuse 기록을 연결할 수 있다. 자동 평가 호출의 시간·토큰은 서비스 지표와 구분한다.

## 3. 초반에 맞출 연결 계약

| 연결 | 제공자 → 사용자 | 넘겨줄 정보 |
| --- | --- | --- |
| `RetrievedChunk` | A → B | `chunk_id`, `book_id`, `file_name`, `page`, `text`, 순위·점수 |
| `ContextBundle` | B → C | 최종 청크·순서·실제 텍스트, 출처 대응표, 문맥 해시 |
| `QueryResponse` | B → C | 요청 ID, 답변, 상태, 사유, 인용 |
| `RunRecord` | A·B가 제공, C가 저장·평가 | 후보/최종 문맥 구분, 실제 모델 입출력, 오류·시도별 사용량, 서버 측 처리 시간 |
| 추적 함수 | C → B | 요청 추적 시작, 검색·생성 기록, 결과 저장에 사용할 함수·콜백 |

타입 정의는 `app/core/contracts.py` 한 곳을 기준으로 한다. A·B·C가 자신의 폴더에 같은 타입을 다시 만들지 않는다. 구현 초반에는 정답 파일에서 가져오지 않은 작은 가상 청크와 가상 응답으로 각 모듈을 개발할 수 있다.

`generate_answer()`는 이미 만든 문맥과 프롬프트 변형을 받을 수 있게 B가 제공한다. C의 보안 실행기는 이 함수를 호출하여 같은 문맥을 재사용한다. `/query`를 두 번 호출해 다시 검색하는 방식으로 보안 비교를 구현하지 않는다.

## 4. 오늘의 진행표

**실작업 6시간을 가정한 제안**이다. 휴식·식사는 제외하고 T0는 세 사람이 실제로 시작하는 시각이다. 정해진 종료 시각이나 팀원의 작업 속도를 확인한 일정은 아니다.

| 시간 | A — 데이터·검색 | B — 답변·API | C — 기록·평가 | 함께 확인할 결과 |
| --- | --- | --- | --- | --- |
| T0~30분 | PDF·임베딩·Qdrant 준비 확인 | 공통 타입·앱 골격·모델 호출 확인 | Langfuse·평가 모델 접근 확인 | 계약·설정 키·대표 질문 1개 확정 |
| 30분~1.5시간 | 대표 PDF 처리·Naive 검색 전달 | Naive→문맥→생성→API 연결 | 요청 1개 추적, 평가 1개 실행 | **질문 1개가 검색부터 평가까지 연결** |
| 1.5~3시간 | PDF 전체 처리, Hybrid·리랭킹 추가 | 출처·상태·오류 처리 완성 | 질문 선정안·평가 실행기·보안 실행기 | 전체 자료·세 검색 방식 연결 |
| 3~4시간 | 세 방식 검색 결과·속도 점검 | API 통합·모델 출력 검증 | 기록 누락·평가 예외 처리 점검 | **비교 질문·공통 설정 동결** |
| 4~5.5시간 | 검색 실패·원문 근거 분석 | 답변 실패·조건 판단 분석 | 전체 일반 평가·보안 비교 실행 | 비교표, 실패 이유, 운영 지표 |
| 5.5~6시간 | 데이터·색인 재실행 안내 | 설치·API 실행 안내와 시연 | 최종 결과·선택 이유 정리 | 팀원 3명 공동 시연·완료 점검 |

첫 30분에 데이터 다운로드, 임베딩/리랭커 로딩, 모델 호출, Langfuse 접속 문제를 확인한다. 당일 가능 여부는 이 점검과 첫 평가 호출 시간에 따라 달라진다. 같은 장애에 오래 머물기보다 담당자가 실패 원인과 필요한 조치를 공유하고 다른 독립 작업을 계속한다.

최종 비교를 시작한 뒤 프롬프트·청킹·모델·공통 설정을 바꾸면 새로운 실험 ID를 사용한다. 이전과 이후 결과를 섞지 않는다. 비교 조건에 영향을 주는 수정은 해당 비교 세트 전체를 같은 조건으로 재실행한다.

## 5. 브랜치와 통합 순서

| 담당 | 작업 브랜치 예시 | 첫 PR |
| --- | --- | --- |
| B | `feat/basic-api-generation` | 공통 타입·설정·최소 API 골격 |
| A | `feat/basic-data-search` | PDF 추출·페이지 출처·Naive 검색 |
| C | `feat/basic-evaluation-tracing` | 실행 기록 타입 연동·Langfuse 추적·평가 실행기 골격 |

병합된 `main`의 설계 문서를 기준으로 개발을 시작한다. B의 공통 계약 PR이 들어오면 A와 C가 같은 기준으로 작업 브랜치를 맞춘다. B도 그 시점부터 공통 계약을 예고 없이 변경하지 않는다.

기능 전체가 완성될 때까지 기다리지 않고 **계약 → Naive 전체 연결 → 세 검색 방식 → 평가 결과** 순서로 작은 PR을 통합한다. 기본 리뷰 연결은 A의 PR을 B, B의 PR을 C, C의 PR을 A가 확인한다. 특정 모듈의 전문 검토가 필요하면 해당 담당자도 함께 확인한다.

이 계획은 팀원의 작업 배정 기준이다. 실제 GitHub 이슈 생성·실명 담당자 지정·개발 브랜치 생성·PR 병합은 아직 수행하지 않았다.

## 6. 시간이 부족할 때의 우선순위

1. 추가 기능·추가 튜닝을 줄이고 필수 서비스 연결과 평가를 먼저 끝낸다.
2. 일반 질문 수를 조정해야 하면 **최종 비교 실행 전**에 6~9개 등으로 줄일 수 있다. 답변 가능 사례와 추가 확인 또는 보류 사례를 포함하고 선정 이유를 남긴다. 실행 후 결과가 나쁜 질문을 빼지 않는다.
3. PDF 전체 처리, 세 검색 방식, Langfuse, 두 자동 평가, 보안 4개와 운영 지표는 필수 범위로 유지한다.
4. A가 모델·검색 설정에 막히면 B와 환경을 함께 확인하고, C는 평가·기록을 독립 개발한다. 연결이 안정된 후 A·B가 각자의 실패 사례를 맡아 C의 분석 부담을 나눈다.
5. 끝내지 못한 필수 항목이나 채점 실패는 사유와 후속 작업을 남긴다. 미실행 결과를 완료로 표시하지 않는다.
