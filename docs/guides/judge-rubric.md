# Judge 채점 기준 이력

[`app/evaluation/prompts/judge.txt`](../../app/evaluation/prompts/judge.txt)의 버전과 버전별 점수 변화를 기록한다. 기준은 평가를 진행하며 고치고, 고칠 때마다 아래 두 표에 한 줄씩 추가한다. 최종 비교는 마지막 버전 하나로 모든 저장 답변을 다시 채점한다.

## 바꾸는 방법

1. `judge.txt`를 고친다. 4개 항목과 0/1 채점, 해당 없음·평가 불가 규칙은 [발제 기준](../project-brief.md)을 따른다. 출력 JSON 형식과 `{{...}}` 자리표시자는 유지하고 문항 번호(S07 등)를 넣지 않는다.
2. 같은 원본 실험을 이전 기준과 새 기준으로 [재채점](c-module-guide.md#재채점)한다. 이전 기준 파일은 `git show <커밋>:app/evaluation/prompts/judge.txt > judge_prev.txt`로 꺼낸다.
3. 점수가 바뀐 문항을 원문과 대조해 의도한 변화인지 확인한다.
4. 아래 두 표를 갱신해 기준 변경과 같은 PR에 올린다.

결과의 기준 버전은 manifest의 `benchmark.judge_prompt` 해시를 아래 표의 해시와 맞춰 확인한다.

Judge 출력 스키마는 프롬프트와 별도로 `benchmark.judge_schema`에 남고 게시 조건(`evaluation_hash`)에 들어간다. `judge-output-v2`(2026-11-11)부터 `has_factual_claims`와 네 항목의 `status`·`score`·`reason`이 모두 필수이며, 하나라도 빠지거나 타입·status·score가 맞지 않으면 네 항목을 모두 평가 불가로 두고 사유에 오류를 남긴다. 이전 `judge-output-v1`(기록 없음)은 맞는 항목만 받고 `has_factual_claims`를 선택으로 다뤘다. 따라서 v1로 게시한 평가 세트 이름은 v2 결과에 다시 쓸 수 없다. `calculation_checks`가 없는 이전 기준 출력도 네 점수는 그대로 받고 진단만 평가 불가로 둔다.

`judge.txt` 밖의 채점 입력 변경은 해시가 바뀌지 않으므로 아래에 적는다. 재채점은 현재 코드로 입력을 다시 만들므로 같은 코드로 채점한 점수끼리 비교한다.

- 2026-11-09: Judge·RAGAS 문맥에 청크 제목(`heading`)을 넣었다. 생성 모델은 제목을 보는데 채점기는 보지 못해, 화주·예약번호가 제목에만 있는 Advanced에서 근거 점수가 깎였다.
- 2026-11-10: RAGAS 출력 한도를 8,192토큰으로 고정했다. 기본 1,024에서는 실제 답변의 주장 추출·검증 출력이 잘려 Faithfulness가 평가 불가(`IncompleteOutputException`)였다. Judge 입력은 바뀌지 않았다.

## 버전별 점수 변화

같은 원본 실험의 저장 답변을 각 기준으로 채점한 값이다. 칸은 1점 수/평가 대상 수이며 재채점 보고서 README의 "방식별 품질 요약"에서 옮긴다. 같은 기준으로 반복 채점한 값은 `·`로 나란히 적는다.

2026-11-10 `basic-dev-20261110`(24요청 × 4항목 = 96칸)에서 확인한 내용이다. 원문 대조와 실행 조건은 [Damsebi 결과 기록](../../experimental/Damsebi/results-2026-11-10.md)에 있다.

- 사실: v1이 0점을 준 이유가 질문이 묻지 않은 부가 정보의 누락이던 요청(S01 hybrid, S09 세 방식)이 v2에서 1점이 됐다. 기준 간 차이(5~7칸)가 같은 기준의 반복 채점 차이(1~2칸)보다 크다.
- 판단: 답할 수 있는 부분까지 보류한 부분 답변(M01 hybrid_rerank)이 v2에서 0점이 됐다. 세 번 모두 같았다.
- 조건·근거: 기준 간 차이(조건 3~6칸, 근거 2~5칸)가 v2 반복 채점 차이(조건 3~5칸, 근거 3~6칸)와 같은 크기다. 기준 효과로 보지 않는다.
- 반복 채점 차이는 v1 3칸, v2 7~12칸이다. v2에서 엇갈린 칸은 복수 근거형의 부분 답변(M01·M03)과 S04에 몰려 있다.

2026-11-11 v3는 전체 재채점이 아니라 사례 세트로 확인했다(저장 답변 고정, 문맥만 변경, 사례별 2회). 표와 판정 이유는 [v3 검증 기록](../../experimental/Damsebi/judge-v3-bc-2026-11-11.md)에 있다.

- 실제 저장 답변 9건(`judge-cases-20261111`): 검산 진단이 규칙 페이지 제거(c2)와 산입 규칙 없는 M19 문맥(c3·c4·c4b)에서 incomplete, 단순 조회(c6·c7)에서 not_applicable로 반응했다. v2+새 스키마는 c2·c4·c4b·c6을 complete로 판정했다.
- 근거 부족을 정확히 밝힌 답변(c3)은 v3 수정 1·확정본 4회 모두 사실 0·조건 1·근거 1·판단 1, 검산 incomplete였다. 사실 0은 참고 정답의 사건일·산입 일수를 답하지 못했기 때문이다.
- 검증용 가상 사례(`judge-synthetic-20261111`, 실제 데이터 아님): 원계약과 같은 대상·기간의 대체 확인서는 v2+새 스키마와 v3 모두 complete로 인정했다(기존 동작 유지). 다른 예약·만료 기간 규칙과 규칙 없음은 모두 incomplete였고, 다른 대상·기간 규칙에는 조건 0이 유지됐다.
- 남은 불일치: 청구서 산식을 검산처럼 제시한 M19 답변(c4)에서 조건 0의 사유가 "검산 완료처럼 제시"뿐인 회차가 있다(v3 확정 1회차, 2회차는 실제 반출일 누락과 함께). 실제 문서의 동등한 대체 근거 사례는 찾지 못해 미검증이다.

## 열린 결정

- 참고 정답(기대 답변) 제외: 발제는 Judge 입력에 참고 정답과 채점 기준을 넣도록 정한다. v2는 참고 정답을 유지하고 표현 일치를 요구하지 않는 방식으로 대응했다. 제외 여부는 비교 결과를 보고 정한다.
- 참고 정답의 선행 확인 절차: 질문이 직접 묻지 않았지만 참고 정답이 "먼저 확인한다"고 적은 절차(S04의 예약번호·품명 일치 확인)를 필요한 사실로 볼지 v2가 정하지 않는다. 같은 답변의 사실·조건이 9회 중 2회씩 0점이었다.
- 근거 항목의 부재 주장: "자료에 없다"는 주장에 붙인 인용과 문맥에 없는 세부 항목을 감점할지가 채점마다 갈린다(M01·M03·S12).
- 답하지 못한 항목의 귀속: 같은 누락을 사실에서만 감점할지 조건에서도 감점할지가 채점마다 갈린다(M01·M03).
- 반복 채점: 조건·근거는 한 번의 채점으로 방식 간 차이를 말하기 어렵다. 기준 문구를 보완할지, 3회 채점의 다수결을 쓸지 정한다. 문구를 고치면 개발용 문항으로만 확인한다.
